# 第六篇：实现用户编辑功能，让用户资料修改形成完整闭环

上一节，我们完成了用户新增功能，打通了从表单提交、Server Action、Service 到 Prisma 数据库写入的完整流程。

本节继续实现用户编辑。

从页面上看，编辑似乎只是把新增表单里的数据回显出来，再执行一次更新。但从工程角度看，两者有几个重要区别：

- 新增用户需要设置初始密码，编辑用户不应该接触密码字段。
- 编辑用户必须先根据 ID 查询现有记录，再将允许修改的资料回显到表单。
- 更新操作需要处理用户不存在、用户名重复等情况。
- 编辑成功后，需要刷新用户列表，并向用户反馈操作结果。

本篇仍然只允许管理员修改用户名和手机号，不在这里处理密码重置和账号启停。这些操作有不同的业务含义，后续应该作为独立功能实现。

## 一、先明确编辑功能的完整流程

我们先把编辑操作拆解成一条完整链路。

```mermaid
flowchart TD
    A[用户列表] --> B[点击编辑]
    B --> C["/admin/users/id/edit"]
    C --> D[根据 ID 查询用户]
    D --> E{用户是否存在}
    E -->|不存在| F[显示 404 页面]
    E -->|存在| G[回显用户名和手机号]
    G --> H[管理员修改资料]
    H --> I[提交表单]
    I --> J[Server Action]
    J --> K[管理员权限检查]
    K --> L[Zod 数据校验]
    L --> M{校验是否通过}
    M -->|否| N[返回错误和原始输入]
    N --> G
    M -->|是| O[调用 Service]
    O --> P[Prisma 更新数据库]
    P --> Q{更新结果}
    Q -->|用户名重复| R[返回友好提示]
    Q -->|用户不存在| S[返回不存在提示]
    Q -->|成功| T[刷新用户列表]
    T --> U[跳转用户列表并显示成功提示]
```

这里用节点文字表示路由，节点文字包含斜杠时必须加引号（`["/admin/users/id/edit"]`）。不写引号时，Mermaid 会把 `[/` 开头的内容当成平行四边形节点，渲染时报解析错误。

另外，不少博客平台不渲染 Mermaid。发布前先确认目标平台支持；不支持的话，换回文字流程描述，或者把图导出成图片。

这里有一个值得注意的设计：**新增和编辑不共用一个表单。**

虽然两者都涉及用户名和手机号，但它们的业务规则并不相同。

新增用户需要输入初始密码，编辑用户不应该允许管理员通过普通资料编辑表单修改密码。如果强行复用一个表单，就需要增加大量条件判断，表单字段、默认值、校验规则和提交逻辑都会变得复杂。

因此，我们分别维护：

- `UserCreateForm`：负责新增用户。
- `UserEditForm`：负责编辑用户。

共用的是字段校验规则，而不是整个表单组件。

## 二、抽取公共校验规则

目前用户新增和编辑都需要校验用户名和手机号。

如果两处分别定义规则，以后修改用户名长度、字符范围或手机号格式时，就可能出现新增和编辑校验不一致的问题。

因此，我们先在 `features/users/schemas.ts` 中抽取公共字段。

### 2.1 定义用户名和手机号规则

修改 `features/users/schemas.ts`：

```ts
import { z } from "zod";

// 用户名：3-30 位，只允许字母、数字和下划线
const usernameField = z
  .string()
  .trim()
  .min(3, "用户名至少 3 位")
  .max(30, "用户名不能超过 30 位")
  .regex(/^[a-zA-Z0-9_]+$/, "只能使用字母、数字和下划线")
  .transform((value) => value.toLowerCase());

// 手机号：允许为空，非空时必须符合手机号格式
const phoneField = z
  .string()
  .trim()
  .transform((value) => (value === "" ? null : value))
  .refine(
    (value) => value === null || /^1[3-9]\d{9}$/.test(value),
    "手机号格式不正确"
  );
```

这里有两个值得注意的地方。

**第一，用户名统一转换为小写。**

用户名是登录标识。统一小写可以避免 `Admin`、`admin` 被当成两个不同的登录名。

但这也意味着，用户编辑时如果提交了原来的混合大小写用户名，就会被转换成小写。

第四篇的种子数据已经改成小写 `demo_user_01`，新环境不会触发这种改名。但如果数据库里还留着早期版本写入的 `Demo_User_01`，编辑这个用户时，用户名就会被悄悄改成 `demo_user_01`。

这不是无关紧要的页面格式变化，而是登录标识发生了变化。正式业务中，修改用户名应该明确告知管理员，并在后续增加操作审计记录。

**第二，手机号统一使用 `null` 表示未填写。**

表单提交时，空输入框的值是空字符串 `""`，但数据库字段是可空字符串类型。

通过 `transform`，我们把空字符串统一转换为 `null`，避免数据库中同时存在 `""` 和 `null` 两种表达方式。

### 2.2 定义新增和编辑 Schema

继续在同一个文件中定义两个 Schema：

```ts
export const createUserSchema = z.object({
  username: usernameField,
  phone: phoneField,
  password: z
    .string()
    .min(8, "密码至少 8 位")
    .max(128, "密码不能超过 128 位"),
});

export const updateUserSchema = z.object({
  username: usernameField,
  phone: phoneField,
});

export type CreateUserInput = z.infer<typeof createUserSchema>;
export type UpdateUserInput = z.infer<typeof updateUserSchema>;
```

两个 Schema 共用用户名和手机号规则，但新增用户额外要求输入密码。

这样既保证了规则一致，又保留了不同业务操作之间的边界。

### 2.3 定义编辑表单状态

继续添加编辑表单需要的状态类型：

```ts
export type UpdateUserState = {
  message?: string;
  fieldErrors?: {
    username?: string[];
    phone?: string[];
  };
  values?: {
    username: string;
    phone: string;
  };
};
```

当校验失败时，我们需要把错误信息和用户已经填写的内容返回给表单。

这里没有把密码放进 `values`，因为编辑操作本身就不应该提交密码。

### 2.4 统一转换 Zod 字段错误

项目当前使用 Zod 4。这里使用 `z.flattenError()` 处理错误，不再继续使用已经不推荐的 `error.flatten()`。

为了让新增和编辑都使用同一种转换方式，我们增加一个公共函数：

```ts
export function toFieldErrors(
  error: z.ZodError
): Record<string, string[]> {
  const flattened = z.flattenError(error).fieldErrors;

  const result: Record<string, string[]> = {};

  for (const [key, messages] of Object.entries(flattened)) {
    if (Array.isArray(messages) && messages.length > 0) {
      result[key] = messages;
    }
  }

  return result;
}
```

这个函数将 Zod 的字段错误整理为普通对象，过滤掉没有错误信息的字段。

后续新增和编辑都复用它，避免两处使用不同的错误转换方式。第五篇的新增 Action 需要一起改，具体见下一节。

### 2.5 这次抽取会波及第五篇，需要一起改

公共字段不是「新增一个 Schema」这么简单，它会改变第五篇已经落地的行为。

原来的手机号校验用的是字符串和 `null` 的联合类型，现在改成了「空串先转 `null` 再校验」，两处实现方式不同，需要同步处理：

**1. 确认 `service.ts` 里没有同名类型**

第五篇的 `createUser` 已经写成 `import type { CreateUserInput } from "./schemas"`。如果之前照抄过更早的稿子，在文件内又写过一个本地类型：

```ts
type CreateUserInput = {
  username: string;
  phone: string | null;
  password: string;
};
```

那就会和导入的同名类型重复声明，编译直接报错。必须删除本地那个定义。

**2. `createUserAction` 必须改用 `toFieldErrors`**

不是「也可以改」，而是必须改。第五篇原来的写法是：

```ts
fieldErrors: parsed.error.flatten().fieldErrors,
```

改成：

```ts
fieldErrors: toFieldErrors(parsed.error),
```

原因是 `flatten()` 的返回类型是宽泛的索引签名，直接塞进 `CreateUserState` 时容易带上 `undefined` 值，导致某些字段出现空数组。`toFieldErrors()` 会过滤掉空数组，两个 Action 的错误结构才能真正一致。

**3. 第五篇的测试要同步**

第五篇 `schemas.test.ts` 里如果有「手机号传空串」的断言，需要确认它断言的是转换后的 `null`，而不是空字符串。字段规则只保留一份，测试也应该只保留一份。

**4. 本节总结表要补上这两项**

| 文件 | 本节改动 |
|---|---|
| `features/users/actions.ts` | 同时修改 `createUserAction` 的错误转换 |
| `features/users/schemas.test.ts` | 同步第五篇的手机号断言 |

## 三、扩展 Service：查询用户和更新用户

接下来处理数据库操作。

本节需要增加两个方法：

- `getUserById`：根据用户 ID 查询编辑页面需要的数据。
- `updateUser`：根据用户 ID 更新用户名和手机号。

数据库操作仍然统一放在 `features/users/service.ts` 中。

### 3.1 根据 ID 查询用户

首先，在 `features/users/service.ts` 中引入编辑类型：

```ts
import type {
  CreateUserInput,
  UpdateUserInput,
} from "./schemas";
```

增加查询方法：

```ts
export async function getUserById(id: string) {
  return db.user.findUnique({
    where: { id },
    select: {
      id: true,
      username: true,
      phone: true,
    },
  });
}
```

这里使用 `findUnique`，因为 User 模型中的 `id` 是主键。

特别注意 `select`：

我们只查询编辑页面真正需要的字段，没有查询 `passwordHash`。

密码哈希属于敏感数据，编辑页面没有任何理由获取它。通过明确指定查询字段，可以减少不必要的数据暴露。

### 3.2 定义更新结果类型

更新操作可能出现三种业务结果：

1. 更新成功。
2. 用户名已经被其他用户占用。
3. 用户记录不存在或已经被删除。

我们使用明确的结果对象表示这些情况，而不是通过异常消息字符串在 Service 和 Action 之间传递业务状态。

```ts
type UpdateUserResult =
  | {
      success: true;
    }
  | {
      success: false;
      code: "USERNAME_TAKEN" | "NOT_FOUND";
      message: string;
    };
```

### 3.3 实现 updateUser

继续在 `service.ts` 中增加：

```ts
export async function updateUser(
  id: string,
  input: UpdateUserInput
): Promise<UpdateUserResult> {
  try {
    await db.user.update({
      where: { id },
      data: {
        username: input.username,
        phone: input.phone,
      },
      select: {
        id: true,
      },
    });

    return { success: true };
  } catch (error) {
    const code =
      typeof error === "object" &&
      error !== null &&
      "code" in error
        ? error.code
        : undefined;

    if (code === "P2002") {
      return {
        success: false,
        code: "USERNAME_TAKEN",
        message: "用户名已存在",
      };
    }

    if (code === "P2025") {
      return {
        success: false,
        code: "NOT_FOUND",
        message: "用户不存在或已被删除",
      };
    }

    throw error;
  }
}
```

这里有三个关键点。

**第一，直接根据 P2002 判断唯一约束冲突。**

当前 User 模型只有一个唯一业务字段 `username`，因此可以直接将 P2002 映射为用户名重复。

这里不再依赖 `error.meta.target` 是否包含 `"username"`。

原因是不同 Prisma 版本和数据库适配器返回的 `target` 结构可能不同。尤其在 Prisma 7 的 PostgreSQL Driver Adapter 场景中，约束信息可能表现为数据库约束名称，而不一定是字段数组。

如果未来手机号也增加唯一约束，就需要重新设计冲突字段识别逻辑，并以实际环境中捕获到的错误结构为依据。

**第二，P2025 表示更新目标记录不存在。**

例如管理员打开编辑页面后，另一位管理员已经删除了这条用户记录。此时更新操作就可能遇到 P2025。

我们把它转换为明确的业务结果，让 Action 可以向用户返回友好提示。

**第三，绝不覆盖 passwordHash。**

更新语句只包含：

```ts
data: {
  username: input.username,
  phone: input.phone,
}
```

没有密码字段，因此不会因为编辑资料而改变用户密码。

这也是为什么不建议直接把整个表单对象传入 Prisma 更新操作。数据库写入字段应该由 Service 明确控制，而不是让表单决定可以修改哪些数据库字段。

## 四、实现 Server Action

Service 负责数据库操作，Server Action 负责接收表单、权限校验、参数校验和页面跳转。

在 `features/users/actions.ts` 中，保留现有的 `createUserAction`，增加编辑操作。

首先补充完整的导入：

```ts
"use server";

import { revalidatePath } from "next/cache";
import { redirect } from "next/navigation";
import { requireUserAdmin } from "@/lib/auth-guard";

import {
  createUserSchema,
  updateUserSchema,
  toFieldErrors,
  type CreateUserState,
  type UpdateUserState,
} from "./schemas";

import {
  createUser,
  updateUser,
} from "./service";
```

然后增加 `updateUserAction`。

关于导入路径：`actions.ts` 里用 `./schemas`、`./service` 这类相对路径，路由页面里用 `@/features/users/...`。两种写法不冲突——相对路径表示「同一模块内部依赖」，别名表示「从外部目录引用这个模块」。同一文件里不要混用两种指向同一目标的写法。

`updateUserAction` 的完整代码：

```ts
export async function updateUserAction(
  id: string,
  _prevState: UpdateUserState,
  formData: FormData
): Promise<UpdateUserState> {
  // 1. 权限检查
  await requireUserAdmin();

  // 2. 提取允许修改的字段
  const values = {
    username: String(formData.get("username") ?? ""),
    phone: String(formData.get("phone") ?? ""),
  };

  // 3. 参数校验
  const parsed = updateUserSchema.safeParse(values);

  if (!parsed.success) {
    return {
      message: "请检查表单内容",
      fieldErrors: toFieldErrors(parsed.error),
      values,
    };
  }

  // 4. 执行更新
  const result = await updateUser(id, parsed.data);

  if (!result.success) {
    return {
      message: result.message,
      fieldErrors:
        result.code === "USERNAME_TAKEN"
          ? { username: [result.message] }
          : undefined,
      values,
    };
  }

  // 5. 刷新用户列表
  revalidatePath("/admin/users");

  // 6. 跳转到用户列表
  redirect("/admin/users?updated=1");
}
```

这里需要理解几个细节。

**1. 权限检查必须放在 Action 内部。**

不能因为编辑页面只有管理员能看到，就认为提交操作天然安全。

Server Action 是服务端入口，必须在每次执行时独立进行权限校验。

当前项目中的 `requireUserAdmin()` 仍然只是开发阶段的守卫，并不是真正的用户身份认证和管理员授权。正式部署前必须替换为真实认证与权限判断。

**2. 只提取允许修改的字段。**

这里没有直接使用 `Object.fromEntries(formData.entries())`，而是明确构造 `username` 和 `phone`。

这样即使客户端额外提交了其他字段，也不会进入本次更新流程。

**3. redirect 放在 try/catch 之外。**

Next.js 的 `redirect()` 通过抛出内部控制流异常完成跳转。如果把它放进一个捕获所有异常的 `try/catch`，就可能被错误地当成普通异常处理。

本例没有必要用一个大的 try/catch 包住整个 Action。Service 已经处理了明确的业务错误，其他异常继续向上抛出即可。

## 五、实现编辑表单

接下来创建：

`features/users/components/user-edit-form.tsx`

这是一个客户端组件，使用 React 19 的 `useActionState` 管理 Server Action 的提交状态。

表单用到的 `Label` 组件已在第五篇安装（`pnpm dlx shadcn@latest add label`），这里直接复用，不需要重复安装。

完整代码：

```tsx
"use client";

import { useActionState } from "react";

import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { Label } from "@/components/ui/label";

import { updateUserAction } from "../actions";
import type { UpdateUserState } from "../schemas";

type UserEditFormProps = {
  user: {
    id: string;
    username: string;
    phone: string | null;
  };
};

const initialState: UpdateUserState = {};

export function UserEditForm({ user }: UserEditFormProps) {
  const actionWithId = updateUserAction.bind(null, user.id);

  const [state, action, pending] = useActionState(
    actionWithId,
    initialState
  );

  const usernameError = state.fieldErrors?.username?.[0];
  const phoneError = state.fieldErrors?.phone?.[0];

  return (
    <form action={action} className="space-y-4">
      <div className="space-y-2">
        <Label htmlFor="username">用户名</Label>

        <Input
          id="username"
          name="username"
          autoComplete="off"
          defaultValue={state.values?.username ?? user.username}
          aria-invalid={!!usernameError}
          aria-describedby={
            usernameError ? "username-error" : undefined
          }
          required
        />

        {usernameError && (
          <p id="username-error" className="text-sm text-destructive">
            {usernameError}
          </p>
        )}
      </div>

      <div className="space-y-2">
        <Label htmlFor="phone">手机号</Label>

        <Input
          id="phone"
          name="phone"
          autoComplete="off"
          defaultValue={state.values?.phone ?? user.phone ?? ""}
          aria-invalid={!!phoneError}
          aria-describedby={
            phoneError ? "phone-error" : undefined
          }
        />

        {phoneError && (
          <p id="phone-error" className="text-sm text-destructive">
            {phoneError}
          </p>
        )}
      </div>

      {state.message && (
        <p role="alert" className="text-sm text-destructive">
          {state.message}
        </p>
      )}

      <Button type="submit" disabled={pending}>
        {pending ? "正在保存..." : "保存修改"}
      </Button>
    </form>
  );
}
```

### 5.1 为什么使用 bind 绑定用户 ID？

编辑操作必须知道当前修改的是哪一条记录。

我们通过：

```ts
const actionWithId = updateUserAction.bind(null, user.id);
```

把用户 ID 绑定到 Server Action。

这样表单只需要提交真正允许修改的字段，不需要再增加一个隐藏的 `id` 输入框。

服务端得到的参数顺序就是：

```ts
updateUserAction(id, prevState, formData)
```

但绑定的 ID 并不可信。

`bind` 只是把参数固定在客户端提交的表单里，攻击者仍然可以构造请求，把第一个参数换成别人的用户 ID。

所以服务端还有两层兜底：

- `requireUserAdmin()` 先确认调用方有权限执行这个操作。
- `updateUser` 遇到不存在的记录会返回 `P2025` 对应的「用户不存在或已被删除」，不会把错误当成成功。

等接入真实认证之后，还需要补上「当前管理员是否有权修改这条记录」的判断，例如只有超级管理员能改其他管理员账号。绑定参数只是传参方式，不能当成权限边界。

### 5.2 为什么 defaultValue 要优先使用 state.values？

```tsx
defaultValue={state.values?.username ?? user.username}
```

这里考虑的是校验失败后的回显问题。

例如管理员把用户名修改成只有两个字符的 `ab`，提交后服务端校验失败。

Server Action 返回：

```ts
{
  message: "请检查表单内容",
  values: {
    username: "ab",
    phone: "13800138000"
  }
}
```

表单重新渲染时，优先使用 `state.values`，管理员刚才输入的内容就不会丢失。

如果没有校验失败状态，则使用数据库查询出来的原始用户资料。

### 5.3 为什么编辑表单不包含密码？

密码修改涉及身份验证、密码策略、密码哈希和安全审计，不应该混在普通资料编辑中。

当前项目新增用户使用 `argon2`（`lib/password.ts` 里的 `hashPassword`，Argon2id 参数）进行密码哈希处理，和第五篇落地时保持一致。编辑用户资料不需要读取、更不需要重新生成 `passwordHash`。

后续可以独立实现管理员重置密码和用户自主修改密码功能。

## 六、将编辑页面逻辑放入 Feature

前面实现了列表页面。当前项目已经采用这样的结构：

- `page.tsx`：负责路由布局和 Suspense 边界。
- `user-list.tsx`：负责读取查询参数、调用 Service 和渲染列表。

编辑页面也应该遵循相同的职责划分。

新增文件：

`features/users/components/user-edit.tsx`

```tsx
import { notFound } from "next/navigation";

import { Skeleton } from "@/components/ui/skeleton";
import { getUserById } from "../service";
import { UserEditForm } from "./user-edit-form";

type UserEditProps = {
  params: Promise<{
    id: string;
  }>;
};

export async function UserEdit({ params }: UserEditProps) {
  const { id } = await params;

  const user = await getUserById(id);

  if (!user) {
    notFound();
  }

  return (
    <div className="max-w-xl">
      <UserEditForm user={user} />
    </div>
  );
}

export function UserEditSkeleton() {
  return (
    <div className="max-w-xl space-y-4">
      <Skeleton className="h-5 w-24" />
      <Skeleton className="h-10 w-full" />
      <Skeleton className="h-5 w-24" />
      <Skeleton className="h-10 w-full" />
      <Skeleton className="h-10 w-28" />
    </div>
  );
}
```

这里有两个值得注意的地方。

第一，`UserEdit` 是异步 Server Component，负责读取路由参数和查询用户。

第二，用户不存在时调用 `notFound()`，显示 404 页面。

由于本项目启用了 Next.js Cache Components，动态参数读取和数据库查询应该放在 Suspense 边界内部，不能直接放在页面外层同步布局中。

另外，`notFound()` 发生在 Suspense 内部时，页面可能已经开始流式输出，HTTP 状态码不一定还能返回 404。因此这里准确地说是显示 404 页面，不应简单地保证 HTTP 响应状态一定是 404。

这里还有几个值得提前认识的工程问题。

**1. 并发编辑问题**

假设管理员 A 和管理员 B 同时打开了同一个用户的编辑页面。A 先修改手机号并保存，B 随后保存了自己页面中的旧数据。

当前实现采用普通覆盖更新，后保存的操作可能覆盖先保存的修改。

对于当前基础用户管理功能，可以暂时接受这种行为。后续如果业务数据重要，可以增加乐观锁：例如使用 `version` 字段或 `updatedAt` 时间戳作为更新条件，更新时带上读取到的旧值，只有数据库中的值没有变化才允许写入，否则返回冲突提示，让管理员重新加载页面后再修改。

**2. 用户名规范化会改变登录标识**

编辑时的 `transform` 会把用户名统一转成小写。如果数据库里还留着早期种子数据写入的 `Demo_User_01`，编辑后就会变成 `demo_user_01`。

这不是单纯的显示变化，而是登录标识发生了变化。正式业务中，修改用户名应该明确提示管理员，并记录操作审计。

**3. 编辑的边界要守住**

本篇只开放用户名和手机号。密码重置涉及身份验证与安全审计，账号启停涉及权限与登录拦截，两者都应该拆成独立功能，而不是塞进同一个表单。

`updateUser` 的 `data` 里没有 `passwordHash`，就是为了让「编辑资料不可能改密码」成为代码层面的保证，而不是靠约定。

至此，用户管理具备了列表、搜索、分页、新增和编辑的完整闭环。后续可以在此基础上继续扩展账号状态、密码重置等能力。
