# 第四篇：实现用户管理列表，从数据库到页面完整跑通

## 一、前言：本篇要实现什么？

系统基础环境已经搭建完成，接下来正式进入业务开发。

本篇实现用户管理列表，包含三个能力：

- 展示用户名、手机号、账号状态和创建时间。
- 根据用户名或手机号进行关键词搜索。
- 支持分页，每页显示 10 条数据。

本篇先完成查询，不涉及新增、编辑和删除。

开始之前，先说明四个设计取舍：

1. **沿用第三篇的 `User` 模型，但把 `status` 从字符串改成 Prisma 枚举。** 账号状态只有「启用」和「停用」两种取值，用枚举可以让数据库自己拒绝非法值，代码里也有类型提示。这需要做一次数据库迁移。
2. **页面使用 shadcn/ui 的表格、按钮、输入框和徽标组件，而不是原生 HTML 标签。** 后台系统会有大量列表和表单，统一的组件能保证风格一致，后面改样式也只需要改一处。
3. **查询直接在服务端组件中调用 Service，不使用 Server Action。** Server Action 适合新增、修改这类提交操作，下一篇实现用户新增时再使用。
4. **认证还没有接入，所以本篇的页面是公开的，只用于本地开发，请不要部署到公网。** 后续接入登录和权限后，再在服务端补上身份和角色校验。

本篇的代码按业务模块组织，用户相关的所有代码都放在 `features/users/` 目录下。本篇完成后，目录会是这样：

```text
learnenglish/
├── app/
│   └── (dashboard)/admin/users/page.tsx   ← 页面，保持很薄
├── components/
│   ├── shared/list-pagination.tsx         ← 通用分页组件
│   └── ui/                                ← shadcn/ui 生成的基础组件
├── features/users/
│   ├── components/user-list.tsx           ← 用户列表组件（查询 + 表格）
│   ├── constants.ts                       ← 状态标签等常量
│   ├── schemas.ts                         ← Zod 校验
│   ├── service.ts                         ← 查询逻辑
│   └── service.test.ts                    ← 测试
├── lib/db.ts
└── prisma/seed.ts
```

本篇的数据链路是：

**页面 → Service → Prisma → PostgreSQL。** 页面负责展示和交互，Service 负责业务查询，Zod 负责校验 URL 参数。

## 二、数据模型：把用户状态改成枚举

### 1. 修改 User 模型

打开 `prisma/schema.prisma`，在第三篇 `User` 模型的基础上，增加一个状态枚举，并把 `status` 字段的类型改成它：

```prisma
enum UserStatus {
  ACTIVE
  DISABLED
}

model User {
  id           String     @id @default(uuid())
  username     String     @unique
  passwordHash String
  phone        String?
  status       UserStatus @default(ACTIVE)
  createdAt    DateTime   @default(now())
  updatedAt    DateTime   @updatedAt
}
```

变化只有两处：新增了 `UserStatus` 枚举；`status` 的类型从 `String` 变成 `UserStatus`，默认值从字符串 `"ACTIVE"` 变成枚举值 `ACTIVE`。其他字段保持不变。

枚举有三个好处：

- **数据库级别的约束**：写入任何不是 `ACTIVE` 或 `DISABLED` 的值，数据库都会拒绝。
- **代码里有类型提示**：写错状态值，TypeScript 会直接报错，而不是等到运行时才发现。
- **新增状态时不会漏改**：后面如果增加一个「待激活」状态，所有需要处理状态的地方，编译时就会提示你。

代价是：每增加一种状态，都需要再做一次迁移。对账号状态这种变化不频繁的字段来说，这是值得的。

### 2. 执行迁移

先确认当前用户表是空的。第三篇只创建了表，没有写入数据，所以首页显示的用户数量应该是 0。也可以在 pgAdmin 里执行：

```sql
SELECT COUNT(*) FROM "User";
```

结果为 0，就可以直接迁移：

```bash
pnpm prisma migrate dev --name user_status_enum
pnpm prisma generate
```

Prisma 会生成新的迁移文件，创建 `UserStatus` 类型并替换 `status` 列。因为表里没有数据，这样操作是安全的。

迁移完成后，再执行 `generate` 重新生成 Prisma Client，否则代码里拿不到新的 `UserStatus` 类型。

> **如果你的用户表里已经有数据，请不要直接执行上面的命令。**
>
> Prisma 处理「字符串列改成枚举列」时，生成的迁移可能是先删除旧列再新增列，这会导致这一列的数据全部丢失。正确的做法是：
>
> 1. 先检查现有数据。执行 `SELECT DISTINCT "status" FROM "User";`，结果里只能有 `ACTIVE` 和 `DISABLED`，有其他值先用 `UPDATE` 修正。
> 2. 只生成迁移，不执行：`pnpm prisma migrate dev --create-only --name user_status_enum`。
> 3. 打开生成的 `migration.sql`，如果里面有 `DROP COLUMN "status"`，就把它改成下面这种原地转换的写法（这是参考写法，请以你实际的迁移文件为准）：
>
> ```sql
> CREATE TYPE "UserStatus" AS ENUM ('ACTIVE', 'DISABLED');
> 
> ALTER TABLE "User" ALTER COLUMN "status" DROP DEFAULT;
> ALTER TABLE "User"
>   ALTER COLUMN "status" TYPE "UserStatus"
>   USING ("status"::"UserStatus");
> ALTER TABLE "User" ALTER COLUMN "status" SET DEFAULT 'ACTIVE';
> ```
>
> 4. 检查无误后执行 `pnpm prisma migrate dev` 应用迁移，再执行 `pnpm prisma generate`。
>
> 在真实项目中，改表结构之前请先备份数据库。

### 3. 两个需要说明的地方

**第一，为什么列表里没有姓名和邮箱？**

在数据库设计那一篇中，我们确定了 `users` 表只保存登录账号信息，教师姓名、家长姓名等业务信息放在各自的档案表中。所以现在的用户列表展示的是账号层面的信息：用户名、手机号、状态和创建时间。等后面完成角色和人员档案后，再把姓名、角色等信息关联到列表中。

**第二，`passwordHash` 绝不能返回给前端。**

`passwordHash` 是密码哈希。后面的查询会通过 `select` 明确指定返回字段，不包含它。

shadcn/ui 和普通的组件库不一样：它不是安装后直接调用的依赖包，而是通过命令行把组件的**源代码复制到你的项目里**。之后这些代码就归你所有，可以按需修改。

这里有三个目录约定需要记住：

- **`components/ui/` 只放 shadcn/ui 生成的基础组件**。可以按需修改，但升级或重新生成时要小心覆盖。

这样分三层放，以后找组件时能立刻定位到它属于哪一层。

## 五、准备测试数据

目前数据库里没有用户，打开页面只能看到「暂无用户数据」，无法验证搜索和分页。我们先写一个脚本，批量插入 25 条测试用户。

新建 `prisma/seed.ts`：

```ts
import "dotenv/config";
import { PrismaPg } from "@prisma/adapter-pg";
import { PrismaClient, UserStatus } from "../app/generated/prisma/client";

const connectionString = process.env.DATABASE_URL;

if (!connectionString) {
  throw new Error("DATABASE_URL 环境变量未配置");
}

const db = new PrismaClient({
  adapter: new PrismaPg({ connectionString }),
});

async function main() {
  const now = Date.now();

  const users = Array.from({ length: 25 }, (_, i) => {
    const n = String(i + 1).padStart(2, "0");

    return {
      username: `demo_user_${n}`,
      passwordHash: "seed-placeholder-not-a-real-hash",
      phone: `138000000${n}`,
```

几点说明：

- 这里导入 Prisma Client 使用的是相对路径，因为这个脚本由 `tsx` 直接运行，不经过 Next.js，不识别 `@/` 别名。
- 状态值使用从生成的客户端中导出的 `UserStatus` 枚举，而不是手写字符串。
- 脚本需要自己读取 `.env`，所以第一行是 `import "dotenv/config"`。
- 测试用户的 `passwordHash` 只是占位字符串，这些账号不能登录。真正的密码哈希，我们在下一篇实现用户新增时处理。
- 用户名统一使用小写 `demo_user_01`，和后面编辑功能里的「用户名转小写」规则保持一致，避免编辑测试用户时被悄悄改名。想验证搜索不区分大小写，用大写关键词 `DEMO` 查询即可。如果之前已经用旧版脚本写入过 `Demo_User_` 开头的用户，先执行 `DELETE FROM "User" WHERE "username" LIKE 'Demo\_User%';` 清掉旧数据，再重新执行种子脚本。
- 每第 5 个用户是停用状态，创建时间依次相差一小时，方便观察排序。
- `skipDuplicates` 保证重复执行脚本不会报错（依赖 `username` 的唯一约束）。

在 `package.json` 的 `scripts` 中增加：

## 六、校验 URL 查询参数

搜索关键词和页码都来自 URL，例如 `/admin/users?keyword=demo&page=2`。URL 是用户可以随意修改的，所以必须校验。

新建 `features/users/schemas.ts`：

```ts
import { z } from "zod";

export const userListQuerySchema = z.object({
  page: z.coerce.number().int().min(1).catch(1),
  keyword: z.string().trim().max(50).catch(""),
});
```

这里使用了 `.catch()`：参数缺失或不合法时，不报错，而是退回默认值。

例如：

- `?page=abc`、`?page=1.5`、`?page=-3` 都会回到第 1 页。
- 关键词超过 50 个字符，会被当作空关键词。
- 同一个参数重复出现（例如 `?keyword=a&keyword=b`），也会被当作空关键词。

对于列表页来说，参数不合法时回到默认视图，比直接报错体验更好。

这个文件不要加 `server-only`。它不依赖服务端，以后客户端表单也可以复用同一份校验规则。

## 七、Service：实现查询和分页

新建 `features/users/service.ts`：

```ts
import "server-only";

import { db } from "@/lib/db";
import type { Prisma } from "@/app/generated/prisma/client";

type UserListParams = {
  page: number;
  pageSize: number;
  keyword: string;
};

export async function getUserList(params: UserListParams) {
  const { pageSize, keyword } = params;

  const where: Prisma.UserWhereInput = keyword
    ? {
        OR: [
          { username: { contains: keyword, mode: "insensitive" } },
          { phone: { contains: keyword } },
        ],
      }
    : {};

  const total = await db.user.count({ where });
  const totalPages = Math.max(1, Math.ceil(total / pageSize));
  const page = Math.min(Math.max(1, params.page), totalPages);

  const items = await db.user.findMany({
    where,
    select: {
      id: true,
      username: true,
      phone: true,
      status: true,
      createdAt: true,
    },
    orderBy: [{ createdAt: "desc" }, { id: "desc" }],
    skip: (page - 1) * pageSize,
    take: pageSize,
  });

  return { items, total, page, pageSize, totalPages };
}
```

这里有几个关键点：

1. **`where` 统一构建搜索条件**，用户名或手机号满足任意一个即可，并显式标注为 `Prisma.UserWhereInput` 类型。
2. **用户名搜索使用 `mode: "insensitive"`**。PostgreSQL 的 `contains` 默认区分大小写，不加这个选项，搜索 `DEMO` 就找不到 `demo_user_01`。手机号都是数字，不需要。
3. **先查总数，再修正页码。** 如果有人访问 `?page=999`，页码会被限制到最后一页，而不是显示一个空表。返回值中的 `page` 是修正后的真实页码，页面应该使用它。
4. **排序有两个字段。** 只按 `createdAt` 排序时，创建时间相同的记录顺序不稳定，翻页可能出现重复或遗漏。增加 `id` 作为第二排序字段后，顺序就是确定的。
5. **`skip` 和 `take` 实现数据库分页**，不会一次性加载全部用户。
6. **`select` 明确指定返回字段**，不包含 `passwordHash`，避免敏感数据泄露。
7. **文件顶部的 `import "server-only"`**，保证这个文件只能在服务端使用。

返回结果中的 `status` 已经是 `UserStatus` 枚举类型，页面使用时会获得完整的类型提示。

关于性能再补充一句：`contains` 相当于 SQL 的 `LIKE '%关键词%'`，普通的 B-tree 索引无法加速这类查询。当前用户量很小，没有影响；如果将来数据量很大，再考虑 PostgreSQL 的 `pg_trgm` 扩展，本篇不展开。

## 八、页面：用 shadcn/ui 展示用户列表

用户管理属于管理员功能。回顾第三篇的目录规划，我们把页面放在 `(dashboard)` 路由组下的 `admin` 目录，访问地址是 `/admin/users`。

为了让页面保持简洁，我们把它拆成四部分：

- `constants.ts`：维护状态枚举到中文标签的映射，方便多处复用。
- `UserList`：负责解析参数、调用 Service，并把搜索结果、表格、分页拼成一个列表区。
- `ListPagination`：负责上一页 / 下一页的链接和按钮，属于跨模块共用的通用组件，后面学员、教师、课程等所有列表页都会复用。
- `page.tsx`：只留标题和 Suspense 边界，负责页面骨架，不碰数据。

### 1. 状态常量

在创建列表组件之前，先把状态的中文标签提取成常量，放在单独的文件里。以后新增用户编辑、状态筛选等功能时都会复用。

新建 `features/users/constants.ts`：

```ts
import type { UserStatus } from "@/app/generated/prisma/client";

export const USER_STATUS_LABEL: Record<UserStatus, string> = {
  ACTIVE: "启用",
  DISABLED: "停用",
};
```

这个文件只维护「枚举值 → 中文标签」的映射。如果以后 `UserStatus` 新增值（比如 `PENDING`），只要在这里补上对应的标签，所有引用 `USER_STATUS_LABEL` 的地方都会自动获得类型检查。

### 2. 用户列表组件

这个组件同时承担「查询」和「渲染表格」两件事。原因是搜索框、「共 N 位用户」、翻页和表格共用同一次查询结果：只把表格拆出去的话，外层仍然要查询并分发数据，等于多一个文件而没减少逻辑。目前只有一个页面用这张表，所以先合并。

新建 `features/users/components/user-list.tsx`：

```tsx
import type { UserStatus } from "@/app/generated/prisma/client";
import { Badge } from "@/components/ui/badge";
import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { Skeleton } from "@/components/ui/skeleton";
import {
  Table,
  TableBody,
  TableCell,
  TableHead,
  TableHeader,
  TableRow,
} from "@/components/ui/table";
import { ListPagination } from "@/components/shared/list-pagination";
import { USER_STATUS_LABEL } from "@/features/users/constants";
import { userListQuerySchema } from "@/features/users/schemas";
import { getUserList } from "@/features/users/service";

const PAGE_SIZE = 10;

const STATUS_META: Record<
  UserStatus,
  { label: string; variant: "default" | "secondary" }
> = {
  ACTIVE: { label: USER_STATUS_LABEL.ACTIVE, variant: "default" },
  DISABLED: { label: USER_STATUS_LABEL.DISABLED, variant: "secondary" },
};

const dateFormatter = new Intl.DateTimeFormat("zh-CN", {
  dateStyle: "medium",
  timeStyle: "short",
  timeZone: "Asia/Shanghai",
});

export type UserListSearchParams = Promise<
  Record<string, string | string[] | undefined>
>;

export async function UserList({
  searchParams,
}: {
  searchParams: UserListSearchParams;
}) {
  const params = await searchParams;

  const query = userListQuerySchema.parse(params);
  const keyword = query.keyword;

  const { items, total, page, totalPages } = await getUserList({
    page: query.page,
    pageSize: PAGE_SIZE,
    keyword,
  });

  return (
    <div className="space-y-4">
      <form className="flex gap-2">
        <Input
          name="keyword"
          defaultValue={keyword}
          placeholder="搜索用户名或手机号"
          className="max-w-xs"
        />
        <Button type="submit">搜索</Button>
      </form>

      <p className="text-sm text-muted-foreground">共 {total} 位用户</p>

      <div className="rounded-md border">
        <Table>
          <TableHeader>
            <TableRow>
              <TableHead>用户名</TableHead>
              <TableHead>手机号</TableHead>
              <TableHead>状态</TableHead>
              <TableHead>创建时间</TableHead>
            </TableRow>
          </TableHeader>

          <TableBody>
            {items.map((user) => {
              const status = STATUS_META[user.status];

              return (
                <TableRow key={user.id}>
                  <TableCell className="font-medium">{user.username}</TableCell>
                  <TableCell>{user.phone ?? "-"}</TableCell>
                  <TableCell>
                    <Badge variant={status.variant}>{status.label}</Badge>
                  </TableCell>
                  <TableCell>{dateFormatter.format(user.createdAt)}</TableCell>
                </TableRow>
              );
            })}

            {items.length === 0 && (
              <TableRow>
                <TableCell
                  colSpan={4}
                  className="h-24 text-center text-muted-foreground"
                >
                  暂无用户数据
                </TableCell>
              </TableRow>
            )}
          </TableBody>
        </Table>
      </div>

      <ListPagination
        page={page}
        totalPages={totalPages}
        basePath="/admin/users"
        params={{ keyword }}
      />
    </div>
  );
}

export function UserListSkeleton() {
  return (
    <div className="space-y-4">
      <div className="flex gap-2">
        <Skeleton className="h-9 w-64" />
        <Skeleton className="h-9 w-16" />
      </div>

      <Skeleton className="h-4 w-24" />

      <div className="space-y-2 rounded-md border p-4">
        {Array.from({ length: PAGE_SIZE }, (_, i) => (
          <Skeleton key={i} className="h-6 w-full" />
        ))}
      </div>

      <Skeleton className="h-8 w-48" />
    </div>
  );
}
```

这个组件有几处值得说明：

- **`UserListSearchParams` 是「Promise 的参数类型」，不是参数本身。** Next.js 16 把 `searchParams` 变成了 Promise，页面拿到后可以直接往下传，不必先 `await`。组件内部 `await searchParams` 才是真正取参数的地方。
- **表格由 shadcn/ui 的 `Table` 系列组件组成**：`Table`、`TableHeader`、`TableBody`、`TableRow`、`TableHead`、`TableCell`，对应原生 HTML 的 `table`、`thead`、`tbody`、`tr`、`th`、`td`，但已经带好了统一的间距、边框和悬停效果。
- **状态使用 `Badge` 展示**，启用和停用用不同的样式区分，比纯文字更醒目。
- **`STATUS_META` 从 `constants.ts` 导入标签**，本身只维护 `variant` 样式映射。两处都是 `Record<UserStatus, ...>` 类型，枚举新增值时 TypeScript 会同时提醒你补上标签和样式。
- **`items` 的类型是自动推导出来的**，不需要手写 `Awaited<ReturnType<...>>` 那一长串。数据就在本组件里查询、本组件里渲染，TypeScript 一路都能推断。
- **这是一个服务端组件**，文件里没有 `"use client"`。它直接调用 Service，查询结果不会经过浏览器。
- **`UserListSkeleton` 是给 Suspense 用的占位。** 所有 `Skeleton` 的高度都和使用处对齐（输入框 `h-9`、表格行 `h-6`、分页按钮 `h-8`），数据到达时不会跳版。

### 3. 通用分页组件

分页在每个列表页都会用到（学员、教师、课程、订单……），而且它不关心展示的是什么，只关心页码、链接路径和要保留的其他查询参数。适合放在 `components/shared/` 下作为跨模块通用组件。

新建 `components/shared/list-pagination.tsx`：

```tsx
import Link from "next/link";
import { Button, buttonVariants } from "@/components/ui/button";

type Props = {
  page: number;
  totalPages: number;
  basePath: string;
  params?: Record<string, string | undefined>;
};

export function ListPagination({
  page,
  totalPages,
  basePath,
  params = {},
}: Props) {
  const hrefOf = (target: number) => {
    const search = new URLSearchParams();

    for (const [key, value] of Object.entries(params)) {
      if (value) search.set(key, value);
    }
    search.set("page", String(target));

    return `${basePath}?${search.toString()}`;
  };

  const linkClass = buttonVariants({ variant: "outline", size: "sm" });

  return (
    <nav aria-label="分页" className="flex items-center gap-4">
      {page > 1 ? (
        <Link href={hrefOf(page - 1)} className={linkClass}>
          上一页
        </Link>
      ) : (
        <Button variant="outline" size="sm" disabled>
          上一页
        </Button>
      )}

      <span className="text-sm">
        {page} / {totalPages}
      </span>

      {page < totalPages ? (
        <Link href={hrefOf(page + 1)} className={linkClass}>
          下一页
        </Link>
      ) : (
        <Button variant="outline" size="sm" disabled>
          下一页
        </Button>
      )}
    </nav>
  );
}
```

组件只接收四个参数：

- `page` / `totalPages`：当前页码和总页数，决定按钮显示什么、哪些能点。
- `basePath`：翻页链接的基础路径，比如 `/admin/users`。组件自己拼完整 URL，不要求页面传一个生成链接的函数进来。
- `params`：翻页时要保留的其他查询参数，比如 `{ keyword: "demo" }`。不传就当作空对象。

几个设计上的考虑：

- **为什么让组件自己拼链接，而不是让页面传函数进来？** 传字符串和对象，以后这个组件即使改成客户端组件也不会出问题；传函数则会在 props 中携带引用，影响序列化。现在是服务端组件，先把边界划清楚。
- **`Record<string, string | undefined>` 配合 `if (value)`**：调用方可以放心地写 `params={{ keyword }}`，即使 `keyword` 是空字符串也不会被拼到 URL 里。
- **`URLSearchParams`** 由浏览器和 Node.js 自带，自动处理中文和特殊字符的编码，不用手动 `encodeURIComponent`。
- **`<nav aria-label="分页">`** 把整个分页包在导航标签里，屏幕阅读器能识别这是一个分页导航，属于顺手的无障碍小优化。

### 4. 页面

新建 `app/(dashboard)/admin/users/page.tsx`：

```tsx
import { Suspense } from "react";
import {
  UserList,
  UserListSkeleton,
} from "@/features/users/components/user-list";

type Props = {
  searchParams: Promise<Record<string, string | string[] | undefined>>;
};

export default function UsersPage({ searchParams }: Props) {
  return (
    <main className="space-y-4 p-6">
      <h1 className="text-xl font-semibold">用户管理</h1>

      <Suspense fallback={<UserListSkeleton />}>
        <UserList searchParams={searchParams} />
      </Suspense>

```

页面现在只做三件事：输出标题、架好 Suspense 边界、把 `searchParams` 的 Promise 原样交给 `UserList`。

**关键是不要把 `searchParams` 先 `await` 掉。** 如果在页面里 `await searchParams` 再往下传，整页都会等参数和查询完成才开始渲染，骨架屏永远没有机会出现。把 Promise 直接往下传，页面外壳可以立刻输出，`UserList` 内部等待数据时由 Suspense 显示骨架屏。这也是 Next.js 16 把 `searchParams` 改成 Promise 的设计意图。

启动开发服务器，访问：

```text
http://localhost:3000/admin/users
```

应该能看到 25 位用户，第一页 10 条，共 3 页，状态列显示为带样式的徽标。

几个值得注意的地方：

- **搜索框和按钮使用 shadcn/ui 的 `Input` 和 `Button`**，样式和后面所有表单保持一致。
- **搜索和分页都通过 URL 参数实现**，刷新页面后查询条件仍然保留，也可以直接把链接分享给别人。
- **搜索表单是普通的 GET 表单**，提交后会跳转到带 `keyword` 的地址，并且因为没有带页码，会自动回到第一页。
- **翻页时会自动保留当前的 `keyword`**——`ListPagination` 组件在 `params` 里收到什么，翻页链接里就保留什么。
- **`UserList` 直接调用 Service**，不经过 Server Action。
- **`pnpm build` 时 `/admin/users` 会显示为 `◐ (Partial Prerender)`。** 标题和页面外壳被静态预渲染，列表数据在请求时流式补上；如果数据库慢，用户先看到骨架屏，而不是一直白屏。
- 此时 `(dashboard)` 路由组下还没有 `layout.tsx`，所以页面暂时没有左侧菜单，后面做后台布局时再补。

## 九、为什么这里不使用 Server Action

Server Action 本质上是一个可以被外部直接调用的 POST 接口。

它适合处理「提交」类操作，例如新增用户、修改资料。而列表页是通过服务端组件渲染的，直接调用 Service 更简单，也少了一层不必要的公开接口。

如果把查询也写成 Server Action，并且没有认证，等于给任何人提供了一个可以批量枚举用户的接口。所以本篇的做法是：

- 查询：服务端组件直接调用 Service。
- 提交（下一篇）：使用 Server Action，并在其中做参数校验和权限校验。

还要再强调一次：**认证接入之前，`/admin/users` 是一个任何人都能访问的页面。** 后面实现登录后，需要在服务端校验当前用户的身份和角色，例如只允许管理员访问。前端隐藏菜单不能代替服务端校验。

## 十二、常见问题

**1. `pnpm dlx shadcn@latest init` 之后页面样式变了**

`init` 会向 `app/globals.css` 写入主题颜色变量，页面的背景、文字颜色可能有轻微变化，这是正常的。如果出现不符合预期的改动，可以用 `git diff` 查看，或者回退到执行 `init` 之前的提交。

**2. 提示 `Cannot find module '@/components/ui/table'`**

说明组件还没有添加，执行 `pnpm dlx shadcn@latest add table button input badge skeleton`。如果已经添加，检查 `components.json` 里的路径别名是否与 `tsconfig.json` 中的 `@/*` 一致。

**3. 添加组件时提示文件已存在，询问是否覆盖**

说明项目里已经有同名文件。如果是你自己改过的文件，选择不覆盖；如果只是之前添加过的组件，可以放心覆盖。

**4. 终端的提示项和文中描述不一致**

shadcn/ui 的命令行会随版本更新，初始化时的问题和可选项可能不同。以终端里的实际提示为准，只要最终项目里有 `components.json`、`lib/utils.ts` 和 `components/ui/` 即可。生成的组件代码也可能与不同版本略有差异，但 `Table`、`TableRow` 等组件名保持一致。

**5. `pnpm db:seed` 提示找不到 `DATABASE_URL`**

检查 `.env` 是否在项目根目录，变量名是否是 `DATABASE_URL`。脚本第一行的 `import "dotenv/config"` 不能删除，因为 `tsx` 不会自动读取 `.env`。

**6. `pnpm db:seed` 报模块找不到或导入错误**

先确认已经执行过 `pnpm prisma generate`，并且 `app/generated/prisma` 目录存在。如果仍然报错，检查脚本里的相对路径 `../app/generated/prisma/client` 是否与你的实际目录一致。

**7. 提示 `UserStatus` 没有导出，或者 `UserStatus.ACTIVE` 报错**

说明迁移后没有重新生成 Prisma Client，执行 `pnpm prisma generate`。如果重新生成后仍然报错，可以打开 `app/generated/prisma` 目录，确认枚举实际由哪个文件导出（有的版本会单独生成 `enums.ts`），再调整导入路径。

**8. 迁移时提示会丢失 `status` 列的数据**

说明表里已经有数据。请不要确认继续，按第二章的提示框，改用 `--create-only` 生成迁移，检查并手动修改 SQL 后再执行。

**9. 测试提示 `Failed to resolve import "@/lib/db"`**

说明 `vitest.config.ts` 中的路径别名没有生效。确认配置文件在项目根目录，并且 `alias` 里 `@` 指向项目根目录。

**10. 页面提示 `server-only` 相关的错误**

说明某个客户端组件（文件顶部有 `"use client"`）引用了 `features/users/service.ts`。服务端查询只能在服务端组件中调用，客户端组件需要的数据应该由服务端组件查询后通过 props 传入。

**11. 搜索英文用户名时找不到数据**

确认 Service 里的用户名条件带有 `mode: "insensitive"`。

## 十三、本篇小结

至此，用户管理列表已经具备数据库查询、关键词搜索和分页能力，页面使用 shadcn/ui 组件搭建。

这次我们建立了一条完整的数据访问链路：

**Prisma 负责数据结构，Service 负责业务查询，Zod 负责校验 URL 参数，页面和 shadcn/ui 组件负责展示和交互。**

同时我们也明确了几个原则：

- 取值固定的字段（如账号状态）用枚举，让数据库和类型系统共同约束；修改已有数据的列类型时，先检查数据、再检查迁移 SQL。
- 界面使用统一的组件库。shadcn/ui 的组件放在 `components/ui/`，业务组件放在对应模块的 `features/<模块>/components/` 下。
- 代码按业务模块组织，用户相关的 Service、校验、组件和测试都放在 `features/users/` 下。
- 列表查询用 `select` 明确指定返回字段，不返回密码哈希。
- 搜索和分页状态放在 URL 中，刷新后依然保留。
- 分页排序必须稳定，页码必须做边界处理。
- 查询放在服务端组件里，提交操作才使用 Server Action。
- 没有认证的页面不能上线，权限必须在服务端校验。

下一篇继续实现用户新增：从表单提交、密码哈希，到服务端校验和数据库写入，完整打通用户创建流程，这时会用到 Server Action，也会用到更多 shadcn/ui 的表单组件。
