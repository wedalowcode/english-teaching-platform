# 英语教学管理平台实战开发（12）：实现角色列表功能，建立 RBAC 数据基础

## 一、前言

上一节我们接入了 Better Auth，完成了用户认证体系的调整。现在系统已经具备用户账号管理和登录能力。

接下来要进入 RBAC（基于角色的访问控制）模块。

在 RBAC 模型中，有三个核心概念：

- 用户（User）：系统的实际使用者。
- 角色（Role）：一组身份和职责的集合。
- 权限（Permission）：允许执行的具体操作。

用户通过角色获得权限，一个用户可以拥有多个角色，一个角色也可以分配给多个用户。

本节先完成角色管理的基础部分：建立角色数据模型，实现角色列表查询。

本节不实现角色新增、编辑、删除和权限分配，这些功能放在后续章节逐步完成。

阅读本节前，需要先确认三件事：

1. `ListPagination` 是用户列表那篇已经封装好的分页组件，本节直接复用。
2. `PageHeader` 和 `getMenuBreadcrumb` 来自第十篇的修订版本，项目里已经有这两个能力，本节不再重复实现。
3. 登录态统一从 `@/lib/auth-session` 的 `requireCurrentUser()` 读取，这是第十一篇调整后的位置。

另外要提前说明一个安全边界：**登录不等于管理员权限**。教师、家长账号只要能登录，默认也是已登录用户。本节会补一个临时的管理员校验，真正的角色与权限校验放到第 17 篇，在那之前不要让非管理员账号登录生产环境。

## 二、设计角色数据模型

### 2.1 设计数据关系

我们先明确本次需要建立的数据关系：

```text
User 用户
  │
  │ 1:N
  ▼
UserRole 用户角色关联
  │
  │ N:1
  ▼
Role 角色
```

这里使用独立的 `UserRole` 关联表，而不是直接在 User 表中增加一个 roleId。

原因很简单：一个教师可能同时承担教务管理工作，一个管理员也可能兼任教师。如果使用单个 roleId，就无法表达一个用户拥有多个角色的情况。

### 2.2 修改 Prisma Schema

打开 `prisma/schema.prisma`。

在现有 `User` 模型中增加一个关系字段：

```prisma
model User {
  // 原有字段保持不变

  sessions      Session[]
  accounts      Account[]

  // 用户角色关联
  userRoles     UserRole[]
}
```

注意：这里仅展示需要增加的字段，不要删除或覆盖现有 User 模型中的 Better Auth 字段。

接下来，在文件末尾增加两个模型：

```prisma
model Role {
  id          String   @id @default(uuid())
  code        String   @unique
  name        String
  description String?
  isSystem    Boolean  @default(false)

  // 角色是否启用
  isActive    Boolean  @default(true)

  // 固定角色的展示顺序，数值越小越靠前
  sort        Int      @default(0)

  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  userRoles   UserRole[]
}

model UserRole {
  id        String   @id @default(uuid())

  userId    String
  roleId    String

  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  role      Role     @relation(fields: [roleId], references: [id], onDelete: Cascade)

  createdAt DateTime @default(now())

  @@unique([userId, roleId])
  @@index([roleId])
}
```

几个字段需要解释一下：

| 字段          | 作用                      |
| ----------- | ----------------------- |
| code        | 角色唯一编码，例如 ADMIN、TEACHER |
| name        | 角色显示名称                  |
| description | 角色职责说明                  |
| isSystem    | 是否为系统内置角色               |
| isActive    | 角色是否启用，停用后不再参与授权        |
| sort        | 固定角色的展示顺序               |
| userRoles   | 用户与角色之间的关联              |

`UserRole` 中的 `@@unique([userId, roleId])` 很重要，它保证同一个用户不能重复绑定同一个角色。

`onDelete: Cascade` 表示用户或角色删除时，对应的关联记录也会自动删除。

### 2.3 把 isSystem 的含义定清楚

`isSystem` 不能理解成“比较重要的角色”，否则第 13 篇做系统角色保护时会保护错对象。

本节统一为它下这个定义：

> `isSystem = true` 表示该角色由系统预置、业务代码依赖它的 `code`、不允许删除或停用。

按照第一篇的规划，系统一共有六个业务角色：

| 编码       | 名称    | 职责                |
| -------- | ----- | ----------------- |
| BOSS     | 老板    | 查看经营数据与整体运营情况     |
| ACADEMIC | 教务人员  | 负责学生、课程和教学安排      |
| ADMIN    | 系统管理员 | 负责系统配置、用户和权限管理    |
| TEACHER  | 教师    | 负责学生授课和学习记录       |
| PARENT   | 家长    | 查看学生学习情况和课程报告     |
| AGENT    | 代理    | 负责招生渠道与代理合作       |

这六个角色全部是系统预置的，`isSystem` 都应该是 `true`。

将来通过界面新建的角色才属于自定义角色，`isSystem` 为 `false`。这样列表里的“系统角色 / 自定义角色”才和实际来源一致。

另外两个细节：

- 主键统一改用 `uuid()`。前面的 `User` 模型和认证库生成的都是字符串 ID，`cuid()` 会让同一套系统出现两种 ID 风格，没有必要的差异应该消掉。
- 不再给 `name` 加普通索引。角色搜索用的是 `contains`，最终会生成 `ILIKE '%关键词%'`，普通 B-tree 索引无法命中。第四篇已经踩过一次同样的坑，这里直接不加；将来数据量真的很大，再考虑 `pg_trgm` 一类的方案。
- `sort` 只用于固定角色排序，新建的自定义角色使用默认值 0。查询时先按 `isSystem` 排序，保证系统角色始终在前，再按 `sort` 排列。

## 三、在 Seed 中增加角色演示数据

角色列表需要有真实数据才能验证搜索、分页和用户数量统计。

项目已经有 `prisma/seed.ts`，其中包含演示用户和角色数据的创建逻辑。本节继续扩展现有 Seed，不使用 Prisma Studio 手动录入数据。

### 3.1 初始化六个内置角色

打开 `prisma/seed.ts`，把 `seedRoles()` 调整为下面的内容：

```ts
async function seedRoles() {
  /**
   * 内置角色由系统预置，业务代码依赖其 code，不允许删除。
   * sort 只决定列表里的展示顺序。
   */
  const roles = [
    {
      code: "BOSS",
      name: "老板",
      description: "查看经营数据与整体运营情况",
      sort: 10,
    },
    {
      code: "ACADEMIC",
      name: "教务人员",
      description: "负责学生、课程和教学安排",
      sort: 20,
    },
    {
      code: "ADMIN",
      name: "系统管理员",
      description: "负责系统配置、用户和权限管理",
      sort: 30,
    },
    {
      code: "TEACHER",
      name: "教师",
      description: "负责学生授课和学习记录",
      sort: 40,
    },
    {
      code: "PARENT",
      name: "家长",
      description: "查看学生学习情况和课程报告",
      sort: 50,
    },
    {
      code: "AGENT",
      name: "代理",
      description: "负责招生渠道与代理合作",
      sort: 60,
    },
  ];

  for (const role of roles) {
    await db.role.upsert({
      where: {
        code: role.code,
      },
      // 只同步系统维护的字段，不覆盖管理员后续修改的名称和说明
      update: {
        isSystem: true,
        sort: role.sort,
      },
      create: {
        ...role,
        isSystem: true,
      },
    });
  }

  console.log(`已初始化 ${roles.length} 个内置角色`);
}
```

这里使用 `upsert`，而不是每次直接创建。

它的行为是：

- 如果角色编码不存在，就创建角色。
- 如果角色编码已经存在，就更新系统维护的字段。
- 不会因为重复运行 Seed 而产生重复角色。

角色编码是业务上的稳定标识，因此使用 `code` 作为唯一条件。

关于 `update`，这里需要说清楚取舍：

- `isSystem` 和 `sort` 是系统维护的字段，界面不允许修改，因此每次 Seed 都以代码定义为准，可以覆盖。
- `name` 和 `description` 是管理员可能在后台修改的内容，这里**不写进 `update`**，避免第 13 篇开放角色编辑后，管理员改过的名称在下次执行 Seed 时被冲掉。
- 如果哪一天希望“代码里的定义永远为准”，就把 `name` 和 `description` 也加进 `update`，但要在团队里明确这是有意的行为。

### 3.2 为演示用户分配角色

只有角色数据还不够。角色列表还需要显示每个角色关联了多少用户。

继续调整 `seedDemoUserRoles()`：

```ts
async function seedDemoUserRoles() {
  const users = await db.user.findMany({
    where: {
      username: {
        startsWith: "demo_user_",
        mode: "insensitive",
      },
    },
    select: {
      id: true,
    },
    orderBy: {
      username: "asc",
    },
  });

  const roleCodes = ["TEACHER", "PARENT", "ACADEMIC", "AGENT"] as const;

  const roles = await db.role.findMany({
    where: {
      code: {
        in: [...roleCodes],
      },
    },
    select: {
      id: true,
      code: true,
    },
  });

  const roleMap = new Map(
    roles.map((role) => [role.code, role.id])
  );

  const data = users.flatMap((user, index) => {
    const roleCode = roleCodes[index % roleCodes.length];
    const roleId = roleMap.get(roleCode);

    return roleId
      ? [{ userId: user.id, roleId }]
      : [];
  });

  const result = await db.userRole.createMany({
    data,
    skipDuplicates: true,
  });

  console.log(`已建立 ${result.count} 条演示用户角色关联`);
}
```

这里按照顺序将演示用户分配给教师、家长、教务人员和代理角色。

两个细节：

- `startsWith` 默认区分大小写。虽然当前演示用户名已经是小写，但种子数据一旦被人改成 `Demo_User_01`，这里就会一条都匹配不到。加上 `mode: "insensitive"` 后，大小写不再影响关联结果。
- 使用 `skipDuplicates`，可以避免重复执行 Seed 时重复创建用户角色关联。

`createMany` 只会补充缺失的关联，不会删除已有关系。第一次执行会有新增，第二次执行新增数量为 0，最终状态保持一致。

### 3.3 为初始管理员分配 ADMIN 角色

初始管理员在第 11 篇已经拆成独立脚本 `prisma/seed-admin.ts`，由 `pnpm db:seed:admin` 执行。

这里要保证两件事：

1. 创建管理员和分配 `ADMIN` 角色在同一个事务里完成，不能出现“账号建好了但没有角色”的中间状态。
2. `ADMIN` 角色不存在时直接报错，不能静默跳过。

调整后的 `seed-admin.ts` 关键部分如下：

```ts
async function seedInitialAdmin() {
  const name = requireEnv("INIT_ADMIN_NAME");
  const email = requireEnv("INIT_ADMIN_EMAIL").toLowerCase();
  const username = requireEnv("INIT_ADMIN_USERNAME").toLowerCase();
  const password = requireEnv("INIT_ADMIN_PASSWORD");

  const existing = await db.user.findFirst({
    where: {
      OR: [{ username }, { email }],
    },
    select: { id: true },
  });

  if (existing) {
    // 管理员已存在时也要确认 ADMIN 角色，避免账号能登录却没有角色
    const adminRoleId = await requireAdminRoleId();

    await db.userRole.upsert({
      where: {
        userId_roleId: {
          userId: existing.id,
          roleId: adminRoleId,
        },
      },
      update: {},
      create: {
        userId: existing.id,
        roleId: adminRoleId,
      },
    });

    console.log(`管理员 ${username} 已存在，已确认 ADMIN 角色`);
    return;
  }

  const userId = crypto.randomUUID();
  const passwordHash = await hashPassword(password);

  await db.$transaction(async (tx) => {
    await tx.user.create({
      data: {
        id: userId,
        name,
        email,
        emailVerified: true,
        username,
        status: UserStatus.ACTIVE,

        accounts: {
          create: {
            id: crypto.randomUUID(),
            accountId: userId,
            providerId: "credential",
            password: passwordHash,
          },
        },
      },
    });

    const adminRole = await tx.role.findUnique({
      where: { code: "ADMIN" },
      select: { id: true },
    });

    if (!adminRole) {
      throw new Error("ADMIN 角色不存在，请先执行 pnpm db:seed");
    }

    await tx.userRole.create({
      data: {
        userId,
        roleId: adminRole.id,
      },
    });
  });

  console.log(`已创建初始管理员 ${username}`);
}

async function requireAdminRoleId() {
  const role = await db.role.findUnique({
    where: { code: "ADMIN" },
    select: { id: true },
  });

  if (!role) {
    throw new Error("ADMIN 角色不存在，请先执行 pnpm db:seed");
  }

  return role.id;
}
```

这里对应修正了三个容易出问题的点：

- **用户名大小写**：环境变量里的用户名先 `toLowerCase()`。Better Auth 的 username 插件会把登录用户名也规范化成小写，如果这里保留原值查找，`INIT_ADMIN_USERNAME=Admin` 就会查不到。
- **静默跳过**：角色不存在时直接 `throw`，让命令失败，而不是打印一句“跳过关联”。否则管理员能登录、却没有任何角色，做权限校验时会把自己锁在门外。
- **已存在账号**：管理员已存在时，不再简单 `return`，而是用 `userRole.upsert` 确认 `ADMIN` 关联存在。这样修复历史数据时，重复执行脚本也是安全的。

### 4.1 先补一个临时的管理员校验

在写查询之前，先把上一节留下的权限缺口补上。

现在页面和 Service 都只校验了“是否已登录”。教师、家长账号一旦能登录，就能打开 `/admin/roles` 和 `/admin/users`，看到全部角色和用户数据。

在 `lib/auth-guard.ts` 中增加一个临时方案：

```ts
import "server-only";

import { cache } from "react";
import { redirect } from "next/navigation";

import { db } from "@/lib/db";
import { requireCurrentUser } from "@/lib/auth-session";

/**
 * 临时的管理员校验：先确认已登录，再确认拥有 ADMIN 角色。
 * 第 17 篇会升级为基于角色和权限的服务端校验。
 */
export const requireAdmin = cache(async () => {
  const user = await requireCurrentUser();

  const isAdmin = await db.userRole.findFirst({
    where: {
      userId: user.id,
      role: { code: "ADMIN" },
    },
    select: { id: true },
  });

  if (!isAdmin) {
    redirect("/forbidden");
  }

  return user;
});

/**
 * 早期篇章里的写操作守卫，现在复用真正的管理员校验。
 */
export async function requireUserAdmin() {
  await requireAdmin();
}
```

`cache()` 的作用是同一次请求内去重：布局、页面、Service 都调用 `requireAdmin()` 时，只会真正查一次会话和一次角色。

还需要一个拒绝访问的落地页，创建 `app/forbidden/page.tsx`：

然后在三个位置使用它：

1. **后台布局** `app/(dashboard)/layout.tsx`：首次打开后台时就能拦下，未登录跳 `/login`，非管理员跳 `/forbidden`。
2. **页面**：角色管理、用户管理等页面入口调用 `requireAdmin()`。

第 2、3 步不能省。布局和页面的检查只在首次加载或刷新时执行，客户端切换路由时不会重新跑；真正能兜底的是 Service 入口。

到第 17 篇，`requireAdmin()` 会升级成按权限判断，调用点不需要再改。

### 4.2 定义查询参数

创建 `features/roles/schemas.ts`：

```ts
import { z } from "zod";

export const roleListQuerySchema = z.object({
  page: z.coerce.number().int().min(1).catch(1),

  keyword: z.string().trim().max(50).catch(""),
});

export type RoleListQuery = z.infer<
  typeof roleListQuerySchema
>;
```

与用户列表保持一致，支持两个查询参数：

- `page`：当前页码。
- `keyword`：角色名称或编码关键词。

通过 Zod 对 URL 参数进行校验，避免非法参数直接进入数据库查询。

这里故意把类型命名为 `RoleListQuery`，而不是 `RoleListParams`。原因是 Service 里还需要一个带 `pageSize` 的分页参数，如果两边都叫 `RoleListParams`，读者很容易以为它们含义相同。Service 侧会通过交叉类型复用这个查询类型，后面可以看到。

### 4.3 实现角色列表查询

创建 `features/roles/service.ts`：

```ts
import "server-only";

import { db } from "@/lib/db";
import { requireAdmin } from "@/lib/auth-guard";
import type { Prisma } from "@/app/generated/prisma/client";

import type { RoleListQuery } from "./schemas";

type RoleListParams = RoleListQuery & {
  pageSize: number;
};

export async function getRoleList(params: RoleListParams) {
  await requireAdmin();

  const { pageSize, keyword } = params;

  const where: Prisma.RoleWhereInput = keyword
    ? {
        OR: [
          {
            name: {
              contains: keyword,
              mode: "insensitive",
            },
          },
          {
            code: {
              contains: keyword,
              mode: "insensitive",
            },
          },
        ],
      }
    : {};

  const total = await db.role.count({ where });

  const totalPages = Math.max(
    1,
    Math.ceil(total / pageSize)
  );

  const page = Math.min(
    Math.max(1, params.page),
    totalPages
  );

  const items = await db.role.findMany({
    where,

    select: {
      id: true,
      code: true,
      name: true,
      description: true,
      isSystem: true,
      createdAt: true,

      _count: {
        select: {
          userRoles: {
            where: {
              user: { status: "ACTIVE" },
            },
          },
        },
      },
    },

    orderBy: [
      { isSystem: "desc" },
      { sort: "asc" },
      { createdAt: "asc" },
      { id: "asc" },
    ],

    skip: (page - 1) * pageSize,
    take: pageSize,
  });

  return {
    items,
    total,
    page,
    pageSize,
    totalPages,
  };
}
```

这里有几个值得注意的地方。

第一，搜索条件使用 OR。

用户输入关键词后，同时匹配角色名称和角色编码。

第二，统计关联用户数量。

```ts
_count: {
  select: {
    userRoles: {
      where: {
        user: { status: "ACTIVE" },
      },
    },
  },
},
```

Prisma 可以通过 `_count` 直接统计关联表记录数量，不需要先查询所有用户角色关联，再由 JavaScript 计算。

这里的 `where` 只统计启用状态的用户。停用账号仍然保留角色关联，方便以后恢复，但不应该出现在“当前有多少人在用这个角色”的统计里。如果产品上需要显示全部关联，可以去掉这个 `where`，但列名要同步改成“全部关联用户”，避免歧义。

第三，排序要确定。

```ts
orderBy: [
  { isSystem: "desc" },
  { sort: "asc" },
  { createdAt: "asc" },
  { id: "asc" },
],
```

系统角色排在前面，系统角色内部按 `sort` 排；自定义角色 `sort` 都是默认值，再用 `createdAt` 和 `id` 兜底。这样即使几个角色是同一秒创建的，顺序也稳定，不会每次刷新都变。

第四，分页参数在 Service 中再次校正。

```ts
const page = Math.min(
  Math.max(1, params.page),
  totalPages
);
```

例如总共只有 2 页，用户却通过 URL 访问第 10 页，Service 会将页码调整到最后一页，避免出现不合理的空白页面。

### 4.4 统一日期格式

用户列表之前用 `Intl.DateTimeFormat` 固定了上海时区并带时间，角色列表如果直接写 `toLocaleDateString("zh-CN")`，会出现两个列表格式不一致、并且依赖服务器时区的问题。

把格式化逻辑抽到 `lib/date.ts`：

```ts
const DATE_TIME_FORMATTER = new Intl.DateTimeFormat("zh-CN", {
  dateStyle: "medium",
  timeStyle: "short",
  timeZone: "Asia/Shanghai",
});

export function formatDateTime(value: Date) {
  return DATE_TIME_FORMATTER.format(value);
}
```

用户列表原来的 `formatUserDate` 改为从这个函数导出，现有组件不需要改动：

```ts
// features/users/constants.ts
export { formatDateTime as formatUserDate } from "@/lib/date";
```

角色列表则直接使用 `formatDateTime`。

## 五、实现角色列表组件

这一部分参考现有用户列表组件的实现方式。

创建 `features/roles/components/role-list.tsx`。

```tsx
import { Badge } from "@/components/ui/badge";
import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";

import {
  Table,
  TableBody,
  TableCell,
  TableHead,
  TableHeader,
  TableRow,
} from "@/components/ui/table";

import { ListPagination } from "@/components/shared/list-pagination";
import { formatDateTime } from "@/lib/date";

import { roleListQuerySchema } from "@/features/roles/schemas";
import { getRoleList } from "@/features/roles/service";

const PAGE_SIZE = 10;

type RoleListSearchParams = Promise<
  Record<string, string | string[] | undefined>
>;

export async function RoleList({
  searchParams,
}: {
  searchParams: RoleListSearchParams;
}) {
  const params = await searchParams;

  const query = roleListQuerySchema.parse(params);

  const keyword = query.keyword;

  const {
    items,
    total,
    page,
    totalPages,
  } = await getRoleList({
    page: query.page,
    pageSize: PAGE_SIZE,
    keyword,
  });

  return (
    <div className="space-y-4">
      <form className="flex gap-2">
        <Input
          name="keyword"
          defaultValue={keyword}
          placeholder="搜索角色名称或编码"
          className="max-w-xs"
        />

        <Button type="submit">
          搜索
        </Button>
      </form>

      <p className="text-sm text-muted-foreground">
        共 {total} 个角色
      </p>

      <div className="rounded-md border bg-card">
        <Table>
          <TableHeader>
            <TableRow>
              <TableHead>角色名称</TableHead>
              <TableHead>角色编码</TableHead>
              <TableHead>角色说明</TableHead>
              <TableHead>关联用户</TableHead>
              <TableHead>角色类型</TableHead>
              <TableHead>创建时间</TableHead>
            </TableRow>
          </TableHeader>

          <TableBody>
            {items.map((role) => (
              <TableRow key={role.id}>
                <TableCell className="font-medium">
                  {role.name}
                </TableCell>

                <TableCell>
                  <code className="text-sm">
                    {role.code}
                  </code>
                </TableCell>

                <TableCell>
                  {role.description ?? "-"}
                </TableCell>

                <TableCell>
                  {role._count.userRoles}
                </TableCell>

                <TableCell>
                  {role.isSystem ? (
                    <Badge variant="secondary">
                      系统角色
                    </Badge>
                  ) : (
                    <Badge variant="outline">
                      自定义角色
                    </Badge>
                  )}
                </TableCell>

                <TableCell>
                  {formatDateTime(role.createdAt)}
                </TableCell>
              </TableRow>
            ))}

            {items.length === 0 && (
              <TableRow>
                <TableCell
                  colSpan={6}
                  className="h-24 text-center text-muted-foreground"
                >
                  暂无角色数据
                </TableCell>
              </TableRow>
            )}
          </TableBody>
        </Table>
      </div>

      <ListPagination
        page={page}
        totalPages={totalPages}
        basePath="/admin/roles"
        params={{ keyword }}
      />
    </div>
  );
}
```

这里重点看最后的分页组件：

```tsx
<ListPagination
  page={page}
  totalPages={totalPages}
  basePath="/admin/roles"
  params={{ keyword }}
/>
```

它与用户列表中的用法保持一致。

`ListPagination` 已经封装了上一页、下一页、页码显示以及 URL 参数拼接逻辑。

我们只需要传入：

| 参数         | 说明        |
| ---------- | --------- |
| page       | 当前页码      |
| totalPages | 总页数       |
| basePath   | 当前列表页面地址  |
| params     | 需要保留的查询参数 |

例如当前访问：

```text
/admin/roles?page=2&keyword=教师
```

点击下一页后，组件会自动生成：

```text
/admin/roles?keyword=%E6%95%99%E5%B8%88&page=3
```

这样就不需要在角色列表中再次实现分页 URL 的生成逻辑。

这也是组件复用的意义：分页规则只维护一份，所有列表页面使用相同的行为。

## 九、本节总结与后续规划

本节完成了 RBAC 的第一阶段：角色基础数据管理。

现在系统已经具备：

- Role 角色模型。
- UserRole 用户角色关联模型。
- 六个内置角色和固定的展示顺序。
- 角色初始化 Seed，以及可重复执行的用户角色关联。
- 管理员创建与 `ADMIN` 角色分配的事务保证。
- 临时的 `requireAdmin()` 校验，覆盖布局、页面和 Service。
- 角色列表 Service。
- 角色列表页面。
- 关键词搜索、启用用户统计和复用分页组件。

从架构角度看，本节有三个值得坚持的原则：

第一，业务数据统一通过 Seed 管理。

开发环境中的演示数据、初始化数据应该可以重复生成，而不是依赖开发人员手动操作数据库。这样项目换环境、重建数据库时，才能保持一致。

第二，公共能力不要重复实现。

用户列表和角色列表使用同一个 `ListPagination`，日期格式也统一从 `lib/date.ts` 获取。未来课程列表、学生列表、订单列表也应该遵循相同的模式。

第三，权限校验要放在真正保护数据的位置。

布局和页面负责体验，Service 负责安全。只做页面级校验，换一条路径就能绕过。

接下来 RBAC 模块可以按照以下顺序推进：

| 篇目     | 主题      | 核心内容                      |
| ------ | ------- | ------------------------- |
| 第 13 篇 | 角色新增与编辑 | 角色表单、编码唯一性、系统角色保护         |
| 第 14 篇 | 用户角色关联  | 为用户分配多个角色                 |
| 第 15 篇 | 权限模型    | Permission、RolePermission |
| 第 16 篇 | 角色权限分配  | 角色与权限的关联管理                |
| 第 17 篇 | 服务端权限校验 | 基于角色和权限控制操作               |
| 第 18 篇 | 动态菜单    | 根据用户权限加载菜单                |

还有几件事需要在后续篇章里明确：

- **角色编码格式**：当前约定是“大写字母开头，只包含大写字母、数字和下划线”。第 13 篇做新增表单时要用 Zod 把这个规则固定下来，不能只靠口头约定。
- **角色与档案表的关系**：给用户分配 `TEACHER` 角色，是否要求必须存在教师档案？给用户分配 `PARENT` 角色，是否必须关联家长档案？这个约束放到第 14 篇处理，本节只建立角色本身。
- **Better Auth Admin 插件**：如果以后启用它的 Admin 插件，它自带的 `role` 字段会和这里的 `UserRole` 形成两个角色来源。届时必须二选一，建议继续以 `UserRole` 为唯一来源，不要同时维护两套。
- **生产环境安全**：在第 17 篇完成真正的权限校验之前，页面级权限只有本节这个临时的 `requireAdmin()`。不要让非管理员账号登录生产环境。

最终目标不是做出一个能展示角色名称的列表，而是建立一套能够在真实教培项目中使用的用户、角色、权限体系。
