# 英语教学管理平台实战开发（11）：接入 Better Auth，重构用户模型并实现用户名密码登录

前面几篇，我们围绕用户管理完成了用户列表、新增、编辑、密码重置、启用停用、删除以及后台整体布局。

但是，目前系统还存在一个非常重要的问题：**我们虽然已经有了用户表，却还没有真正的身份认证体系。**

之前的用户管理主要围绕业务 CRUD 展开：

- 用户名和密码保存在 User 表中。
- 使用 Argon2id 对密码进行哈希。
- 用户状态通过 ACTIVE、DISABLED 控制。
- 后台操作通过开发环境守卫临时限制。

这些实现能够帮助我们理解用户管理的基本原理，但如果准备把系统作为真实项目交付，就不能继续自己维护 Cookie、Session、密码校验和登录状态。

本篇开始引入 Better Auth，重新设计用户认证模型。

## 一、先理解：认证系统到底负责什么？

在一个真正的业务系统中，用户管理和身份认证并不是一回事。

用户管理解决的是：

- 创建用户。
- 修改用户资料。
- 设置用户状态。
- 重置密码。
- 管理用户账号。

身份认证解决的是：

- 用户如何证明自己的身份？
- 密码如何验证？
- 登录成功后如何保持登录状态？
- Session 如何创建、验证和失效？
- 用户退出后如何销毁登录状态？

除此之外，还有第三个问题：用户登录后能够做什么？

这属于授权体系，后续我们会通过 RBAC 实现。

因此，整个系统应该分成三个层次：

```text
┌────────────────────────────────────┐
│             业务授权 RBAC           │
│       用户角色、权限、数据范围       │
├────────────────────────────────────┤
│             身份认证                │
│    登录、密码校验、Session、退出     │
├────────────────────────────────────┤
│             用户管理                │
│       用户资料、状态、账号维护       │
└────────────────────────────────────┘
```

本篇重点解决中间这一层，同时调整底层用户模型，为后续 RBAC 做好准备。

## 二、为什么选择 Better Auth？

Better Auth 是一个面向 TypeScript 应用的认证框架，支持多种数据库适配器，也提供用户名、密码、Session 等认证能力。

与自己编写登录系统相比，它可以承担大量通用认证工作：

- 用户名密码认证。
- 密码哈希和验证。
- Session 创建与验证。
- Cookie 管理。
- 登录和退出接口。
- 多设备会话管理。
- 后续扩展其他认证方式。

我们当前使用 Next.js App Router、Prisma 7 和 PostgreSQL，Better Auth 提供了对应的 Prisma Adapter，可以直接融入现有项目。

本篇代码基于以下版本，其他版本的 API 可能有差异：

| 依赖 | 版本 |
|---|---|
| Next.js | 16.4.5 |
| better-auth | 1.7.18 |
| Prisma | 7.10 |
| React | 19.3 |

Better Auth 在 1.6 到 1.8 之间调整过插件配置项和 CLI 子命令，官方文档有时会同时出现稳定版与测试版的内容。阅读时先确认版本文档，再对照本文代码，不要混用。

本项目采用以下组合：

| 技术 | 用途 |
|---|---|
| Better Auth | 身份认证 |
| Username Plugin | 用户名登录 |
| Prisma Adapter | 持久化认证数据 |
| PostgreSQL | 保存用户、账号和 Session |
| Argon2id | 密码哈希 |
| Next.js Route Handler | 承载认证接口 |
| RBAC | 后续实现业务授权 |

这里特别强调：Better Auth 不负责替我们设计教培机构的业务权限。它解决的是身份认证，不是整个业务系统的权限模型。

## 三、重构 User 数据模型

这是本篇最重要的调整。

之前的 User 模型：

```prisma
enum UserStatus {
  ACTIVE
  DISABLED
}

model User {
  id           String     @id @default(uuid())
  username     String     @unique
  passwordHash String
  phone        String?
  status       UserStatus @default(ACTIVE)
  createdAt    DateTime   @default(now())
  updatedAt    DateTime   @updatedAt
}
```

这个模型有一个明显的问题：它把用户身份、登录凭证和业务资料混在了一张表中。

Better Auth 采用另一种设计：

- User：用户身份资料。
- Account：认证账号和凭证。
- Session：登录会话。
- Verification：验证码及验证令牌。

密码不再放在 User 表，而是放在 Account 表中。

这也是为什么我们要调整现有数据模型。

### 3.1 新的用户模型

修改 `prisma/schema.prisma`。

首先保留用户状态枚举：

```prisma
enum UserStatus {
  ACTIVE
  DISABLED
}
```

然后重新设计 User：

```prisma
model User {
  id              String     @id
  name            String
  email           String     @unique
  emailVerified   Boolean    @default(false)
  image           String?

  username        String?    @unique
  phone           String?
  status          UserStatus @default(ACTIVE)

  createdAt       DateTime   @default(now())
  updatedAt       DateTime   @updatedAt

  sessions        Session[]
  accounts        Account[]
}
```

这里有几个重要变化：

**第一，增加 name。**

name 是用户的展示名称，不再直接把 username 当作用户的姓名。

例如：

- username：teacher_001
- name：张老师

**第二，增加 email，而且必须唯一。**

Better Auth 的核心 User 模型要求 email 必填且唯一。即使本项目用用户名登录，也要为账号保存一个邮箱。

这里必须提前定一条规则，否则做到「新增用户」时一定会卡住：**新增用户表单要求录入真实邮箱。**

教师、家长、代理中确实有一部分人没有邮箱。对这部分账号，统一使用机构内部占位邮箱：

```text
<用户名>@users.internal
```

例如 `teacher_001@users.internal`。

这个地址不用于收信，只用来满足唯一性约束，也便于一眼看出是内部占位账号。不要使用 `test@test.com` 这种会被多人重复使用的地址，否则唯一约束会直接报错。

如果后续确认大部分用户都没有邮箱，应该在正式推广前评估改用手机号认证，而不是继续堆积占位地址。

**第三，username 仍然保留。**

它是登录标识，由 Username 插件管理。

**第四，phone 和 status 继续保留。**

手机号属于业务联系资料，status 用于控制账号是否允许使用。

### 3.2 增加 Session 模型

```prisma
model Session {
  id        String   @id
  expiresAt DateTime
  token     String   @unique

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  ipAddress String?
  userAgent String?

  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
}
```

Session 表用于保存用户的登录会话。

每次登录成功，Better Auth 会创建对应的 Session。

用户再次访问系统时，浏览器携带 Cookie，Better Auth 根据 Session Token 验证身份。

用户退出时，会话可以被销毁。

### 3.3 增加 Account 模型

```prisma
model Account {
  id                    String    @id
  accountId             String
  providerId            String

  userId                String
  user                  User      @relation(fields: [userId], references: [id], onDelete: Cascade)

  accessToken           String?
  refreshToken          String?
  idToken               String?

  accessTokenExpiresAt  DateTime?
  refreshTokenExpiresAt DateTime?

  scope                 String?
  password              String?

  createdAt             DateTime  @default(now())
  updatedAt             DateTime  @updatedAt

  @@index([userId])
}
```

Account 与 User 是多对一关系。

一个用户未来可以关联多个认证账号，例如：

- 用户名密码。
- 微信登录。
- Google 登录。
- 其他 OAuth 账号。

当前我们只使用用户名密码，因此 Account 中的 `providerId` 对应 `credential`。

密码哈希保存在 Account.password。

### 3.4 增加 Verification 模型

```prisma
model Verification {
  id         String   @id
  identifier String
  value      String
  expiresAt  DateTime

  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt
}
```

Verification 用于保存认证过程中的验证信息。

例如后续接入邮箱验证、密码找回、验证码等功能时，都可能使用它。

至此，认证模型已经基本建立。

也可以让 CLI 生成一版模型再对比：

```bash
pnpm dlx @better-auth/cli@latest generate --config lib/auth.ts
```

需要注意，本项目在 `lib/auth.ts` 顶部写了 `import "server-only"`，CLI 在 Next.js 之外加载这个文件时会直接报错。要么临时注释掉这一行再生成，要么以本文模型为准，逐个字段核对。**不要用 CLI 输出整体覆盖现有的 schema**，否则会丢掉 `phone`、`status`、`UserRole` 等业务字段。

### 3.5 这一改动会打断前面所有用户管理代码

这是本篇最容易被忽略、但一定会踩到的问题：`User` 表去掉了 `passwordHash`，新增了必填的 `name` 和 `email`。上一篇结束时能跑通的代码，改完模型后会直接编译失败。

本篇不是「下一篇再衔接」，所以把改造清单一次列清楚。改完本节，项目应该重新处于可运行状态。

**1. `lib/password.ts`**

保留 `hashPassword` / `verifyPassword`，但把 Argon2id 参数抽到一个不带 `server-only` 的文件里，方便 seed 脚本复用。具体见第五章。

**2. `features/users/service.ts`**

- `createUser`：不再写 `passwordHash`。先 `crypto.randomUUID()` 生成用户 ID，再用嵌套写入同时创建 user 和 credential account：

  ```typescript
  const userId = crypto.randomUUID();

  await db.user.create({
    data: {
      id: userId,
      name: input.name,
      email: input.email,
      username: input.username,
      phone: input.phone ?? null,
      status: "ACTIVE",
      accounts: {
        create: {
          id: crypto.randomUUID(),
          accountId: userId,
          providerId: "credential",
          password: await hashPassword(input.password),
        },
      },
    },
    select: { id: true },
  });
  ```

  `accountId` 必须等于 `userId`，Better Auth 的 credential 认证靠这个字段关联用户。

- `resetUserPassword`：改为更新 `Account.password`，账号不存在时补建：

  ```typescript
  const account = await db.account.findFirst({
    where: { userId: id, providerId: "credential" },
    select: { id: true },
  });

  const password = await hashPassword(newPassword);

  if (account) {
    await db.account.update({
      where: { id: account.id },
      data: { password },
    });
  } else {
    await db.account.create({
      data: {
        id: crypto.randomUUID(),
        accountId: id,
        providerId: "credential",
        userId: id,
        password,
      },
    });
  }
  ```

- `getUserList` / `getUserById`：`select` 改为 `id`、`name`、`email`、`username`、`phone`、`status`、`createdAt`、`updatedAt`，删除所有 `passwordHash`。
- `createUser` 的 P2002 分支：除了 `username`，还要处理 `email`，提示「邮箱已被使用」。
- 列表搜索条件增加 `email`。

**3. `features/users/schemas.ts`**

新增必填的 `name` 与 `email`，并统一转小写：

```typescript
const nameField = z.string().trim().min(1, "请输入姓名").max(50);

const emailField = z
  .email("邮箱格式不正确")
  .max(100, "邮箱不能超过 100 位")

```

**4. 创建、编辑表单**

- 新增用户：增加「姓名」「邮箱」两个输入框，提交后 `CreateUserState.values` 需要带上这两个字段，校验失败时回填。
- 编辑用户：增加「姓名」「邮箱」，且姓名、邮箱都必填。
- `users/new/page.tsx`、`users/[id]/edit/page.tsx` 的说明文字同步调整。

**5. `prisma/seed.ts`**

## 五、配置 Better Auth

在项目中创建：

```text
lib/
├── auth.ts
├── auth-client.ts
├── password.ts
└── password-config.ts
```

### 5.1 复用 Argon2id

当前项目已经有 `lib/password.ts`，其中实现了 Argon2id 哈希和验证。

问题在于这个文件顶部有 `import "server-only"`。seed 脚本用 `tsx` 在 Next.js 之外运行时，加载它就会报错。所以我们把参数单独抽出来。

新建 `lib/password-config.ts`（**不要**加 `server-only`）：

```typescript
// Argon2id 参数。放在不带 server-only 的模块里，方便 seed 脚本复用。
// 调整参数时，已有用户的密码哈希仍可验证，但新哈希会使用新参数。
export const argon2Params = {
  memoryCost: 19456,
  timeCost: 2,
  parallelism: 1,
};
```

`lib/password.ts` 改为引用它：

```typescript
import "server-only";
import * as argon2 from "argon2";

import { argon2Params } from "@/lib/password-config";

export async function hashPassword(password: string) {
  return argon2.hash(password, {
    type: argon2.argon2id,
    ...argon2Params,
  });
}

export async function verifyPassword(
  password: string,
  passwordHash: string
) {
  return argon2.verify(passwordHash, password);
}
```

Better Auth 默认使用 scrypt。

我们通过自定义密码配置继续使用 Argon2id，避免项目中出现两套密码哈希规则。

### 5.2 创建认证服务

创建 `lib/auth.ts`：

```typescript
import "server-only";

import { APIError } from "better-auth/api";
import { prismaAdapter } from "better-auth/adapters/prisma";
import { betterAuth } from "better-auth";
import { username } from "better-auth/plugins";

import { db } from "@/lib/db";
import { hashPassword, verifyPassword } from "@/lib/password";

export const auth = betterAuth({
  database: prismaAdapter(db, {
    provider: "postgresql",
  }),

  baseURL: process.env.BETTER_AUTH_URL,
  secret: process.env.BETTER_AUTH_SECRET,

  emailAndPassword: {
    enabled: true,

    // 本项目不开放用户自行注册，账号由管理员创建
    disableSignUp: true,

    password: {
      hash: hashPassword,

      verify: ({ password, hash }) => {
        return verifyPassword(password, hash);
      },
    },
  },

  plugins: [
    username({
      minUsernameLength: 3,
      maxUsernameLength: 30,

      // 不需要额外保存 displayUsername
      displayUsername: false,

      // 只拦截 update-user 接口的改名请求
      immutableUsername: true,
    }),
  ],

  user: {
    additionalFields: {
      phone: {
        type: "string",
        required: false,
        input: false,
      },

      status: {
        type: ["ACTIVE", "DISABLED"],
        required: true,
        defaultValue: "ACTIVE",
        input: false,
      },
    },
  },

  databaseHooks: {
    session: {
      create: {
        // 创建会话（即登录成功的最后一步）之前检查账号状态
        before: async (session) => {
          const user = await db.user.findUnique({
            where: {
              id: session.userId,
            },
            select: {
              status: true,
            },
          });

          if (!user) {
            throw new APIError("UNAUTHORIZED", {
              message: "账号不存在，请联系管理员",
            });
          }

          if (user.status === "DISABLED") {
            throw new APIError("UNAUTHORIZED", {
              message: "账号已停用，请联系管理员",
            });
          }
        },
      },
    },
  },
});
```

这里有几个值得理解的地方。

**第一，使用 Prisma Adapter。**

Better Auth 不需要自己管理数据库连接，直接复用项目中的 `db`。

**第二，使用 Username 插件。**

它扩展了 Email & Password 认证，让用户可以使用用户名登录。

插件默认会把用户名规范化成小写，登录查询时也按小写匹配。所以**不需要**再手写 `username.toLowerCase()`，写了反而容易在两处规则不一致时出问题。

**第三，关闭公开注册。**

教培平台的账号应该由机构管理员创建，而不是任何人都能自行注册。

**第四，`immutableUsername` 的真实作用范围。**

它只拦截经过 Better Auth `update-user` 接口的改名请求。本项目的管理员编辑用户是直接用 Prisma 更新 `User.username`，**不受这个开关限制**。

所以准确的说法是「用户自己不能通过认证接口改用户名」，而不是「用户名不允许修改」。管理员改名后，旧 Session 仍然有效，因为 Session 关联的是 `userId`，不是用户名。

**第五，状态检查放在 `databaseHooks.session.create.before`，不能放在 `hooks.before`。**

这是本篇一个重要的安全细节。如果写成登录入口的前置钩子：

```typescript
hooks: {
  before: createAuthMiddleware(async (ctx) => {
    // 风险写法，不要使用
  }),
},
```

钩子在**验证密码之前**执行。任何人只要猜对用户名，不需要密码，就能得到「账号已停用」的提示，等于确认了这个账号存在且被停用。

放到 `session.create.before` 后，执行时机变成「密码已验证通过 → 准备创建会话」，只有账号本人输对密码才会看到停用提示。猜用户名的人只会收到统一的「用户名或密码错误」。

**关于 Better Auth Admin 插件。**

Better Auth 官方提供了 Admin 插件，具备封禁/解封用户、设置角色、撤销用户会话、管理员创建用户等能力。它和我们自己维护的 `status` 字段在「封禁」这一点上有重叠。

本篇先用手写的 `status`，原因是后续 RBAC 的角色模型需要和业务角色（教师、学员、家长、代理）绑定，不完全等同于 Admin 插件里的 `role` 字段。等 RBAC 设计完成后再评估是否迁移到 Admin 插件，避免两套封禁逻辑并存。

### 5.3 创建客户端认证实例

创建 `lib/auth-client.ts`：

```typescript
import { createAuthClient } from "better-auth/react";
import { usernameClient } from "better-auth/client/plugins";

export const authClient = createAuthClient({
  plugins: [
    usernameClient({
      displayUsername: false,
    }),
  ],
});
```

服务端的 Username 插件和客户端插件需要保持一致。

这样，客户端才能获得用户名登录相关的方法和类型。

### 5.4 登录限流

Better Auth 内置了限流，不需要额外依赖：

- `rateLimit.enabled` 默认等于 `NODE_ENV === "production"`，也就是**开发环境默认不限制**。
- 默认窗口 `window: 10`（秒），`max: 100`。
- `/sign-in/*`、`/sign-up/*`、`/change-password`、`/change-email` 有更严格的单独规则：10 秒内 3 次。

对登录接口来说，10 秒 3 次略显严格，但方向是对的，能挡住低成本的密码爆破。开发时如果频繁被拦，说明你在反复试错，而不是限制本身有问题。

默认计数保存在内存里。多实例部署时每个实例各算各的，等于把额度放大了 N 倍。生产环境如果有多实例，应配置 `secondaryStorage`（例如 Redis），让限流计数共享。

如果希望开发环境也能验证限流行为，可以显式打开：

```typescript
rateLimit: {
  enabled: true,
  window: 60,
  max: 20,
},
```

注意 `customRules` 是在默认规则之上追加，不会覆盖 `/sign-in` 的特殊规则。

## 七、数据库迁移

修改完 Prisma Schema 后，执行：

项目里的 Prisma 配置文件叫 `prisma7.config.ts`，不是默认的 `prisma.config.ts`，所以每条命令都要带 `--config`。这里刻意写成单行：Windows PowerShell 的 `\` 不是续行符，反斜杠换行粘贴进去会直接报错。

**开发环境（数据可以丢）**

新模型给 `User` 加了必填的 `name`、`email`，旧数据没有值可以回填，`migrate dev` 会卡在「添加必填列」这一步。开发库里都是演示数据，最干净的做法是重置：

```bash
pnpm exec prisma migrate reset --config prisma7.config.ts
pnpm exec prisma migrate dev --config prisma7.config.ts --name add_better_auth
pnpm exec prisma generate --config prisma7.config.ts
pnpm run db:seed
pnpm run db:seed:admin
```

`migrate reset` 会清空数据库并重放已有迁移，确认当前库里没有需要保留的数据再执行。

**已有真实数据（不能丢）**

不能直接 `migrate dev`，必须先手工生成迁移再补数据：

```bash
pnpm exec prisma migrate dev --config prisma7.config.ts --name add_better_auth --create-only
```

然后编辑生成的 `migration.sql`，按「加可空列 → 回填 → 设非空 → 建 Account → 删旧列」的顺序改成可执行脚本，最后再 `migrate dev` 应用。

这里需要特别注意现有数据。

如果只是开发环境，并且原来的用户都是测试数据，可以在确认没有需要保留的数据后重新初始化数据库，再使用新的账号初始化流程。

如果库里已有真实用户，迁移必须自己写，`prisma migrate dev` 不会替你想清楚这三件事：

1. **`name` 从哪来。** 旧表没有姓名，只能用用户名临时填充，后续人工订正：

   ```sql
   ALTER TABLE "User" ADD COLUMN "name" TEXT;
   UPDATE "User" SET "name" = "username" WHERE "name" IS NULL;
   ALTER TABLE "User" ALTER COLUMN "name" SET NOT NULL;
   ```

2. **`email` 从哪来。** 这是最容易卡住的一列。真实用户可能根本没有邮箱，而这一列既要非空又要唯一。可行做法是按第 3.1 节的约定批量生成内部占位地址：

   ```sql
   ALTER TABLE "User" ADD COLUMN "email" TEXT;
   UPDATE "User" SET "email" = "username" || '@users.internal' WHERE "email" IS NULL;
   ALTER TABLE "User" ALTER COLUMN "email" SET NOT NULL;
   CREATE UNIQUE INDEX "User_email_key" ON "User"("email");
   ```

3. **密码去哪。** 原来的 Argon2id 哈希可以整体搬进 Account 表：

   ```sql
   INSERT INTO "Account" (
     "id",
     "accountId",
     "providerId",
     "userId",
     "password",
     "createdAt",
     "updatedAt"
   )
   SELECT
     gen_random_uuid()::text,
     "id",
     'credential',
     "id",
     "passwordHash",
     NOW(),
     NOW()
   FROM "User"
   WHERE "passwordHash" IS NOT NULL;
   ```

**顺序不能反**：先把 Account 数据写进去，确认每个用户都有对应账号，最后才执行 `ALTER TABLE "User" DROP COLUMN "passwordHash"`。一旦先删列，密码就再也拿不回来了。

实际执行前，需要按照 Prisma 生成的迁移文件核对表名、字段名、ID 类型和约束。

迁移完成后，原有 Argon2id 密码可以继续由我们配置的 `verify` 函数验证，不需要强迫所有用户重新设置密码。

### 8.1 实现登录表单

`features/auth/components/login-form.tsx`：

```tsx
"use client";

import { useState } from "react";
import { useRouter } from "next/navigation";

import { authClient } from "@/lib/auth-client";

import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { Label } from "@/components/ui/label";

export function LoginForm() {
  const router = useRouter();

  const [username, setUsername] = useState("");
  const [password, setPassword] = useState("");
  const [error, setError] = useState("");
  const [loading, setLoading] = useState(false);

  async function handleSubmit(
    event: React.FormEvent<HTMLFormElement>
  ) {
    event.preventDefault();

    setError("");
    setLoading(true);

    try {
      const result = await authClient.signIn.username({
        username,
        password,
      });

      if (result.error) {
        // 用户名或密码错误统一提示，避免泄露账号是否存在。
        // 账号停用的提示只有在密码校验通过后才会出现，可以原样展示。
        const isCredentialError =
          result.error.code === "INVALID_USERNAME_OR_PASSWORD";

        setError(
          isCredentialError
            ? "用户名或密码错误"
            : result.error.message || "登录失败，请稍后重试"
        );
        return;
      }

      router.replace("/admin/users");
      router.refresh();
    } catch {
      setError("登录失败，请稍后重试");
    } finally {
      setLoading(false);
    }
  }

  return (
    <form
      onSubmit={handleSubmit}
      className="space-y-5"
    >
      <div className="space-y-2">
        <Label htmlFor="username">用户名</Label>

        <Input
          id="username"
          name="username"
          autoComplete="username"
          value={username}
          onChange={(event) =>
            setUsername(event.target.value)
          }
          placeholder="请输入用户名"
          required
        />
      </div>

      <div className="space-y-2">
        <Label htmlFor="password">密码</Label>

        <Input
          id="password"
          name="password"
          type="password"
          autoComplete="current-password"
          value={password}
          onChange={(event) =>
            setPassword(event.target.value)
          }
          placeholder="请输入密码"
          required
        />
      </div>

      {error && (
        <p className="text-sm text-destructive" role="alert">
          {error}
        </p>
      )}

      <Button
        type="submit"
        className="w-full"
        disabled={loading}
      >
        {loading ? "登录中..." : "登录"}
      </Button>
    </form>
  );
}
```

这里使用 Better Auth 客户端的 `signIn.username()` 方法。

我们不再需要：

- 自己查询密码哈希。
- 自己调用 Argon2 验证。
- 自己生成 Session Token。
- 自己设置 HttpOnly Cookie。

这些工作交给 Better Auth。

**为什么这里不用前几篇的 Server Action + `useActionState`？**

前几篇的表单是「提交到自己的 Server Action，再返回状态」。登录不一样：Better Auth 的 `/api/auth/sign-in/username` 需要在响应里直接写 `Set-Cookie`。走客户端 SDK 时，浏览器原样接收这个响应，Cookie 自动落地，代码最短。

如果包一层 Server Action，就要在 Action 里转发 Cookie，多一层容易出错的手工处理。所以登录表单保留客户端调用，这是有意的差异，不是忘了统一。

对应地，登录页只做最小校验：

- 浏览器原生 `required` 保证非空。
- 用户名长度、密码强度交给 Better Auth（`minUsernameLength` / `maxUsernameLength`），避免前后端两套规则打架。
- 业务性错误（账号停用、限流）原样展示服务端消息；凭证错误统一成「用户名或密码错误」。

另外，`callbackURL` 和 `router.replace` 只需要用一个。这里用 `router.replace` + `router.refresh()`：后者让服务端布局重新执行 `requireCurrentUser()`，拿到刚建立的会话。两者同时写，等于把跳转做了两遍。

## 九、建立服务端当前用户校验

登录成功不代表后续所有请求都安全。

真正重要的是：用户每次访问受保护的业务页面、执行服务端操作时，都需要在服务端验证身份。

创建 `lib/auth-session.ts`。

放在 `lib/` 而不是顶层 `server/`，是为了和现有的 `lib/`、`features/` 保持一致。项目已经有 `lib/auth.ts`、`lib/db.ts`，再加一个 `server/` 目录只会让「服务端代码放哪」出现两套答案。

### 9.1 获取当前登录用户

`lib/auth-session.ts`：

```typescript
import "server-only";

import { cache } from "react";
import { headers } from "next/headers";
import { redirect } from "next/navigation";

import { auth } from "@/lib/auth";
import { db } from "@/lib/db";

/**
 * 读取当前登录用户。
 *
 * 1. 没有会话（未登录、Cookie 过期、会话已撤销）返回 null。
 * 2. 会话有效但用户在库中不存在，返回 null。
 * 3. 会话有效但用户已停用，返回 null。
 *
 * 用 cache() 去重：同一次请求内，页面、布局、Service、Server Action
 * 多次调用只会真正读一次会话和一次用户。
 */
export const getCurrentUser = cache(async () => {
  const session = await auth.api.getSession({
    headers: await headers(),
  });

  if (!session) {
    return null;
  }

  const user = await db.user.findUnique({
    where: {
      id: session.user.id,
    },
    select: {
      id: true,
      name: true,
      email: true,
      username: true,
      phone: true,
      status: true,
    },
  });

  if (!user || user.status !== "ACTIVE") {
    return null;
  }

  return user;
});

export async function requireCurrentUser() {
  const user = await getCurrentUser();

  if (!user) {
    redirect("/login");
  }

  return user;
}
```

这段代码非常重要。

它不仅通过 Better Auth 获取 Session，还重新从数据库读取用户状态。

为什么要这样做？

假设一个用户上午登录了系统，下午管理员将其账号停用。

如果我们只依赖登录时生成的 Session，那么这个用户可能仍然持有有效会话。

现在每次调用 `requireCurrentUser()` 都会检查数据库中的账号状态，因此停用用户无法继续通过这个统一入口访问受保护的服务端功能。

**为什么套一层 `cache()`？**

因为这一层会被调用很多次：布局一次、页面一次、页面里的 Service 再一次。不加 `cache()`，一次页面渲染会查三遍 Session 表和 User 表。

`cache()` 的作用域是「单次请求」，不会跨请求共享，所以不会把一个用户的会话错误地给另一个用户。这也是它适合缓存会话读取、而不是适合缓存业务列表的原因。

注意：这并不意味着所有业务代码自动安全。后续每个 Server Action、Service 的敏感入口仍然需要执行相应的认证和授权校验。下一节会具体落到代码上。

### 9.2 保护后台布局

目前后台布局是：

```text
app/(dashboard)/layout.tsx
```

它使用 SidebarProvider、AdminSidebar 和 AdminTopbar 组成后台框架。

现在我们要让后台在渲染前先确认身份。

修改 `app/(dashboard)/layout.tsx`：

```tsx
import type { ReactNode } from "react";
import { Suspense } from "react";

import { AdminSidebar } from "@/components/layout/admin-sidebar";
import { AdminTopbar } from "@/components/layout/admin-topbar";
import { SidebarInset, SidebarProvider } from "@/components/ui/sidebar";
import { requireCurrentUser } from "@/lib/auth-session";

// 鉴权需要在渲染前完成，允许布局阻塞首个响应
export const instant = false;

type DashboardLayoutProps = {
  children: ReactNode;
};

export default async function DashboardLayout({
  children,
}: DashboardLayoutProps) {
  const user = await requireCurrentUser();

  return (
    <SidebarProvider>
      <Suspense fallback={null}>
        <AdminSidebar />
      </Suspense>

      <SidebarInset className="min-w-0">
        <AdminTopbar user={user} />

        <div className="min-w-0 flex-1 p-6">{children}</div>
      </SidebarInset>
    </SidebarProvider>
  );
}
```

这里要澄清一个常见误解：**布局里的鉴权不能当成唯一的安全边界。**

它能拦住第一次加载：未登录直接访问 `/admin/users`，服务端渲染布局时 `requireCurrentUser()` 就重定向了。

但它拦不住客户端导航。Next.js 的布局在 App Router 里不会随子路由切换重新渲染——这是有意的优化。所以管理员在后台点菜单时，只有目标页面重新渲染，布局里的 `await` 不会再执行。

后果很具体：会话过期或账号被停用之后，管理员在后台继续点菜单，`getUserList` 照样返回数据，因为没人再检查一次。

正确做法是分层：

| 层次 | 职责 |
|---|---|
| `proxy.ts` | 只看 Cookie 是否存在，做最便宜的粗筛，不做数据库查询 |
| 布局 | 首屏拦截，同时拿到用户信息给 Topbar 用 |
| 页面 | 读取数据前 `await requireCurrentUser()` |
| Service / Server Action | 真正的安全边界，每次调用都校验 |

**关于 `export const instant = false`。**

三点说明：

1. 它只在启用 `cacheComponents` 时有效，并且只能写在服务端组件或路由文件里，客户端组件上无效。
2. 这个 API 在 Next.js 16.2 叫 `unstable_instant`，16.3 起才稳定为 `instant`。本文使用 Next.js 16.4.5。
3. `instant = false` 的语义是「这个路由/布局允许阻塞」。布局顶层直接 `await` 会话属于阻塞式动态渲染，Cache Components 模式默认不允许，构建时会报错；`instant = false` 是显式声明「这里就该先等鉴权」。

它适合的场景正是现在这种：`Suspense` 之前没有有意义的界面，必须等身份确认才有内容可渲染。如果一个页面有明确的骨架屏、鉴权只是其中一小部分，就不该整页阻塞。

**未登录访问时到底返回什么？**

这一点必须用实际响应说明，不能想当然。

既然布局是阻塞式渲染，`redirect()` 在返回任何 HTML 之前就抛出了，浏览器拿到的是普通的 HTTP 重定向，不存在「先收到静态外壳、再在流式响应里收到跳转指令」这个过程。

用 curl 验证：

```bash
curl.exe -i http://localhost:3000/admin/users
```

实际响应：

```text
HTTP/1.1 307 Temporary Redirect
location: /login
```

这是更简单、也更容易验证的模型：没有外壳，没有流式跳转，只有一条重定向指令。

### 9.3 把校验下沉到页面、Service 和 Server Action

**页面层。** 每个读取业务数据的后台页面，在调用 Service 之前先确认身份。以用户列表为例：

```tsx
// app/(dashboard)/admin/users/page.tsx
import { requireCurrentUser } from "@/lib/auth-session";

export const instant = false;

export default async function UsersPage() {
  await requireCurrentUser();

  // ... 之后才渲染 UserList
}
```

新增、编辑、角色列表、角色成员页同理。页面级的校验是必要的，因为客户端导航时只有页面会重新渲染，布局不会。

**Service 层。** 页面校验可以绕过（例如将来加了别的调用方），所以数据入口也要自己守一遍：

```typescript
// features/users/service.ts
import { requireCurrentUser } from "@/lib/auth-session";

export async function getUserList(params: UserListParams) {
  await requireCurrentUser();

  // ... 原有查询
}

export async function getUserById(id: string) {
  await requireCurrentUser();

  return db.user.findUnique({ /* ... */ });
}
```

写在 Service 里的好处是：无论谁调用、从页面还是从脚本里调用，都走同一条检查。

因为有 `cache()`，页面调用一次、Service 再调用一次，实际只查一次库，不会产生额外开销。

**Server Action 层。** 所有写操作前面已经统一用 `requireUserAdmin()` 拦截。这一篇要把它从「开发期占位守卫」换成真正的会话校验，不再依赖 `NODE_ENV`：

```typescript
// lib/auth-guard.ts
import "server-only";

import { requireCurrentUser } from "@/lib/auth-session";

/**
 * 当前只校验是否已登录。
 * 角色权限（管理员/教务/教师）在后续篇章中接入。
 */
export async function requireUserAdmin() {
  await requireCurrentUser();
}
```

这样改造之后：

- 生产环境不再「一律拒绝」，登录后的管理员可以正常操作。
- 开发环境也不再「谁都能操作」，未登录请求同样会被挡住。
- 授权（谁能管用户、谁能管课程）留给下一篇，这里不假装已经解决。

### 9.4 用 `proxy.ts` 做粗筛

Next.js 16 把 `middleware.ts` 改名为 `proxy.ts`，并固定在 Node.js 运行时执行。

它的价值是：在进入页面渲染之前，用很低的开销把明显未登录的请求挡掉。它**不能**作为安全边界——只看 Cookie 是否存在，不验证签名，也不查库。

在项目根目录创建 `proxy.ts`：

```typescript
import { getSessionCookie } from "better-auth/cookies";
import { NextResponse, type NextRequest } from "next/server";

/**
 * 只在 Cookie 层面做粗筛，不查数据库。
 * 真正的安全边界在 lib/auth-session.ts 和服务端数据入口。
 */
export function proxy(request: NextRequest) {
  const sessionCookie = getSessionCookie(request);

  if (!sessionCookie) {
    return NextResponse.redirect(new URL("/login", request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ["/admin/:path*"],
};
```

`matcher` 只匹配后台路径。不要把 `/api/auth` 或 `/login` 也纳入匹配，否则登录请求本身会被重定向，形成死循环。

如果伪造一个 Cookie，`proxy.ts` 会放行——这是预期行为，因为随后的布局和 Service 会从数据库确认身份并拒绝。粗筛负责省钱，精细校验负责安全，两者不能互相替代。

### 9.5 显示真实用户信息

## 十、准备初始管理员账号

现在登录系统需要一个真实账号。

由于我们关闭了公开注册，不能让任何人通过注册接口创建账号。

初始管理员应该通过受控的初始化脚本创建。

**不要直接改 `prisma/seed.ts`。** 那个脚本负责 25 条演示数据，职责是让列表、搜索、分页有内容可显示。把管理员塞进去会导致两个问题：跑演示数据就等于创建真实管理员；脚本也无法单独执行。

单独建 `prisma/seed-admin.ts`：

```typescript
import "dotenv/config";

import { PrismaPg } from "@prisma/adapter-pg";
import * as argon2 from "argon2";

import { PrismaClient, UserStatus } from "../app/generated/prisma/client";
import { argon2Params } from "../lib/password-config";

const connectionString = process.env.DATABASE_URL;

if (!connectionString) {
  throw new Error("DATABASE_URL 环境变量未配置");
}

const db = new PrismaClient({
  adapter: new PrismaPg({ connectionString }),
});

function hashPassword(password: string) {
  return argon2.hash(password, {
    type: argon2.argon2id,
    ...argon2Params,
  });
}

function requireEnv(key: string) {
  const value = process.env[key];

  if (!value) {
    throw new Error(`缺少环境变量 ${key}`);
  }

  return value;
}

async function seedInitialAdmin() {
  const name = requireEnv("INIT_ADMIN_NAME");
  const email = requireEnv("INIT_ADMIN_EMAIL").toLowerCase();
  const username = requireEnv("INIT_ADMIN_USERNAME").toLowerCase();
  const password = requireEnv("INIT_ADMIN_PASSWORD");

  const existing = await db.user.findFirst({
    where: {
      OR: [{ username }, { email }],
    },
    select: { id: true },
  });

  if (existing) {
    console.log(`管理员 ${username} 已存在，跳过创建`);
    return;
  }

  const userId = crypto.randomUUID();
  const passwordHash = await hashPassword(password);

  await db.$transaction(async (tx) => {
    await tx.user.create({
      data: {
        id: userId,
        name,
        email,
        emailVerified: true,
        username,
        status: UserStatus.ACTIVE,

        accounts: {
          create: {
            id: crypto.randomUUID(),
            accountId: userId,
            providerId: "credential",
            password: passwordHash,
          },
        },
      },
    });

    const adminRole = await tx.role.findUnique({
      where: { code: "ADMIN" },
      select: { id: true },
    });

    if (adminRole) {
      await tx.userRole.create({
        data: {
          userId,
          roleId: adminRole.id,
        },
      });
    }
  });

  console.log(`已创建初始管理员 ${username}`);
}

async function main() {
  await seedInitialAdmin();
}

main()
  .catch((error) => {
    console.error(error);
    process.exitCode = 1;
  })
  .finally(async () => {
    await db.$disconnect();
  });
```

关键点：

1. **`argon2Params` 从 `../lib/password-config` 相对导入。** 这个文件不带 `server-only`，`tsx` 能正常加载。如果从 `@/lib/password` 导入，脚本会立刻报错——项目里 `@/` 别名只在 Next.js 的构建体系里生效。
2. **相对路径 + 显式 `.env` 加载。** 脚本不在 Next.js 运行时里，`dotenv/config` 负责读环境变量。
3. **幂等。** 已存在同名或同邮箱的账号就跳过，重复执行不会报唯一约束错误。
4. **事务。** 用户、Account、角色关联要么全成功，要么全回滚，不会留下没有密码的账号。
5. **嵌套创建 credential Account。** `accountId` 必须等于 `userId`，这是 Better Auth 关联凭证的方式。

`package.json` 中增加命令，和演示数据分开：

```json
{
  "scripts": {
    "db:seed": "tsx prisma/seed.ts",
    "db:seed:admin": "tsx prisma/seed-admin.ts"
  }
}
```

在 `.env` 中配置：

```env
INIT_ADMIN_NAME="系统管理员"
INIT_ADMIN_EMAIL="admin@school.internal"
INIT_ADMIN_USERNAME="admin"
INIT_ADMIN_PASSWORD="替换为强密码"
```

然后执行：

```bash
pnpm db:seed:admin
```

不要把真实管理员密码写进 Git 仓库。初始化完成后，可以从本地 `.env` 里移除密码，或改为由部署平台注入。

## 十一、退出登录

登录之后，还需要实现退出功能。

Topbar 是服务端组件，不能直接绑定点击事件，所以退出按钮要单独做成客户端组件。

创建 `components/layout/sign-out-button.tsx`：

```tsx
"use client";

import { useState } from "react";
import { useRouter } from "next/navigation";

import { authClient } from "@/lib/auth-client";
import { Button } from "@/components/ui/button";

export function SignOutButton() {
  const router = useRouter();
  const [pending, setPending] = useState(false);

  async function handleSignOut() {
    setPending(true);

    try {
      await authClient.signOut();

      router.replace("/login");
      router.refresh();
    } finally {
      setPending(false);
    }
  }

  return (
    <Button
      type="button"
      variant="outline"
      size="sm"
      disabled={pending}
      onClick={handleSignOut}
    >
      {pending ? "退出中..." : "退出登录"}
    </Button>
  );
}
```

然后在 `AdminTopbar` 右侧渲染 `<SignOutButton />`。

Better Auth 会负责销毁当前 Session 和对应的登录状态，比自己删 Cookie 或手工操作 Session 表更可靠。

还有一个配套动作容易被忽略：**停用账号、重置密码时应该撤销该用户已有会话。**

账号停用如果只改 `status`，旧 Session 仍然存在。`requireCurrentUser()` 每次都会查状态，所以停用后访问会被拦住；但 Session 记录本身还在，直到过期。为了让状态变更立即生效，`setUserStatus` 在停用时要顺手清理会话：

```typescript
await db.user.update({
  where: { id },
  data: { status },
  select: { id: true },
});

if (status === "DISABLED") {
  await db.session.deleteMany({ where: { userId: id } });
}
```

重置密码同理。密码被重置通常意味着账号可能已经泄露，旧会话应该一并作废。这件事和「强制下线所有设备」是同一个能力，后续可以抽成一个 `revokeUserSessions(userId)` 复用。

### 12.1 登录验证

启动项目：

- 登录成功，进入 `/admin/users`。

### 12.2 Session 验证

登录后查看 PostgreSQL。

应该能看到：

- User 表中存在用户。
- Account 表中存在 credential 账号。
- Session 表中存在当前登录会话。
- Account.password 中保存的是 Argon2id 哈希，而不是明文密码。

### 12.3 未登录访问验证

退出登录后，直接在浏览器地址栏输入：

```text
http://localhost:3000/admin/users
```

预期结果：自动跳转到登录页面。

注意这里的跳转由服务端触发。由于布局是阻塞式渲染，`redirect()` 在输出任何 HTML 之前就执行了，浏览器拿到的是普通的 HTTP 重定向，不存在「静态外壳 + 流式跳转指令」。

用 curl 可以直接看到真实响应：

```bash

```

```text
HTTP/1.1 307 Temporary Redirect
location: /login
```

### 12.4 停用账号验证

使用管理员账号登录。

将测试账号状态修改为 DISABLED。

验证：

- 停用账号无法重新登录。
- 已经登录的停用账号再次访问后台时，会被服务端校验拦截。

停用账号时会同时执行 `db.session.deleteMany({ where: { userId } })`，旧会话立即失效，不需要等待 Cookie 过期。

验证时注意区分两种入口：

- 直接刷新页面：布局执行 `requireCurrentUser()`，返回 307 到 `/login`。
- 在后台点菜单（客户端导航）：布局**不会**重新执行，但目标页面和它调用的 Service 都会执行 `requireCurrentUser()`，同样被拦下。

如果只靠布局，第二种情况会漏。这就是 9.3 把校验下沉到页面和 Service 的原因。

同时验证错误密码的响应：

```text
POST /api/auth/sign-in/username（错误密码）
HTTP 401
{"code":"INVALID_USERNAME_OR_PASSWORD","message":"用户名或密码错误"}
```

对比正确密码时的提示：

```text
POST /api/auth/sign-in/username（正确密码）
HTTP 401
{"code":"UNAUTHORIZED","message":"账号已停用，请联系管理员"}
```

两条提示都出现在密码校验之后，猜用户名的人拿不到「账号存在且已停用」的信息。

## 十三、本篇总结

至此，我们完成了英语教学管理平台的第一次认证架构升级。

本篇主要做了以下工作：

1. 引入 Better Auth（1.7.18）。
2. 重构 User 数据模型，并给出既有用户管理代码的完整改造清单。
3. 增加 Account、Session、Verification。
4. 使用 Username 插件实现用户名登录。
5. 通过自定义密码配置继续使用 Argon2id。
6. 创建 Next.js 认证接口。
7. 实现登录页面。
8. 建立服务端当前用户校验，并用 `cache()` 去重。
9. 把校验下沉到布局、页面、Service 和 Server Action。
10. 用 `proxy.ts` 做 Cookie 粗筛。
11. 显示真实登录用户信息，并提供独立的退出登录组件。
12. 把初始管理员脚本和演示数据脚本拆开。

但这还不是完整的权限系统。

目前我们解决的是：

**用户是谁？用户是否已经登录？账号是否处于可用状态？**

`requireUserAdmin()` 现在只校验「已登录」，名字里的 Admin 暂时是历史遗留。它真正变成权限判断，要等 RBAC 落地。

接下来还需要解决：

- 谁可以管理用户？
- 谁可以管理教师和学员？
- 教师只能看到哪些学生？
- 家长只能查看哪些孩子？
- 代理只能管理哪些客户？
- 不同校区之间的数据如何隔离？

这些都属于后续 RBAC 和数据权限的工作。

下一篇，我们将继续完善认证体系与用户管理之间的衔接，尤其是管理员新增用户、重置密码、停用账号和撤销 Session 的完整流程。

真正的企业级系统，不能只是登录成功，而是要让身份、账号生命周期和业务权限形成完整闭环。
