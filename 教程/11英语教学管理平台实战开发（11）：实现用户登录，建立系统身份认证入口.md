# 英语教学管理平台实战开发（11）：接入 Better Auth，重构用户模型并实现用户名密码登录

前面几篇，我们围绕用户管理完成了用户列表、新增、编辑、密码重置、启用停用、删除以及后台整体布局。

但是，目前系统还存在一个非常重要的问题：**我们虽然已经有了用户表，却还没有真正的身份认证体系。**

之前的用户管理主要围绕业务 CRUD 展开：

- 用户名和密码保存在 User 表中。
- 使用 Argon2id 对密码进行哈希。
- 用户状态通过 ACTIVE、DISABLED 控制。
- 后台操作通过开发环境守卫临时限制。

这些实现能够帮助我们理解用户管理的基本原理，但如果准备把系统作为真实项目交付，就不能继续自己维护 Cookie、Session、密码校验和登录状态。

本篇开始引入 Better Auth，重新设计用户认证模型。

## 一、先理解：认证系统到底负责什么？

在一个真正的业务系统中，用户管理和身份认证并不是一回事。

用户管理解决的是：

- 创建用户。
- 修改用户资料。
- 设置用户状态。
- 重置密码。
- 管理用户账号。

身份认证解决的是：

- 用户如何证明自己的身份？
- 密码如何验证？
- 登录成功后如何保持登录状态？
- Session 如何创建、验证和失效？
- 用户退出后如何销毁登录状态？

除此之外，还有第三个问题：用户登录后能够做什么？

这属于授权体系，后续我们会通过 RBAC 实现。

因此，整个系统应该分成三个层次：

```text
┌────────────────────────────────────┐
│             业务授权 RBAC           │
│       用户角色、权限、数据范围       │
├────────────────────────────────────┤
│             身份认证                │
│    登录、密码校验、Session、退出     │
├────────────────────────────────────┤
│             用户管理                │
│       用户资料、状态、账号维护       │
└────────────────────────────────────┘
```

本篇重点解决中间这一层，同时调整底层用户模型，为后续 RBAC 做好准备。

## 二、为什么选择 Better Auth？

Better Auth 是一个面向 TypeScript 应用的认证框架，支持多种数据库适配器，也提供用户名、密码、Session 等认证能力。

与自己编写登录系统相比，它可以承担大量通用认证工作：

- 用户名密码认证。
- 密码哈希和验证。
- Session 创建与验证。
- Cookie 管理。
- 登录和退出接口。
- 多设备会话管理。
- 后续扩展其他认证方式。

我们当前使用 Next.js App Router、Prisma 7 和 PostgreSQL，Better Auth 提供了对应的 Prisma Adapter，可以直接融入现有项目。

本项目采用以下组合：

| 技术 | 用途 |
|---|---|
| Better Auth | 身份认证 |
| Username Plugin | 用户名登录 |
| Prisma Adapter | 持久化认证数据 |
| PostgreSQL | 保存用户、账号和 Session |
| Argon2id | 密码哈希 |
| Next.js Route Handler | 承载认证接口 |
| RBAC | 后续实现业务授权 |

这里特别强调：Better Auth 不负责替我们设计教培机构的业务权限。它解决的是身份认证，不是整个业务系统的权限模型。

## 三、重构 User 数据模型

这是本篇最重要的调整。

之前的 User 模型：

```prisma
enum UserStatus {
  ACTIVE
  DISABLED
}

model User {
  id           String     @id @default(uuid())
  username     String     @unique
  passwordHash String
  phone        String?
  status       UserStatus @default(ACTIVE)
  createdAt    DateTime   @default(now())
  updatedAt    DateTime   @updatedAt
}
```

这个模型有一个明显的问题：它把用户身份、登录凭证和业务资料混在了一张表中。

Better Auth 采用另一种设计：

- User：用户身份资料。
- Account：认证账号和凭证。
- Session：登录会话。
- Verification：验证码及验证令牌。

密码不再放在 User 表，而是放在 Account 表中。

这也是为什么我们要调整现有数据模型。

### 3.1 新的用户模型

修改 `prisma/schema.prisma`。

首先保留用户状态枚举：

```prisma
enum UserStatus {
  ACTIVE
  DISABLED
}
```

然后重新设计 User：

```prisma
model User {
  id              String     @id
  name            String
  email           String     @unique
  emailVerified   Boolean    @default(false)
  image           String?

  username        String?    @unique
  phone           String?
  status          UserStatus @default(ACTIVE)

  createdAt       DateTime   @default(now())
  updatedAt       DateTime   @updatedAt

  sessions        Session[]
  accounts        Account[]
}
```

这里有几个重要变化：

**第一，增加 name。**

name 是用户的展示名称，不再直接把 username 当作用户的姓名。

例如：

- username：teacher_001
- name：张老师

**第二，增加 email。**

Better Auth 的核心 User 模型要求 email。即使本项目使用用户名登录，也需要为账号保存真实的邮箱信息。

不要给没有邮箱的用户随意生成虚构邮箱。真实项目中，如果业务群体普遍没有邮箱，需要在正式推广前重新评估手机号认证方案。

**第三，username 仍然保留。**

它是登录标识，由 Username 插件管理。

**第四，phone 和 status 继续保留。**

手机号属于业务联系资料，status 用于控制账号是否允许使用。

### 3.2 增加 Session 模型

```prisma
model Session {
  id        String   @id
  expiresAt DateTime
  token     String   @unique

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  ipAddress String?
  userAgent String?

  userId    String
  user      User     @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )
}
```

Session 表用于保存用户的登录会话。

每次登录成功，Better Auth 会创建对应的 Session。

用户再次访问系统时，浏览器携带 Cookie，Better Auth 根据 Session Token 验证身份。

用户退出时，会话可以被销毁。

### 3.3 增加 Account 模型

```prisma
model Account {
  id                    String    @id
  accountId             String
  providerId            String

  userId                String
  user                  User      @relation(
    fields: [userId],
    references: [id],
    onDelete: Cascade
  )

  accessToken           String?
  refreshToken          String?
  idToken               String?

  accessTokenExpiresAt  DateTime?
  refreshTokenExpiresAt DateTime?

  scope                 String?
  password              String?

  createdAt             DateTime  @default(now())
  updatedAt             DateTime  @updatedAt
}
```

Account 与 User 是多对一关系。

一个用户未来可以关联多个认证账号，例如：

- 用户名密码。
- 微信登录。
- Google 登录。
- 其他 OAuth 账号。

当前我们只使用用户名密码，因此 Account 中的 `providerId` 对应 `credential`。

密码哈希保存在 Account.password。

### 3.4 增加 Verification 模型

```prisma
model Verification {
  id         String   @id
  identifier String
  value      String
  expiresAt  DateTime

  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt
}
```

Verification 用于保存认证过程中的验证信息。

例如后续接入邮箱验证、密码找回、验证码等功能时，都可能使用它。

至此，认证模型已经基本建立。

注意：这里展示的是本项目需要的核心模型。实际使用时，应以安装版本的 Better Auth CLI 生成结果为准，检查字段、索引和插件模型，不要直接覆盖已有的整个 Prisma Schema。

## 五、配置 Better Auth

在项目中创建：

```text
lib/
├── auth.ts
├── auth-client.ts
└── password.ts
```

### 5.1 复用 Argon2id

当前项目已经有 `lib/password.ts`，其中实现了 Argon2id 哈希和验证。

原代码可以继续保留：

```typescript
import "server-only";
import * as argon2 from "argon2";

export async function hashPassword(password: string) {
  return argon2.hash(password, {
    type: argon2.argon2id,
    memoryCost: 19456,
    timeCost: 2,
    parallelism: 1,
  });
}

export async function verifyPassword(
  password: string,
  passwordHash: string
) {
  return argon2.verify(passwordHash, password);
}
```

Better Auth 默认使用 scrypt。

我们通过自定义密码配置继续使用 Argon2id，避免项目中出现两套密码哈希规则。

### 5.2 创建认证服务

创建 `lib/auth.ts`：

```typescript
import { betterAuth } from "better-auth";
import { prismaAdapter } from "better-auth/adapters/prisma";
import { username } from "better-auth/plugins";
import { createAuthMiddleware, APIError } from "better-auth/api";

import { db } from "@/lib/db";
import {
  hashPassword,
  verifyPassword,
} from "@/lib/password";

export const auth = betterAuth({
  database: prismaAdapter(db, {
    provider: "postgresql",
  }),

  baseURL: process.env.BETTER_AUTH_URL,
  secret: process.env.BETTER_AUTH_SECRET,

  emailAndPassword: {
    enabled: true,

    // 本项目不开放用户自行注册
    disableSignUp: true,

    password: {
      hash: hashPassword,

      verify: ({ password, hash }) => {
        return verifyPassword(password, hash);
      },
    },
  },

  plugins: [
    username({
      minUsernameLength: 3,
      maxUsernameLength: 30,

      // 不需要额外保存 displayUsername
      displayUsername: false,

      // 用户名作为登录标识，不允许随意修改
      immutableUsername: true,
    }),
  ],

  user: {
    additionalFields: {
      phone: {
        type: "string",
        required: false,
        input: false,
      },

      status: {
        type: ["ACTIVE", "DISABLED"],
        required: true,
        defaultValue: "ACTIVE",
        input: false,
      },
    },
  },

  // 在登录入口检查账号状态
  hooks: {
    before: createAuthMiddleware(async (ctx) => {
      if (ctx.path !== "/sign-in/username") {
        return;
      }

      const usernameValue = ctx.body.username;

      if (typeof usernameValue !== "string") {
        return;
      }

      const user = await db.user.findUnique({
        where: {
          username: usernameValue.toLowerCase(),
        },
        select: {
          status: true,
        },
      });

      if (user?.status === "DISABLED") {
        throw new APIError("UNAUTHORIZED", {
          message: "账号已停用，请联系管理员",
        });
      }
    }),
  },
});
```

这里有几个值得理解的地方。

**第一，使用 Prisma Adapter。**

Better Auth 不需要自己管理数据库连接，直接复用项目中的 `db`。

**第二，使用 Username 插件。**

它扩展了 Email & Password 认证，让用户可以使用用户名登录。

**第三，关闭公开注册。**

教培平台的账号应该由机构管理员创建，而不是任何人都能自行注册。

**第四，状态检查。**

用户登录时，先检查账号状态。停用账号不能正常创建新的登录会话。

注意：这只是登录入口的状态检查。对于已经登录的用户，后面还要在服务端读取当前用户时再次检查状态，不能只依赖登录时的一次校验。

```bash

  --name add_better_auth
```

然后重新生成 Prisma Client：

```bash

  --config prisma7.config.ts
```

这里需要特别注意现有数据。

如果只是开发环境，并且原来的用户都是测试数据，可以在确认没有需要保留的数据后重新初始化数据库，再使用新的账号初始化流程。

如果是真实项目，不能直接删除旧的 `passwordHash`。

原来的 Argon2id 哈希可以迁移到新 Account 表的 `password` 字段。迁移时需要先创建 Account 记录，再迁移密码哈希，最后才删除旧字段。

例如，迁移 SQL 的核心逻辑是：

```sql
INSERT INTO "Account" (
  "id",
  "accountId",
  "providerId",
  "userId",
  "password",
  "createdAt",
  "updatedAt"
)
SELECT
  gen_random_uuid()::text,
  "id",
  'credential',
  "id",
  "passwordHash",
  NOW(),
  NOW()
FROM "User"
WHERE "passwordHash" IS NOT NULL;
```

实际执行前，需要按照 Prisma 生成的迁移文件核对表名、字段名、ID 类型和约束，并将数据迁移安排在删除旧字段之前。

迁移完成后，原有 Argon2id 密码可以继续由我们配置的 `verify` 函数验证，不需要强迫所有用户重新设置密码。

### 8.1 实现登录表单

`features/auth/components/login-form.tsx`：

```tsx
"use client";

import { useState } from "react";
import { useRouter } from "next/navigation";

import { authClient } from "@/lib/auth-client";

import { Button } from "@/components/ui/button";
import { Input } from "@/components/ui/input";
import { Label } from "@/components/ui/label";

export function LoginForm() {
  const router = useRouter();

  const [username, setUsername] = useState("");
  const [password, setPassword] = useState("");
  const [error, setError] = useState("");
  const [loading, setLoading] = useState(false);

  async function handleSubmit(
    event: React.FormEvent<HTMLFormElement>
  ) {
    event.preventDefault();

    setError("");
    setLoading(true);

    try {
      const result = await authClient.signIn.username({
        username,
        password,
        callbackURL: "/admin/users",
      });

      if (result.error) {
        setError("用户名或密码错误");
        return;
      }

      router.replace("/admin/users");
      router.refresh();
    } catch {
      setError("登录失败，请稍后重试");
    } finally {
      setLoading(false);
    }
  }

  return (
    <form
      onSubmit={handleSubmit}
      className="space-y-5"
    >
      <div className="space-y-2">
        <Label htmlFor="username">用户名</Label>

        <Input
          id="username"
          name="username"
          autoComplete="username"
          value={username}
          onChange={(event) =>
            setUsername(event.target.value)
          }
          placeholder="请输入用户名"
          required
        />
      </div>

      <div className="space-y-2">
        <Label htmlFor="password">密码</Label>

        <Input
          id="password"
          name="password"
          type="password"
          autoComplete="current-password"
          value={password}
          onChange={(event) =>
            setPassword(event.target.value)
          }
          placeholder="请输入密码"
          required
        />
      </div>

      {error && (
        <p className="text-sm text-destructive" role="alert">
          {error}
        </p>
      )}

      <Button
        type="submit"
        className="w-full"
        disabled={loading}
      >
        {loading ? "登录中..." : "登录"}
      </Button>
    </form>
  );
}
```

这里使用 Better Auth 客户端的 `signIn.username()` 方法。

我们不再需要：

- 自己查询密码哈希。
- 自己调用 Argon2 验证。
- 自己生成 Session Token。
- 自己设置 HttpOnly Cookie。

这些工作交给 Better Auth。

## 九、建立服务端当前用户校验

登录成功不代表后续所有请求都安全。

真正重要的是：用户每次访问受保护的业务页面、执行服务端操作时，都需要在服务端验证身份。

创建：

```text
server/
└── auth/
    └── session.ts
```

### 9.1 获取当前登录用户

`server/auth/session.ts`：

```typescript
import "server-only";

import { headers } from "next/headers";
import { redirect } from "next/navigation";

import { auth } from "@/lib/auth";
import { db } from "@/lib/db";

export async function getCurrentUser() {
  const session = await auth.api.getSession({
    headers: await headers(),
  });

  if (!session) {
    return null;
  }

  const user = await db.user.findUnique({
    where: {
      id: session.user.id,
    },
    select: {
      id: true,
      name: true,
      email: true,
      username: true,
      phone: true,
      status: true,
    },
  });

  if (!user || user.status !== "ACTIVE") {
    return null;
  }

  return user;
}

export async function requireCurrentUser() {
  const user = await getCurrentUser();

  if (!user) {
    redirect("/login");
  }

  return user;
}
```

这段代码非常重要。

它不仅通过 Better Auth 获取 Session，还重新从数据库读取用户状态。

为什么要这样做？

假设一个用户上午登录了系统，下午管理员将其账号停用。

如果我们只依赖登录时生成的 Session，那么这个用户可能仍然持有有效会话。

现在每次调用 `requireCurrentUser()` 都会检查数据库中的账号状态，因此停用用户无法继续通过这个统一入口访问受保护的服务端功能。

注意：这并不意味着所有业务代码自动安全。后续每个 Server Action、Service 的敏感入口仍然需要执行相应的认证和授权校验。

### 9.2 保护后台布局

目前后台布局是：

```text
app/(dashboard)/layout.tsx
```

它使用 SidebarProvider、AdminSidebar 和 AdminTopbar 组成后台框架。

现在我们要让鉴权发生在渲染任何后台内容之前。

修改 `app/(dashboard)/layout.tsx`：

```tsx
import type { ReactNode } from "react";
import { Suspense } from "react";

import { AdminSidebar } from "@/components/layout/admin-sidebar";
import { AdminTopbar } from "@/components/layout/admin-topbar";
import { SidebarInset, SidebarProvider } from "@/components/ui/sidebar";
import { requireCurrentUser } from "@/server/auth/session";

// 鉴权需要在渲染前完成，允许布局阻塞首个响应
export const instant = false;

type DashboardLayoutProps = {
  children: ReactNode;
};

export default async function DashboardLayout({
  children,
}: DashboardLayoutProps) {
  const user = await requireCurrentUser();

  return (
    <SidebarProvider>
      <Suspense fallback={null}>
        <AdminSidebar />
      </Suspense>

      <SidebarInset className="min-w-0">
        <AdminTopbar user={user} />

        <div className="min-w-0 flex-1 p-6">{children}</div>
      </SidebarInset>
    </SidebarProvider>
  );
}
```

这里有两个关键点，都不能省。

第一，鉴权必须发生在渲染之前。一个容易踩的坑是把守卫包在 Suspense 里：

```tsx
<Suspense fallback={null}>
  <DashboardAuthGuard>{children}</DashboardAuthGuard>
</Suspense>
```

这种写法看起来很合理，但在 Next.js 16 的流式渲染下，页面组件会和守卫并发渲染。未登录用户访问 `/admin/users` 时，页面里的用户列表数据可能已经随流式响应输出，守卫的跳转指令才到达——数据已经泄露了。所以在布局顶层先 `await requireCurrentUser()`，让鉴权先于一切内容，才是安全的顺序。

第二，`export const instant = false`。布局顶层直接 `await` 会话属于阻塞式动态渲染，Next.js 16 的 Cache Components 模式默认不允许路由出现这种“阻塞”，构建时会直接报错。`instant = false` 明确告诉框架：这个布局允许阻塞导航，先完成身份校验再返回内容。这是安全优先的取舍——后台首屏稍慢一点，换来数据绝不外泄。

另外，作为纵深防御，三个后台页面（用户列表、新增、编辑）在读取数据前也都执行了一次 `await requireCurrentUser()`，并同样声明了 `instant = false`。布局守卫负责整体拦截，页面级校验保证每一页自身也安全。

未登录用户访问后台时，`requireCurrentUser()` 会跳转到登录页。浏览器会先收到一个静态外壳，随后在流式响应中收到跳转指令，最终停在登录页——整个过程不包含任何业务数据。

## 十、准备初始管理员账号

现在登录系统需要一个真实账号。

由于我们关闭了公开注册，不能让任何人通过注册接口创建账号。

初始管理员应该通过受控的初始化脚本创建。

创建一个只用于初始化的脚本，直接使用 Prisma 创建 User 和 Account，并使用项目的 Argon2id 哈希函数生成密码。

核心逻辑如下：

```typescript
const passwordHash = await hashPassword(
  process.env.INIT_ADMIN_PASSWORD!
);

const userId = crypto.randomUUID();

await db.user.create({
  data: {
    id: userId,
    name: process.env.INIT_ADMIN_NAME!,
    email: process.env.INIT_ADMIN_EMAIL!,
    emailVerified: true,
    username: process.env.INIT_ADMIN_USERNAME!,
    status: "ACTIVE",

    accounts: {
      create: {
        id: crypto.randomUUID(),
        accountId: userId,
        providerId: "credential",
        password: passwordHash,
      },
    },
  },
});
```

这里的嵌套创建会同时创建 User 和对应的 credential Account。

正式编写初始化脚本时，需要增加：

- 必要环境变量校验。
- 用户名和邮箱重复检查。
- 数据库事务。
- 初始化完成后清理临时密码环境变量。
- 禁止在每次应用启动时重复创建管理员。

不要把真实管理员密码写进 Git 仓库，也不要将测试用的占位密码当作真实密码使用。

## 十一、退出登录

登录之后，还需要实现退出功能。

可以在 Topbar 中增加退出按钮，调用 Better Auth 客户端：

```typescript
await authClient.signOut();

router.replace("/login");
router.refresh();
```

Better Auth 会负责销毁当前 Session 和对应的登录状态。

这比自己删除 Cookie 或手工操作 Session 表更加可靠。

## 十二、验证整个登录流程

完成以上代码后，不要只看页面是否能够显示，而是要验证认证链路是否真正打通。

### 12.1 登录验证

启动项目：

```bash
pnpm dev
```

访问：

```text
http://localhost:3000/login
```

输入初始化管理员的用户名和密码。

预期结果：

- 用户名密码正确，可以登录。
- 用户名或密码错误，显示错误提示。
- 登录成功，进入 `/admin/users`。
- 后台 Topbar 显示真实用户名。

### 12.2 Session 验证

登录后查看 PostgreSQL。

应该能看到：

- User 表中存在用户。
- Account 表中存在 credential 账号。
- Session 表中存在当前登录会话。
- Account.password 中保存的是 Argon2id 哈希，而不是明文密码。

### 12.3 未登录访问验证

退出登录后，直接在浏览器地址栏输入：

```text
http://localhost:3000/admin/users
```

预期结果：自动跳转到登录页面。

注意这里的跳转由服务端触发：浏览器先收到一个静态外壳，随后在流式响应中收到跳转指令，最终停在登录页。可以用浏览器开发者工具的 Network 面板确认，整个响应里不会出现用户列表等业务数据。

### 12.4 停用账号验证

使用管理员账号登录。

将测试账号状态修改为 DISABLED。

验证：

- 停用账号无法重新登录。
- 已经登录的停用账号再次访问后台时，会被服务端校验拦截。

还需要注意：停用账号时，真实项目应同时撤销该用户现有的 Session。后续用户管理功能会进一步完善这一操作。

## 十三、本篇总结

至此，我们完成了英语教学管理平台的第一次认证架构升级。

本篇主要做了以下工作：

1. 引入 Better Auth。
2. 重构 User 数据模型。
3. 增加 Account、Session、Verification。
4. 使用 Username 插件实现用户名登录。
5. 通过自定义密码配置继续使用 Argon2id。
6. 创建 Next.js 认证接口。
7. 实现登录页面。
8. 建立服务端当前用户校验。
9. 保护后台布局。
10. 显示真实登录用户信息。

但这还不是完整的权限系统。

目前我们解决的是：

**用户是谁？用户是否已经登录？账号是否处于可用状态？**

接下来还需要解决：

- 谁可以管理用户？
- 谁可以管理教师和学员？
- 教师只能看到哪些学生？
- 家长只能查看哪些孩子？
- 代理只能管理哪些客户？
- 不同校区之间的数据如何隔离？

这些都属于后续 RBAC 和数据权限的工作。

下一篇，我们将继续完善认证体系与用户管理之间的衔接，尤其是管理员新增用户、重置密码、停用账号和撤销 Session 的完整流程。

真正的企业级系统，不能只是登录成功，而是要让身份、账号生命周期和业务权限形成完整闭环。
