# 第15篇：构建完整的权限体系：超级管理员、角色授权与数据范围控制

## 一、为什么需要重新设计权限体系？

前面几篇已经完成了用户管理、角色管理等基础功能。

目前系统中已经有以下角色：

| 角色编码 | 角色名称 | 职责 |
|---|---|---|
| BOSS | 企业负责人 | 企业经营与管理 |
| ACADEMIC | 教务管理 | 教务与教学管理 |
| ADMIN | 系统管理员 | 企业日常系统管理 |
| TEACHER | 教师 | 教学执行 |
| AGENT | 代理/合作方 | 代理业务与客户跟进 |
| PARENT | 家长 | 查看孩子的学习情况 |

这些角色基本覆盖了平台的业务参与者，但在权限架构上还缺少一个重要角色：**SUPER_ADMIN（超级管理员）**。

为什么需要它？

假设我们正在开发角色权限管理功能，需要测试以下操作：

- 创建角色。
- 修改角色权限。
- 给用户分配角色。
- 禁用用户。
- 查看系统审计记录。
- 调整权限配置。

如果这些操作全部交给 ADMIN，那么 ADMIN 既承担日常系统管理职责，又承担系统安全配置职责，权限边界就不够清晰。

而且，在后续开发中，我们需要不断验证不同角色的权限。如果没有一个统一的管理账号，每次配置测试账号都可能需要切换多个账号。

因此，本篇先明确一个新的角色体系。

### 1.1 重新划分角色层次

我们将角色分为三个层次。

**第一层：系统级角色**

| 角色 | 职责 |
|---|---|
| SUPER_ADMIN | 平台超级管理员，负责权限体系、安全配置和系统治理 |
| ADMIN | 企业系统管理员，负责被授权的日常系统管理 |

**第二层：业务管理与执行角色**

| 角色 | 职责 |
|---|---|
| BOSS | 企业经营管理 |
| ACADEMIC | 教务、教学管理 |
| TEACHER | 教学执行 |
| AGENT | 代理及合作伙伴业务 |

**第三层：外部服务角色**

| 角色 | 职责 |
|---|---|
| PARENT | 家长端用户 |

这里有一个非常重要的架构决定：

**除了 PARENT 家长端独立之外，其他角色全部使用同一套后台框架。**

也就是说：

- SUPER_ADMIN 使用统一后台。
- BOSS 使用统一后台。
- ACADEMIC 使用统一后台。
- ADMIN 使用统一后台。
- TEACHER 使用统一后台。
- AGENT 使用统一后台。
- PARENT 使用独立的家长端。

不同角色进入后台后，根据权限加载不同菜单、页面和操作，而不是为每个角色开发一套独立后台。

### 1.2 超级管理员不等于所有业务数据都能看

这里还需要明确一个容易混淆的概念。

SUPER_ADMIN 拥有系统级权限，不代表它自动拥有所有业务数据权限。

例如：

- 它可以配置 TEACHER 角色有哪些权限。
- 它可以创建和禁用用户。
- 它可以修改角色授权。
- 但它不应该因为是超级管理员，就自动获得查看所有学生教学记录、修改课时账本的权限。

系统管理权限和业务数据权限是两条独立的授权链路。

这可以避免一个问题：为了管理系统，不得不让超级管理员拥有所有业务操作权限。

开发阶段如果需要验证业务功能，应该通过专门的测试账号完成，而不是把所有业务权限都塞进超级管理员。

## 二、权限体系的整体设计

一个完整的权限判断，不能只看用户属于哪个角色。

至少需要考虑四个维度：

1. 用户是否有效。
2. 用户是否拥有有效角色。
3. 用户角色是否拥有对应权限。
4. 用户是否有权访问当前数据。

因此，我们采用以下授权模型：

```text
用户 User
   │
   ├── 用户角色 UserRole
   │       │
   │       └── 角色 Role
   │              │
   │              └── 角色权限 RolePermission
   │                       │
   │                       ├── permissionCode
   │                       └── scope
   │
   └── 当前身份 CurrentActor
            │
            ├── 系统权限判断
            ├── 业务权限判断
            ├── 数据范围合并
            └── 资源访问校验
```

其中，SUPER_ADMIN 有一条特殊规则：

```text
SUPER_ADMIN
     │
     └── SYSTEM 权限直接通过
```

但这条规则只适用于 SYSTEM 域权限，不适用于 BUSINESS 域权限。

### 2.1 权限编码规范

权限统一采用：

```text
资源.动作
```

例如：

| 权限编码 | 含义 |
|---|---|
| user.view | 查看用户 |
| user.create | 创建用户 |
| user.edit | 编辑用户 |
| user.delete | 删除用户 |
| user.resetPassword | 重置密码 |
| user.disable | 禁用用户 |
| role.view | 查看角色 |
| role.create | 创建角色 |
| role.edit | 编辑角色 |
| role.delete | 删除角色 |
| role.disable | 禁用角色 |
| role.assignUser | 管理角色成员 |
| role.assignPermissions | 分配角色权限 |
| permission.view | 查看权限目录 |
| dashboard.view | 查看经营仪表盘 |
| student.view | 查看学生 |
| student.edit | 编辑学生 |
| schedule.view | 查看课程安排 |
| schedule.create | 创建课程安排 |
| teachingRecord.create | 创建教学记录 |
| parentReport.view | 查看家长报告 |

注意：

- 使用 `user.resetPassword`，不要使用 `user.reset-password`。
- 复合资源使用驼峰命名，例如 `teachingRecord.create`。
- 不要使用 `parent.report.view` 这种三段式编码。
- 权限编码一旦投入使用，应尽量保持稳定。

### 2.2 SYSTEM 和 BUSINESS 两个权限域

权限分成两个域：

| 权限域 | 用途 | 授权方式 |
|---|---|---|
| SYSTEM | 系统管理、安全配置、角色授权 | SUPER_ADMIN 特殊授权规则，其他身份按明确规则 |
| BUSINESS | 业务操作和数据访问 | RolePermission + DataScope |

例如：

```ts
type PermissionDomain = "SYSTEM" | "BUSINESS";
```

这里需要特别强调：

**SUPER_ADMIN 只绕过 SYSTEM 权限的数据库授权检查，不绕过用户有效性检查，也不绕过 BUSINESS 权限检查。**

这意味着：

- 用户被禁用，超级管理员身份也不能继续使用。
- SUPER_ADMIN 角色被禁用，该角色不再产生超级管理员能力。
- 用户没有 `student.view`，不能仅凭 SUPER_ADMIN 身份查看学生。
- 用户没有 `schedule.create`，不能仅凭 SUPER_ADMIN 身份创建排课。

## 三、调整 Prisma 数据模型

本篇在原有 User、Role、UserRole 基础上，增加 RolePermission，并明确权限数据范围。

### 3.1 DataScope 数据范围枚举

数据范围先定义三个等级：

```prisma
enum DataScope {
  ALL
  OWN
  ASSIGNED
}
```

含义如下：

| 数据范围 | 含义 |
|---|---|
| ALL | 全部数据 |
| OWN | 自己拥有或创建的数据 |
| ASSIGNED | 分配给自己的数据 |

暂时不增加 DEPARTMENT。

原因是目前系统还没有完整的部门组织关系。如果提前加入部门数据范围，后续还需要定义部门归属、上下级部门继承、跨部门授权等规则。

数据范围应该基于真实的数据关系设计，而不是先把枚举定义得很丰富。

### 3.2 RolePermission 模型

```prisma
model RolePermission {
  id             String    @id @default(uuid())
  roleId         String
  permissionCode String
  scope          DataScope

  role           Role      @relation(fields: [roleId], references: [id], onDelete: Cascade)

  createdAt      DateTime  @default(now())
  updatedAt      DateTime  @updatedAt

  @@unique([roleId, permissionCode])
  @@index([permissionCode])
}
```

这里有两个重要细节。

第一，`scope` 不设置数据库默认值。

不要这样写：

```prisma
scope DataScope @default(ALL)
```

因为如果业务代码漏传了数据范围，数据库就会自动给出 ALL，可能导致权限意外扩大。

我们希望缺少数据范围时直接暴露错误，而不是默认放开。

第二，`permissionCode` 暂时使用 String。

权限目录由 TypeScript 维护，数据库保存授权结果。写入数据库之前必须经过权限目录校验，避免保存不存在的权限编码。

### 3.3 在 Role 中增加关联

现有 Role 模型增加：

```prisma
rolePermissions RolePermission[]
```

User、UserRole 继续使用当前项目已有结构。

本篇示例会使用以下关系名称：

```text
User.userRoles
UserRole.role
Role.rolePermissions
Role.isActive
User.isActive
```

如果当前 Prisma Schema 中字段名称不同，以实际项目为准统一调整，不要为了照搬示例而重复创建关系。

### 3.4 生成 Prisma Client

本项目使用 Prisma 7，生成命令需要带上项目的配置文件：

```bash
pnpm prisma generate --config prisma7.config.ts
```

创建迁移：

```bash
pnpm prisma migrate dev --name add_role_permission
```

注意：

- 不要修改现有 User、Role 的主键类型。
- 不要重新创建已有 UserRole 关系。
- 不要擅自修改现有认证字段。
- 迁移前先检查现有数据库结构。

## 四、建立统一权限目录

权限目录是整个授权体系的基础。

如果权限编码散落在页面、Server Action 和 Service 中，后续维护会非常困难。

因此，我们建立统一的权限定义文件：

```text
lib/
  auth/
    permissions.ts
    permission-service.ts
    permission-scope.ts
    authorization.ts
```

### 4.1 定义权限结构

`lib/auth/permissions.ts`

```ts
export type PermissionDefinitionBase = {
  resource: string;
  action: string;
  name: string;
  module: string;

  domain: "SYSTEM" | "BUSINESS";

  // 是否允许通过 RolePermission 授权
  grantable: boolean;

  // 是否支持数据范围
  scopeable: boolean;
};

export type PermissionDefinition = PermissionDefinitionBase & {
  createScopes?: {
    permission: PermissionCode;
    relation: string;
  }[];
};
```

注意，这里先定义基础权限结构，再从权限目录推导 PermissionCode。

### 4.4 增加创建依赖配置

创建业务记录时，通常需要引用其他业务资源。

例如：

- 创建排课，需要选择学生和课程。
- 创建教学记录，需要选择一条排课。
- 创建词汇申请，需要选择学生。
- 创建订单，需要选择学生。
- 创建跟进记录，需要选择线索。

这里不能简单地认为拥有 `student.view` 就可以在任何业务创建表单中使用学生。

因此，我们为权限定义增加 `createScopes`。

```ts
export type PermissionDefinition = PermissionDefinitionBase & {
  createScopes?: {
    permission: PermissionCode;
    relation: string;
  }[];
};
```

再构建完整权限定义：


## 五、明确超级管理员的特殊授权规则

现在我们有了完整权限目录，接下来明确 SUPER_ADMIN 的特殊规则。

### 5.1 定义保留角色

在代码中统一定义：

```ts
export const SYSTEM_ROLE_CODES = {
  SUPER_ADMIN: "SUPER_ADMIN",
  ADMIN: "ADMIN",
} as const;
```

系统保留角色不允许通过普通角色管理功能删除或修改角色编码。

特别是：

- 不允许将普通角色修改成 SUPER_ADMIN。
- 不允许创建第二个同编码的 SUPER_ADMIN 角色。
- 不允许通过普通角色权限分配界面给普通角色增加超级管理员能力。
- 不允许普通管理员把 SUPER_ADMIN 角色分配给其他用户。

SUPER_ADMIN 是平台级安全身份，不是普通业务角色。

### 5.2 SYSTEM 权限不写入 RolePermission

这里采用一个明确的设计：

**SYSTEM 域权限不通过 RolePermission 表持久化授权。**

对于 SYSTEM 权限：

- SUPER_ADMIN 通过系统级角色身份获得权限。
- ADMIN 不自动获得所有 SYSTEM 权限。
- 普通业务角色不能通过 RolePermission 获得 SYSTEM 权限。

对于 BUSINESS 权限：

- 必须通过 RolePermission 明确授权。
- 必须配置数据范围。
- 不因为拥有 SUPER_ADMIN 身份而自动放行。

因此，权限定义中的：

```ts
grantable: false
```

表示该权限不能通过普通角色授权界面写入 RolePermission。

本篇的 SYSTEM 权限全部设置为 `grantable: false`。

### 5.3 统一入口权限

我们仍然保留两个入口权限：

```text
portal.admin
portal.parent
```

它们属于 BUSINESS 域，必须明确授权。

其中：

- `portal.admin`：进入统一后台。
- `portal.parent`：进入家长端。

SUPER_ADMIN 也需要明确获得 `portal.admin`。

不要因为它是超级管理员，就跳过后台入口权限。

这样，入口控制和系统权限控制仍然是两个独立的机制。

## 六、实现当前登录用户上下文

权限判断必须基于真实登录身份，不能由客户端传入用户 ID 或角色编码。

我们先建立统一的 CurrentActor。

### 6.1 定义 CurrentActor

`lib/auth/authorization.ts`

```ts
import type { DataScope } from "@/app/generated/prisma/client";
import type { PermissionCode } from "./permissions";

export type CurrentActor = {
  userId: string;
  name: string;
  email: string;

  isActive: boolean;

  roleCodes: string[];
  activeRoleCodes: string[];

  grants: {
    permissionCode: string;
    scope: DataScope;
  }[];
};

export type PermissionDecision = {
  allowed: boolean;
  actor: CurrentActor | null;
  scopes: DataScope[];
  reason?: "UNAUTHENTICATED" | "FORBIDDEN";
};
```

这里的 DataScope 必须使用 Prisma 生成的枚举类型。

不要再手写一个：

```ts
type DataScope = "ALL" | "OWN" | "ASSIGNED";
```

否则数据库枚举和 TypeScript 类型可能逐渐出现不一致。

如果当前生成客户端的导出路径与示例不同，应以项目实际生成路径为准。

### 6.2 获取当前登录用户

项目已经使用 Better Auth，因此不需要再重新实现登录认证。

我们只需要从 Better Auth 获取当前会话，再查询数据库中的用户和角色状态。

`lib/auth/current-actor.ts`

```ts
import "server-only";

import { cache } from "react";
import { headers } from "next/headers";

import { auth } from "@/lib/auth";
import { db } from "@/lib/db";

export const getCurrentActor = cache(async () => {
  const session = await auth.api.getSession({
    headers: await headers(),
  });

  if (!session?.user?.id) {
    return null;
  }

  const user = await db.user.findUnique({
    where: {
      id: session.user.id,
    },

    include: {
      userRoles: {
        include: {
          role: {
            include: {
              rolePermissions: true,
            },
          },
        },
      },
    },
  });

  if (!user || !user.isActive) {
    return null;
  }

  const activeUserRoles = user.userRoles.filter(
    (item) => item.role.isActive
  );

  const activeRoleCodes = activeUserRoles.map(
    (item) => item.role.code
  );

  const grants = activeUserRoles.flatMap((item) =>
    item.role.rolePermissions.map((permission) => ({
      permissionCode: permission.permissionCode,
      scope: permission.scope,
    }))
  );

  return {
    userId: user.id,
    name: user.name,
    email: user.email,

    isActive: user.isActive,

    roleCodes: user.userRoles.map(
      (item) => item.role.code
    ),

    activeRoleCodes,

    grants,
  };
});
```

注意：

1. 这里使用 Better Auth 当前会话中的用户 ID。
2. 用户必须处于启用状态。
3. 只有启用状态的角色才参与权限计算。
4. 禁用用户不能继续使用系统。
5. 禁用角色后，该角色的授权立即不再生效。

示例中的 `auth` 导入路径需要与当前项目已经导出的 Better Auth 实例保持一致。

这里使用 React `cache()`，目的是在同一次服务端请求中复用当前用户上下文。

不要使用 Next.js 持久化缓存来缓存权限结果。

用户角色、权限和禁用状态都可能发生变化，跨请求缓存会带来权限失效问题。

## 七、实现权限判断服务

接下来实现统一权限判断。

权限判断需要处理三种情况：

1. 未登录。
2. 已登录但没有权限。
3. 已登录且具有权限。

同时需要考虑多角色合并。

### 7.1 获取某个权限的有效数据范围

`lib/auth/permission-service.ts`

```ts
import "server-only";

import { DataScope } from "@/app/generated/prisma/client";

import type { CurrentActor } from "./authorization";
import type { PermissionCode } from "./permissions";

export function getPermissionScopes(
  permissionCode: PermissionCode,
  actor: CurrentActor
): DataScope[] {
  const scopes = actor.grants
    .filter(
      (grant) =>
        grant.permissionCode === permissionCode
    )
    .map((grant) => grant.scope);

  return [...new Set(scopes)];
}
```

这里没有通过角色等级来判断权限。

因为一个用户可能同时拥有多个角色。

例如：

```text
用户 A

BOSS
TEACHER
```

如果 BOSS 角色拥有 `student.view: ALL`，TEACHER 角色拥有 `student.view: ASSIGNED`，那么最终的数据范围应该是：

```text
ALL OR ASSIGNED = ALL
```

只要任意一个有效角色允许访问全部数据，就可以访问全部数据。

反过来：

```text
OWN OR ASSIGNED
```

则表示可以访问自己拥有的数据，以及分配给自己的数据。

这里使用逻辑 OR，而不是枚举值排序。

### 7.2 实现权限判断

```ts
import { PERMISSIONS } from "./permissions";
import { getCurrentActor } from "./current-actor";
import { getPermissionScopes } from "./permission-service";

import type { PermissionCode } from "./permissions";
import type { PermissionDecision } from "./authorization";

export async function checkPermission(
  permissionCode: PermissionCode
): Promise<PermissionDecision> {
  const actor = await getCurrentActor();

  if (!actor) {
    return {
      allowed: false,
      actor: null,
      scopes: [],
      reason: "UNAUTHENTICATED",
    };
  }

  const permission = PERMISSIONS[permissionCode];

  if (!permission) {
    return {
      allowed: false,
      actor,
      scopes: [],
      reason: "FORBIDDEN",
    };
  }

  // 超级管理员只绕过 SYSTEM 权限
  if (
    permission.domain === "SYSTEM" &&
    actor.activeRoleCodes.includes("SUPER_ADMIN")
  ) {
    return {
      allowed: true,
      actor,
      scopes: [],
    };
  }

  // SYSTEM 权限不允许普通角色通过 RolePermission 获得
  if (permission.domain === "SYSTEM") {
    return {
      allowed: false,
      actor,
      scopes: [],
      reason: "FORBIDDEN",
    };
  }

  const scopes = getPermissionScopes(
    permissionCode,
    actor
  );

  if (scopes.length === 0) {
    return {
      allowed: false,
      actor,
      scopes: [],
      reason: "FORBIDDEN",
    };
  }

  return {
    allowed: true,
    actor,
    scopes,
  };
}
```

这里的核心是：

```ts
if (
  permission.domain === "SYSTEM" &&
  actor.activeRoleCodes.includes("SUPER_ADMIN")
)
```

只有启用的超级管理员角色才能获得系统级权限。

普通 ADMIN 不会自动获得所有系统管理权限。

如果将来需要给 ADMIN 开放某项日常管理功能，应当明确设计对应的授权策略，而不是让它继承超级管理员的全部能力。

### 7.3 校验无效数据范围

数据库中的历史数据、手工修改数据或错误迁移，可能造成异常数据。

因此还需要增加校验：

```ts
const VALID_SCOPES = new Set([
  DataScope.ALL,
  DataScope.OWN,
  DataScope.ASSIGNED,
]);

export function validatePermissionScope(
  permissionCode: PermissionCode,
  scope: DataScope
) {
  const permission = PERMISSIONS[permissionCode];

  if (!permission) {
    throw new Error("未知权限");
  }

  if (!VALID_SCOPES.has(scope)) {
    throw new Error("无效的数据范围");
  }

  if (!permission.scopeable && scope !== DataScope.ALL) {
    throw new Error("该权限不支持配置数据范围");
  }
}
```

注意：

- 不支持数据范围的权限只能使用 ALL。
- 不允许通过 OWN、ASSIGNED 等数据范围制造没有意义的授权。
- 无效数据范围必须拒绝，不能默认扩大为 ALL。

对于读取到的历史异常授权，应记录安全日志，并在权限计算时拒绝该异常授权，不能因为数据异常而放宽访问范围。

## 八、实现资源级数据范围过滤

到目前为止，我们只是知道用户拥有某项权限，以及该权限对应的数据范围。

但还没有真正限制数据库查询。

例如：

教师 A 拥有：

```text
student.view: ASSIGNED
```

那么他只能看到分配给自己的学生。

不能仅仅在前端隐藏其他学生。

真正的控制必须放在数据库查询条件中。

### 8.1 定义资源级数据范围解析器

不同业务资源的数据归属关系并不一样。

例如：

- 学生可能关联家长和负责教师。
- 线索可能关联创建人或负责销售。
- 排课可能关联授课教师。
- 教学记录可能关联具体排课。

因此，我们按资源定义解析规则。

`lib/auth/permission-scope.ts`

```ts
import "server-only";

import { DataScope } from "@/app/generated/prisma/client";

import type { CurrentActor } from "./authorization";

type ScopeResolver = {
  ALL: (actor: CurrentActor) => object | null;
  OWN: (actor: CurrentActor) => object | null;
  ASSIGNED: (actor: CurrentActor) => object | null;
};

export const RESOURCE_SCOPE_RESOLVERS: Record<
  string,
  ScopeResolver
> = {
  student: {
    ALL: () => null,

    OWN: (actor) => ({
      parentLinks: {
        some: {
          userId: actor.userId,
        },
      },
    }),

    ASSIGNED: (actor) => ({
      teacherAssignments: {
        some: {
          userId: actor.userId,
        },
      },
    }),
  },

  lead: {
    ALL: () => null,

    OWN: (actor) => ({
      createdById: actor.userId,
    }),

    ASSIGNED: (actor) => ({
      assignedToId: actor.userId,
    }),
  },

  schedule: {
    ALL: () => null,

    OWN: (actor) => ({
      createdById: actor.userId,
    }),

    ASSIGNED: (actor) => ({
      teacherId: actor.userId,
    }),
  },
};
```

注意：

`parentLinks`、`teacherAssignments`、`createdById`、`assignedToId`、`teacherId` 是资源关系示例。

如果当前 Prisma Schema 尚未建立这些关系，不能直接复制后假定它们存在。

需要在对应业务模型落地时，按照实际关系字段实现解析器。

例如，学生归属关系到底是通过教师关联表还是排课关联表决定，需要结合实际业务模型确定。

### 8.2 构建数据范围查询条件

```ts
import { PERMISSIONS } from "./permissions";
import { getPermissionScopes } from "./permission-service";
import { RESOURCE_SCOPE_RESOLVERS } from "./permission-scope";

import type { CurrentActor } from "./authorization";
import type { PermissionCode } from "./permissions";

export function buildScopeWhere(
  permissionCode: PermissionCode,
  actor: CurrentActor
): object | null {
  const permission = PERMISSIONS[permissionCode];

  if (!permission.scopeable) {
    return null;
  }

  const scopes = getPermissionScopes(
    permissionCode,
    actor
  );

  if (scopes.length === 0) {
    throw new Error("没有有效的数据范围");
  }

  if (scopes.includes("ALL" as never)) {
    return null;
  }

  const resolver =
    RESOURCE_SCOPE_RESOLVERS[permission.resource];

  if (!resolver) {
    throw new Error(
      `未配置资源数据范围解析器：${permission.resource}`
    );
  }

  const conditions = scopes
    .map((scope) => {
      return resolver[scope](actor);
    })
    .filter((item): item is object => item !== null);

  if (conditions.length === 0) {
    throw new Error("无法解析数据范围");
  }

  if (conditions.length === 1) {
    return conditions[0];
  }

  return {
    OR: conditions,
  };
}
```

实际项目中建议将 `scope` 与 `DataScope` 枚举类型直接对应，不需要使用 `as never`。

例如：

```ts
if (scopes.includes(DataScope.ALL)) {
  return null;
}
```

示例中需要导入生成的 DataScope 枚举。

这里返回 `null` 表示不额外添加数据范围条件，适用于 ALL。

其他情况返回 Prisma 查询条件。

### 8.3 在列表查询中使用

例如学生列表：

```ts
import "server-only";

import { db } from "@/lib/db";

import { checkPermission } from "@/lib/auth/authorization";
import { buildScopeWhere } from "@/lib/auth/permission-scope";

export async function getStudentList() {
  const decision = await checkPermission("student.view");

  if (!decision.allowed || !decision.actor) {
    throw new Error("无权查看学生");
  }

  const scopeWhere = buildScopeWhere(
    "student.view",
    decision.actor
  );

  return db.student.findMany({
    where: scopeWhere ?? {},
    orderBy: {
      createdAt: "desc",
    },
  });
}
```

这样数据库查询就已经包含数据范围限制。

### 8.4 单条记录也必须检查

不能只限制列表。

例如用户通过 URL 直接访问：

```text
/student/123
```

如果只在列表查询中限制数据范围，用户仍然可能通过修改 ID 访问其他人的数据。

正确做法：

```ts
const student = await db.student.findFirst({
  where: {
    AND: [
      {
        id: studentId,
      },
      scopeWhere ?? {},
    ],
  },
});
```

这里使用 `findFirst`，而不是直接 `findUnique`。

因为需要同时组合主键条件和数据范围条件。

如果记录不存在，或者用户没有访问权限，都返回 404，避免通过错误信息泄露其他数据是否存在。

### 8.5 修改和删除同样需要数据范围

例如：

```ts
await db.student.updateMany({
  where: {
    AND: [
      {
        id: studentId,
      },
      scopeWhere ?? {},
    ],
  },

  data: {
    name,
  },
});
```

然后检查：

```ts
if (result.count === 0) {
  throw new Error("记录不存在或无权操作");
}
```

不要出现以下情况：

- 列表只能看到自己的数据。
- 详情页却可以通过 ID 访问所有数据。
- 编辑操作只检查 `student.edit`，不检查数据范围。
- 删除操作绕过数据范围。

权限和数据范围必须同时生效。

## 九、解决创建业务数据时的关联越权问题

前面定义了 `createScopes`，现在真正实现它。

为什么需要这一层？

假设某个教师拥有：

```text
schedule.create: ALL
```

但他只能访问自己负责的学生。

如果创建排课时，只检查：

```text
schedule.create
```

那么他可能提交一个不属于自己的 `studentId`。

因此，创建操作必须验证被引用的父资源。

### 9.1 定义父资源查询器

```ts
import "server-only";

import { db } from "@/lib/db";

import type { PermissionCode } from "./permissions";

type ParentResourceFinder = (
  id: string,
  where: object
) => Promise<boolean>;

export const PARENT_RESOURCE_FINDERS: Record<
  string,
  ParentResourceFinder
> = {
  student: async (id, where) => {
    const record = await db.student.findFirst({
      where: {
        AND: [
          { id },
          where,
        ],
      },
      select: {
        id: true,
      },
    });

    return Boolean(record);
  },

  course: async (id, where) => {
    const record = await db.course.findFirst({
      where: {
        AND: [
          { id },
          where,
        ],
      },
      select: {
        id: true,
      },
    });

    return Boolean(record);
  },

  schedule: async (id, where) => {
    const record = await db.schedule.findFirst({
      where: {
        AND: [
          { id },
          where,
        ],
      },
      select: {
        id: true,
      },
    });

    return Boolean(record);
  },

  lead: async (id, where) => {
    const record = await db.lead.findFirst({
      where: {
        AND: [
          { id },
          where,
        ],
      },
      select: {
        id: true,
      },
    });

    return Boolean(record);
  },
};
```

这里的 Prisma Model 名称是后续业务模块需要提供的资源查询入口。

如果某个业务模型尚未实现，先不要注册对应 Finder。

### 9.2 实现 assertCreateScope

```ts
import { PERMISSIONS } from "./permissions";
import { getPermissionScopes } from "./permission-service";
import { buildScopeWhere } from "./permission-scope";
import { PARENT_RESOURCE_FINDERS } from "./parent-resource";

import type { CurrentActor } from "./authorization";
import type { PermissionCode } from "./permissions";

export async function assertCreateScope(
  permissionCode: PermissionCode,
  payload: Record<string, unknown>,
  actor: CurrentActor
) {
  const definition = PERMISSIONS[permissionCode];

  const dependencies = definition.createScopes ?? [];

  for (const dependency of dependencies) {
    const parentId = payload[dependency.relation];

    if (
      typeof parentId !== "string" ||
      parentId.length === 0
    ) {
      throw new Error(
        `缺少关联字段：${dependency.relation}`
      );
    }

    const scopes = getPermissionScopes(
      dependency.permission,
      actor
    );

    if (scopes.length === 0) {
      throw new Error("无权使用关联业务资源");
    }

    const parentPermission =
      PERMISSIONS[dependency.permission];

    const finder =
      PARENT_RESOURCE_FINDERS[parentPermission.resource];

    if (!finder) {
      throw new Error(
        `未配置父资源查询器：${parentPermission.resource}`
      );
    }

    const where = buildScopeWhere(
      dependency.permission,
      actor
    );

    const allowed = await finder(
      parentId,
      where ?? {}
    );

    if (!allowed) {
      throw new Error("关联资源不存在或无权使用");
    }
  }
}
```

这样，创建排课时会自动检查学生和课程。

创建教学记录时会检查排课。

创建课时流水时会检查学生。

### 9.3 在创建 Service 中调用

例如排课创建：

```ts
export async function createSchedule(
  input: CreateScheduleInput
) {
  const decision = await checkPermission(
    "schedule.create"
  );

  if (!decision.allowed || !decision.actor) {
    throw new Error("无权创建排课");
  }

  await assertCreateScope(
    "schedule.create",
    input,
    decision.actor
  );

  return db.schedule.create({
    data: {
      studentId: input.studentId,
      courseId: input.courseId,
      teacherId: input.teacherId,
      startTime: input.startTime,
      endTime: input.endTime,
    },
  });
}
```

实际创建操作还需要在数据库事务中处理关联资源的并发变化，例如父资源被禁用、删除或转移归属的情况。

尤其是涉及金额、课时、教学记录的操作，应当把授权检查与写入尽量放在同一个事务中，避免检查通过后业务状态发生变化。

## 十、保护统一后台与家长端入口

现在我们有了统一权限服务，接下来处理入口访问。

### 10.1 统一后台入口

以下角色都使用统一后台：

```text
SUPER_ADMIN
BOSS
ACADEMIC
ADMIN
TEACHER
AGENT
```

他们都需要明确拥有：

```text
portal.admin
```

注意，这不是说他们拥有相同的菜单，而是允许进入统一后台框架。

### 10.2 家长端入口

家长端使用：

```text
portal.parent
```

家长不应该因为拥有 PARENT 角色就自动进入统一后台。

家长端使用独立路由：

```text
/parent
```

统一后台沿用项目当前已经使用的后台路由，例如：

```text
/admin
/teacher
```

不要为了本次权限改造重新设计全部 URL。

### 10.3 路由布局结构

建议最终结构：

```text
app/
  (backend)/
    layout.tsx

    admin/
      page.tsx

    teacher/
      page.tsx

  (parent)/
    parent/
      layout.tsx
      page.tsx
```

这里的 route group 只是组织代码的方式，不会出现在 URL 中。

如果项目当前的 `/admin`、`/teacher` 路由已经存在，可以继续沿用，不必为了示例进行大规模搬迁。

核心是：

- 统一后台使用一套公共布局。
- 不同角色根据权限加载不同菜单。
- 家长端使用独立布局。
- 不为每个后台角色创建独立的一套后台框架。

### 10.4 页面权限保护

建立统一页面权限函数：

```ts
import "server-only";

import { redirect } from "next/navigation";

import { checkPermission } from "./authorization";

import type { PermissionCode } from "./permissions";

export async function requirePagePermission(
  permissionCode: PermissionCode
) {
  const decision = await checkPermission(
    permissionCode
  );

  if (decision.reason === "UNAUTHENTICATED") {
    redirect("/login");
  }

  if (!decision.allowed) {
    return {
      allowed: false as const,
      actor: decision.actor,
    };
  }

  return {
    allowed: true as const,
    actor: decision.actor!,
  };
}
```

页面使用：

```tsx
export default async function StudentPage() {
  const result = await requirePagePermission(
    "student.view"
  );

  if (!result.allowed) {
    return <div>403：无权访问</div>;
  }

  return <StudentList />;
}
```

这里使用普通的 403 页面作为稳定实现。

Next.js 的 `forbidden()` 目前仍属于实验性能力，需要开启 `experimental.authInterrupts`，并且官方文档对其可用渠道有明确限制。如果项目明确选择启用实验性功能，可以再使用它；不应该把它当作默认稳定依赖。

### 10.5 Server Action 也必须检查权限

页面检查不能代替 Server Action 检查。

用户可以绕过前端，直接调用服务端操作。

建议统一返回类型：

```ts
export type ActionResult<T = undefined> =
  | {
      success: true;
      data?: T;
    }
  | {
      success: false;
      code:
        | "UNAUTHENTICATED"
        | "FORBIDDEN"
        | "VALIDATION_ERROR"
        | "BUSINESS_ERROR";
      message: string;
    };
```

例如：

```ts
"use server";

export async function deleteStudentAction(
  studentId: string
): Promise<ActionResult> {
  const decision = await checkPermission(
    "student.edit"
  );

  if (!decision.allowed || !decision.actor) {
    return {
      success: false,
      code: decision.reason ?? "FORBIDDEN",
      message: "无权执行该操作",
    };
  }

  // 后续调用 Service
  return {
    success: true,
  };
}
```

实际项目中，删除操作应定义独立的 `student.delete` 权限，而不是复用 `student.edit`。这里重点是展示 Server Action 必须独立校验授权。

不要把普通的权限拒绝直接抛成未处理的 Error，否则可能被当作服务端异常处理。

### 12.3 校验默认授权

```ts
import { PERMISSIONS } from "./permissions";

for (const grant of DEFAULT_ROLE_GRANTS) {
  const definition =
    PERMISSIONS[grant.permissionCode];

  if (!definition) {
    throw new Error(
      `未知权限：${grant.permissionCode}`
    );
  }

  if (!definition.grantable) {
    throw new Error(
      `权限不允许写入 RolePermission：${grant.permissionCode}`
    );
  }

  if (
    !definition.scopeable &&
    grant.scope !== DataScope.ALL
  ) {
    throw new Error(
      `权限不支持当前数据范围：${grant.permissionCode}`
    );
  }
}
```

这样可以避免将 SYSTEM 权限错误地写入 RolePermission。

```ts
const roles = await db.role.findMany({
  select: {
    id: true,
    code: true,
  },
});

  roles.map((role) => [role.code, role.id])
);

const permissionRows = DEFAULT_ROLE_GRANTS.map(
  (grant) => {
    const roleId = roleMap.get(grant.roleCode);

    if (!roleId) {
      throw new Error(
        `角色不存在：${grant.roleCode}`
      );
    }

    return {
      roleId,
      permissionCode: grant.permissionCode,
      scope: grant.scope,
    };
  }
);

await db.rolePermission.createMany({
  data: permissionRows,
  skipDuplicates: true,
});
```

这里不使用 `upsert` 更新已有记录。

因为重新运行 Seed 的目标是补齐缺失的初始化数据，而不是覆盖用户已经调整的权限。

## 十三、初始化超级管理员账号

超级管理员账号不能通过普通注册流程创建。

应该在受控的初始化流程中创建。

开发环境建议初始化一个固定测试账号：

```text
账号：superadmin
角色：SUPER_ADMIN
环境：development
```

具体密码不要写死在代码仓库中。

可以通过环境变量提供：

```env
INITIAL_SUPER_ADMIN_EMAIL=superadmin@example.com
INITIAL_SUPER_ADMIN_PASSWORD=从安全环境变量读取
```

注意：以上账号地址只是示例，实际使用自己的测试地址。

初始化逻辑应该：

1. 检查是否已经存在超级管理员角色。
2. 检查指定账号是否存在。
3. 如果账号不存在，通过 Better Auth 官方支持的用户创建流程创建。
4. 如果账号已经存在，只在初始化流程中确认其身份，不重复创建。
5. 通过事务关联 SUPER_ADMIN 角色。
6. 检查系统中至少存在一个有效超级管理员。
7. 记录初始化审计日志。

密码应通过 Better Auth 的密码哈希机制处理，不要自行明文写入 User 表，也不要在 Seed 中直接绕过认证库的密码处理逻辑。

开发环境可以通过环境变量初始化测试账号。

生产环境则应通过受控部署流程创建首个超级管理员，并在初始化后妥善保管凭据。

### 13.1 开发阶段的测试账号

建议固定准备以下账号：

| 账号 | 角色 | 用途 |
|---|---|---|
| superadmin | SUPER_ADMIN | 系统管理与权限配置 |
| boss | BOSS | 经营视角 |
| academic | ACADEMIC | 教务视角 |
| admin | ADMIN | 日常系统管理视角 |
| teacher | TEACHER | 教学视角 |
| agent | AGENT | 代理业务视角 |
| parent | PARENT | 家长端视角 |

不要通过在代码里加入开发环境权限放行来省略账号切换。

否则开发环境和生产环境的权限表现可能完全不同。

## 十四、保护最后一个超级管理员

超级管理员是系统安全的最后一道管理入口。

如果最后一个 SUPER_ADMIN 被禁用、删除或者撤销角色，系统就可能失去权限管理能力。

因此必须保护最后一个有效超级管理员。

需要保护四种操作：

1. 禁用超级管理员用户。
2. 删除超级管理员用户。
3. 从超级管理员用户身上移除 SUPER_ADMIN 角色。
4. 禁用 SUPER_ADMIN 角色。

注意：这和保护最后一个 ADMIN 是不同的规则。

现在真正需要保护的是：

```text
有效用户
+
有效 SUPER_ADMIN 角色
+
用户拥有 SUPER_ADMIN 角色关联
```

### 14.1 统计有效超级管理员数量

```ts
async function countActiveSuperAdmins(
  tx: Prisma.TransactionClient
) {
  return tx.userRole.count({
    where: {
      role: {
        code: "SUPER_ADMIN",
        isActive: true,
      },

      user: {
        isActive: true,
      },
    },
  });
}
```

这里需要根据当前 Prisma 关系名称调整。

### 14.2 定义异常类型

```ts
export class LastSuperAdminError extends Error {
  constructor() {
    super("不能移除最后一个有效超级管理员");
    this.name = "LastSuperAdminError";
  }
}
```

### 14.3 统一保护事务

```ts
import "server-only";

import {
  Prisma,
} from "@/app/generated/prisma/client";

import { db } from "@/lib/db";

function isSerializationConflict(error: unknown) {
  return (
    error instanceof Prisma.PrismaClientKnownRequestError &&
    error.code === "P2034"
  );
}

export async function withSuperAdminInvariant<T>(
  operation: (
    tx: Prisma.TransactionClient
  ) => Promise<T>
): Promise<T> {
  for (let attempt = 0; attempt < 3; attempt++) {
    try {
      return await db.$transaction(
        async (tx) => {
          const result = await operation(tx);

          const count = await countActiveSuperAdmins(tx);

          if (count < 1) {
            throw new LastSuperAdminError();
          }

          return result;
        },
        {
          isolationLevel:
            Prisma.TransactionIsolationLevel.Serializable,
        }
      );
    } catch (error) {
      if (
        isSerializationConflict(error) &&
        attempt < 2
      ) {
        continue;
      }

      throw error;
    }
  }

  throw new Error("超级管理员保护事务失败");
}
```

这里使用 PostgreSQL 的 Serializable 隔离级别。

目的是避免两个并发请求同时移除不同的超级管理员，分别检查时都认为还存在另一个超级管理员，最终导致系统失去全部超级管理员。

遇到序列化冲突时，最多重试三次。

### 14.4 禁用用户

```ts
await withSuperAdminInvariant(async (tx) => {
  await tx.user.update({
    where: {
      id: userId,
    },
    data: {
      isActive: false,
    },
  });
});
```

如果被禁用的是最后一个有效超级管理员，事务会回滚。

### 14.5 删除用户

```ts
await withSuperAdminInvariant(async (tx) => {
  await tx.user.delete({
    where: {
      id: userId,
    },
  });
});
```

如果 UserRole 采用级联删除，删除用户后统计数量会自动反映结果。

### 14.6 移除 SUPER_ADMIN 角色

```ts
await withSuperAdminInvariant(async (tx) => {
  await tx.userRole.delete({
    where: {
      userId_roleId: {
        userId,
        roleId,
      },
    },
  });
});
```

这里假设 UserRole 的联合唯一键名称为 `userId_roleId`，以实际 Prisma Schema 为准。

### 14.7 禁用 SUPER_ADMIN 角色

```ts
await withSuperAdminInvariant(async (tx) => {
  await tx.role.update({
    where: {
      id: roleId,
    },
    data: {
      isActive: false,
    },
  });
});
```

这四种操作都必须通过同一个保护事务。

不能只在前端按钮上做限制。

另外，生产环境中不应允许普通用户通过角色管理页面修改 SUPER_ADMIN 的保留属性。

## 十五、审计日志设计

权限系统不仅要能控制操作，还应该知道是谁修改了权限。

例如：

- 谁创建了一个角色？
- 谁给角色增加了权限？
- 谁撤销了某个用户的超级管理员身份？
- 谁禁用了一个账号？
- 谁修改了某个权限的数据范围？

这些都应该有审计记录。

### 15.1 审计模型

建议增加独立的审计日志模型：

```prisma
model AuditLog {
  id           String   @id @default(uuid())

  actorUserId  String?
  actorName    String
  actorEmail   String?

  action       String
  targetType   String
  targetId     String?

  before       Json?
  after        Json?

  ip           String?
  userAgent    String?

  createdAt    DateTime @default(now())

  actor        User?    @relation(
    fields: [actorUserId],
    references: [id],
    onDelete: SetNull
  )

  @@index([actorUserId, createdAt])
  @@index([targetType, targetId])
  @@index([action, createdAt])
}
```

User 中增加对应关系：

```prisma
auditLogs AuditLog[]
```

这里保留：

- 操作者 ID。
- 操作者姓名快照。
- 操作者邮箱快照。

即使操作者后来被删除，也能保留当时的操作人信息。

### 15.2 审计日志不记录敏感信息

以下内容不能进入审计日志：

- 明文密码。
- 密码哈希。
- 登录 Token。
- 重置密码 Token。
- API 密钥。
- 其他认证密钥。

`before` 和 `after` 只保存业务必要字段。

例如修改角色权限：

```json
{
  "roleCode": "TEACHER",
  "permissionCode": "student.view",
  "before": {
    "scope": "OWN"
  },
  "after": {
    "scope": "ASSIGNED"
  }
}
```

### 15.3 审计日志采用追加模式

审计日志应该是追加写入：

- 不提供普通更新接口。
- 不提供普通删除接口。
- 修改授权时记录一条新日志。
- 撤销授权时也记录一条日志。

对于角色权限变更，RolePermission 的修改和 AuditLog 的写入必须处于同一个数据库事务中。

如果审计记录写入失败，权限变更也应该回滚。

另外，IP 和 User-Agent 也属于个人信息，不能无限期保留。

建议先设置 180 天保留策略，再根据业务和合规要求调整；超过期限的数据进行归档或清理。

## 十六、角色权限配置的安全边界

现在需要把几个容易出现漏洞的地方统一起来。

### 16.1 ADMIN 不能管理超级管理员

ADMIN 不能：

- 创建 SUPER_ADMIN。
- 将 SUPER_ADMIN 分配给用户。
- 删除 SUPER_ADMIN。
- 禁用 SUPER_ADMIN 角色。
- 修改 SUPER_ADMIN 的系统保留属性。

这些操作只允许通过 SUPER_ADMIN 身份执行。

### 16.2 ADMIN 不自动获得 SYSTEM 权限

ADMIN 不是超级管理员。

例如：

```text
ADMIN
  ├── portal.admin
  └── 不自动获得 user.view
  └── 不自动获得 role.view
  └── 不自动获得 permission.view
```

如果后续需要 ADMIN 管理日常用户，可以再设计明确的授权策略。

但不能让它通过角色编码自动获得所有系统权限。

### 16.3 角色权限分配必须校验权限目录

分配权限时，必须验证：

```ts
const permission = PERMISSIONS[permissionCode];

if (!permission) {
  throw new Error("未知权限");
}

if (!permission.grantable) {
  throw new Error("该权限不允许通过角色授权");
}
```

同时检查数据范围：

```ts
validatePermissionScope(
  permissionCode,
  scope
);
```

不能直接把客户端传来的 permissionCode 和 scope 写进数据库。

### 16.4 两个角色分配入口都要保护

目前用户管理和角色管理都有角色关联功能：

- 用户管理中给用户分配角色，需要 `user.assignRole`。
- 角色管理中维护角色成员，需要 `role.assignUser`。

这两个权限代表不同的操作入口，但最终都要经过同一个角色关联 Service。

不能因为用户从另一个页面进入，就绕过权限检查。

### 16.5 AGENT 不允许修改学生教学数据

AGENT 的业务范围主要是线索、跟进、报名和转化。

它不应该拥有：

```text
student.edit
teachingRecord.create
lessonLedger.create
schedule.edit
```

尤其不能修改学生课时、教学记录、教师排课。

招生业务和教学业务必须保持边界。

## 十七、实现角色权限修改 Service

现在把前面定义的规则应用到实际授权操作。

这里以修改角色权限为例。

### 17.1 先检查调用者身份

```ts
const decision = await checkPermission(
  "role.assignPermissions"
);

if (!decision.allowed || !decision.actor) {
  return {
    success: false,
    code: "FORBIDDEN",
    message: "无权修改角色权限",
  };
}
```

因为 `role.assignPermissions` 是 SYSTEM 权限，所以只有有效 SUPER_ADMIN 可以通过特殊授权规则。

### 17.2 校验目标角色

```ts
const role = await db.role.findUnique({
  where: {
    id: roleId,
  },
});

if (!role) {
  throw new Error("角色不存在");
}

if (role.code === "SUPER_ADMIN") {
  throw new Error("不能通过普通权限配置修改超级管理员");
}
```

### 17.3 校验所有权限编码

```ts
for (const item of permissions) {
  const definition = PERMISSIONS[item.permissionCode];

  if (!definition) {
    throw new Error(
      `未知权限：${item.permissionCode}`
    );
  }

  if (!definition.grantable) {
    throw new Error(
      `该权限不允许通过角色授权：${item.permissionCode}`
    );
  }

  validatePermissionScope(
    item.permissionCode,
    item.scope
  );
}
```

### 17.4 在事务中更新授权并记录审计

```ts
await db.$transaction(async (tx) => {
  const before = await tx.rolePermission.findMany({
    where: {
      roleId,
    },
  });

  await tx.rolePermission.deleteMany({
    where: {
      roleId,
    },
  });

  if (permissions.length > 0) {
    await tx.rolePermission.createMany({
      data: permissions.map((item) => ({
        roleId,
        permissionCode: item.permissionCode,
        scope: item.scope,
      })),
    });
  }

  await tx.auditLog.create({
    data: {
      actorUserId: decision.actor!.userId,
      actorName: decision.actor!.name,
      actorEmail: decision.actor!.email,

      action: "ROLE_PERMISSION_UPDATE",
      targetType: "Role",
      targetId: roleId,

      before: before,
      after: permissions,
    },
  });
});
```

实际 Service 还应在事务中重新确认角色状态和保留角色规则，避免检查与写入之间出现状态变化。

对于大量权限更新，还应考虑事务隔离、唯一约束和并发修改问题。

## 十八、权限系统测试

权限系统不能只靠页面测试。

因为很多越权问题在页面上看不出来，必须针对授权服务和数据范围写测试。

建议使用 Vitest。

### 18.1 超级管理员 SYSTEM 权限测试

场景：

```text
用户：superadmin
用户状态：启用
角色：SUPER_ADMIN
角色状态：启用
数据库：没有任何 SYSTEM 权限授权记录
请求：role.assignPermissions
```

预期：

```text
allowed = true
```

因为 SYSTEM 权限通过超级管理员身份获得，不需要写入 RolePermission。

### 18.2 普通 ADMIN 测试

场景：

```text
用户：admin
用户状态：启用
角色：ADMIN
角色状态：启用
请求：role.assignPermissions
```

预期：

```text
allowed = false
```

不能因为 ADMIN 角色名称包含管理员，就获得超级管理员权限。

### 18.3 禁用用户测试

场景：

```text
用户：superadmin
用户状态：禁用
角色：SUPER_ADMIN
角色状态：启用
```

预期：

```text
allowed = false
```

用户禁用后，即使数据库中仍然关联超级管理员角色，也不能继续使用。

### 18.4 禁用角色测试

场景：

```text
用户：superadmin
用户状态：启用
角色：SUPER_ADMIN
角色状态：禁用
```

预期：

```text
allowed = false
```

### 18.5 数据范围合并测试

例如：

```text
角色 A：student.view = OWN
角色 B：student.view = ASSIGNED
```

预期：

```text
OWN OR ASSIGNED
```

不能错误地只取第一个角色的数据范围。

再增加一个角色：

```text
角色 C：student.view = ALL
```

预期：

```text
ALL
```

### 18.6 无授权测试

场景：

```text
用户拥有有效角色
但没有 student.view 授权
```

预期：

```text
allowed = false
```

不能默认放开。

### 18.7 SYSTEM 权限不能写入数据库

测试：

```text
user.view
role.view
permission.view
role.assignPermissions
```

这些权限的 `grantable` 都是 false。

尝试写入 RolePermission 时必须拒绝。

### 18.8 创建关联资源越权测试

例如教师创建排课：

```text
schedule.create = ALL
student.useForSchedule = ASSIGNED
```

教师提交一个不属于自己的学生 ID。

预期：

```text
创建失败
```

即使拥有创建排课的权限，也不能使用没有权限访问的学生。

### 18.9 最后一个超级管理员保护测试

分别测试：

| 操作 | 预期 |
|---|---|
| 禁用最后一个超级管理员 | 拒绝 |
| 删除最后一个超级管理员 | 拒绝 |

```text
                         ▼
                   CurrentActor
                         │
                         ▼

            ▼                         ▼
```

## 二十、下一篇做什么？

本篇主要完成权限体系的基础架构，并没有把所有业务角色的权限一次性配置完毕。

下一步应该继续完善权限管理的实际使用流程：

- 权限目录如何展示。
- 角色权限如何分组展示。
- 如何给角色分配权限。
- 如何设置 ALL、OWN、ASSIGNED。
- 如何查看某个用户最终拥有的权限。
- 如何处理多个角色之间的权限合并。
- 如何验证授权修改是否真正影响菜单、页面和数据。

后续再结合学生、课程、排课、教学记录、课时账本等模块，逐步落实完整的业务权限矩阵。

**权限系统最重要的不是把按钮隐藏起来，而是让每一次服务端操作、每一次数据查询、每一次业务写入，都有明确且可验证的授权依据。**
