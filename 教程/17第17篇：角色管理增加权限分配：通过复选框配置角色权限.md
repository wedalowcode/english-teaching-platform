# 第17篇：角色管理增加权限分配：通过复选框配置角色权限

## 一、前言

前面已经完成了角色管理、用户与角色关联。现在我们需要解决一个关键问题：

**用户拥有某个角色之后，究竟可以在系统中做什么？**

例如：

- 教务人员可以查看学生，但不能删除学生。
- 教师可以查看自己的教学任务，但不能查看全部教师的任务。
- 财务人员可以查看收款记录，但不一定有权限修改订单。

因此，角色不能只是一个名称，还必须关联一组权限。

本篇实现角色权限分配功能，完成以下链路：

```text
角色列表 → 更多菜单 → 分配权限页面
         ↓
Service：从权限目录生成可分配权限 + 查询已有授权
         ↓
前端：模块导航 + 资源折叠 + 复选框 + 数据范围
         ↓
Server Action：zod 校验 → 白名单校验 → scope 校验
         ↓
Prisma 事务：先删后写 RolePermission
```

## 二、权限数据模型

项目在 `prisma/schema.prisma` 中定义了 `RolePermission`：

```prisma
enum DataScope {
  ALL
  OWN
  ASSIGNED
}

model RolePermission {
  id String @id @default(uuid())

  roleId String

  // 权限编码由 TypeScript 权限目录维护
  permissionCode String

  // 数据范围：ALL / OWN / ASSIGNED
  scope DataScope

  role Role @relation(
    fields: [roleId],
    references: [id],
    onDelete: Cascade
  )

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([roleId, permissionCode])
  @@index([permissionCode])
}
```

两个关键字段：

- `permissionCode`：记录角色获得了什么权限。
- `scope`：记录这项权限允许访问什么范围的数据。

例如：

| 角色 | 权限编码 | 数据范围 |
|---|---|---|
| 教师 | student.view | OWN |
| 教务 | student.view | ALL |
| 教师 | schedule.view | ASSIGNED |

权限定义由 TypeScript 维护，数据库只保存授权结果。这样避免把权限名称、模块等静态信息重复存储到数据库中。

## 三、domain 的真实语义

早期版本中，`domain: "SYSTEM"` 的权限被硬编码为只允许 SUPER_ADMIN 获得，不允许通过 RolePermission 分配给普通角色。这个设计在实现上造成了困惑：权限配置页明明列出了权限，普通角色却分配不到。

当前实现中，`domain` 仅作为 SUPER_ADMIN **内置绕过**的范围标记：

```ts
// lib/auth/authorization.ts
if (
  permission.domain === "SYSTEM" &&
  actor.activeRoleCodes.includes(SYSTEM_ROLE_CODES.SUPER_ADMIN)
) {
  return { allowed: true, actor, scopes: [] };
}

// BUSINESS 权限 + 非超管角色的 SYSTEM 权限：统一通过 RolePermission 判断
const scopes = actor.grants.filter(
  (grant) => grant.permissionCode === permissionCode
).map((grant) => grant.scope);
```

也就是说：

- **SUPER_ADMIN**：所有 `domain === "SYSTEM"` 的权限内置放行，不需要写入 RolePermission 表。
- **其他角色**：不管 domain 是什么，都必须通过 RolePermission 表获得授权。

这个设计让权限分配路径统一、前端行为一致，不再有"前端能勾选但后端不放行"的情况。

## 四、可分配权限白名单

打开 `lib/auth/permissions.ts`，在类型定义之后维护一个明确的白名单：

```ts
export const ROLE_ASSIGNABLE_PERMISSION_CODES = [
  // 统一后台入口
  "portal.admin",

  // 用户管理
  "user.view",
  "user.create",
  "user.edit",
  "user.delete",
  "user.disable",
  "user.resetPassword",
  "user.assignRole",

  // 角色管理
  "role.view",
  "role.create",
  "role.edit",
  "role.delete",
  "role.disable",
  "role.assignUser",
  "role.assignPermissions",
] as const satisfies readonly PermissionCode[];
```

这个数组同时是三个边界：

| 边界 | 使用位置 |
|---|---|
| 前端展示边界 | 权限配置页只列出白名单内的权限 |
| 后端保存边界 | Server Action 拒绝白名单外的权限编码 |
| 事务删除边界 | 只删除白名单内的权限记录，不影响其他表写入 |

规则：权限目录可以提前定义未来功能的权限，但只有真正实现并经过验证的权限才能加入白名单。未开放的权限编码即使伪造请求，服务端也会拒绝。

## 六、Service：查询角色权限配置

`features/roles/service.ts`：

```ts
import {
  PERMISSIONS,
  ROLE_ASSIGNABLE_PERMISSION_CODES,
  SYSTEM_ROLE_CODES,
} from "@/lib/auth/permissions";

export async function getRolePermissionConfig(roleId: string) {
  await requirePagePermission("role.assignPermissions");

  const role = await db.role.findUnique({
    where: { id: roleId },
    select: {
      id: true,
      code: true,
      name: true,
      isSystem: true,
    },
  });

  if (!role) return null;

  const permissions = ROLE_ASSIGNABLE_PERMISSION_CODES.map((code) => {
    const item = PERMISSIONS[code];

    return {
      code,
      name: item.name,
      module: item.module,
      resource: item.resource,
      action: item.action,
      scopeable: item.scopeable,
    };
  });

  const assigned = await db.rolePermission.findMany({
    where: {
      roleId,
      permissionCode: {
        in: [...ROLE_ASSIGNABLE_PERMISSION_CODES],
      },
    },
    select: {
      permissionCode: true,
      scope: true,
    },
  });

  return {
    role,
    permissions,
    assigned,
    isSuperAdmin: role.code === SYSTEM_ROLE_CODES.SUPER_ADMIN,
  };
}
```

关键点：

- 可分配权限不是从数据库读的，而是从权限目录生成。数据库只保存授权结果。
- `isSuperAdmin` 传给前端后，超级管理员角色会看到一条"内置系统权限由身份自动获得"的说明横幅，避免用户误解为什么用户管理/角色管理权限不在可分配列表里（那些权限对超管自动生效，不需要也不应该写入 RolePermission）。

## 七、Action：校验并保存权限

`features/roles/actions.ts`：

首先是 zod 校验前端传来的数据结构：

```ts
const permissionItemSchema = z.object({
  code: z.string(),
  scope: z.enum(["ALL", "OWN", "ASSIGNED"]),
});

const savePermissionsSchema = z.array(permissionItemSchema);
```

然后是完整的保存逻辑：

```ts
import { DataScope } from "@/app/generated/prisma/client";
import {
  PERMISSIONS,
  ROLE_ASSIGNABLE_PERMISSION_CODES,
} from "@/lib/auth/permissions";

export async function saveRolePermissionsAction(
  roleId: string,
  values: unknown
): Promise<RoleActionResult> {
  await requirePagePermission("role.assignPermissions");

  // 1. 基础结构校验
  const parsed = savePermissionsSchema.safeParse(values);
  if (!parsed.success) {
    return { success: false, message: "权限配置参数不正确" };
  }

  const items = parsed.data;
  const allowedCodes = ROLE_ASSIGNABLE_PERMISSION_CODES as readonly string[];

  // 2. 白名单 + 去重校验
  if (
    new Set(items.map((item) => item.code)).size !== items.length ||
    items.some((item) => !allowedCodes.includes(item.code))
  ) {
    return { success: false, message: "包含重复或尚未开放的权限" };
  }

  // 3. 数据范围校验
  for (const item of items) {
    const permission = PERMISSIONS[item.code as PermissionCode];

    if (!permission.scopeable && item.scope !== "ALL") {
      return {
        success: false,
        message: `${permission.name}不支持配置数据范围`,
      };
    }
  }

  // 4. 角色存在性校验
  const role = await db.role.findUnique({
    where: { id: roleId },
    select: { id: true },
  });
  if (!role) {
    return { success: false, message: "角色不存在" };
  }

  // 5. 事务保存：先删后写
  await db.$transaction(async (tx) => {
    await tx.rolePermission.deleteMany({
      where: {
        roleId,
        permissionCode: { in: [...ROLE_ASSIGNABLE_PERMISSION_CODES] },
      },
    });

    if (items.length > 0) {
      await tx.rolePermission.createMany({
        data: items.map((item) => ({
          roleId,
          permissionCode: item.code,
          scope: item.scope as DataScope,
        })),
      });
    }
  });

  revalidatePath("/admin/roles");
  revalidatePath(`/admin/roles/${roleId}/permissions`);

  return { success: true };
}
```

三层防御：

1. **zod 校验**：拒绝非数组、非枚举值等畸形输入。
2. **白名单 + 去重**：拒绝伪造的权限编码和重复条目。
3. **scope 规则**：不支持数据范围的权限强制要求 `ALL`。

事务的先删后写采用的是**整组提交**模型：前端提交角色最终应该拥有的全部权限，服务端在一次事务中用新的授权集合替换旧集合。事务保证要么一起成功，要么一起回滚。

注意 `deleteMany` 的范围限定在白名单内，不会误删未来可能写入的其他权限类型。

### 8.3 核心状态

```tsx
type Scope = "ALL" | "OWN" | "ASSIGNED";

const [selected, setSelected] = useState<Record<string, Scope>>(
```

### 8.6 保存

```tsx
function save() {
  const values = Object.entries(selected).map(([code, scope]) => ({ code, scope }));

  startTransition(async () => {
    const result = await saveRolePermissionsAction(roleId, values);

    if (result.success) {
      toast.success("角色权限保存成功");
    } else {
      toast.error(result.message ?? "保存失败");
    }
  });
}
```

用 `useTransition` 让 React 标记提交为 pending，`Button disabled={pending}` 防重复提交。保存成功后通过 Sonner toast 提示用户，PageHeader 的 `revalidatePath` 在服务端触发页面重渲染，权限配置页自动回显最新状态。

## 九、数据范围执行 vs 数据范围配置

这是一个重要的边界：

**权限配置页选择 ALL/OWN/ASSIGNED，只是把值写入 `RolePermission.scope` 字段。真正查询业务数据时，还需要 Service 根据当前用户身份和 scope 值生成 Prisma where 条件。**

例如未来学生列表 Service 的伪代码：

```ts
const scope = await getPermissionScopes(actor, "student.view");

let where = {};
if (scope.includes("OWN")) {
  where = { ownerTeacherId: actor.userId };
} else if (scope.includes("ASSIGNED")) {
  where = { assignments: { some: { teacherId: actor.userId } } };
}
// ALL 不加限制
```

**不能因为界面上已经能选择"本人数据"，就认为数据库查询自动具备了数据隔离能力。** 这部分需要等学生/课程/排课等业务模块落地后，在对应的 Service 里逐个落实。

## 十、本篇小结

**从权限目录到数据库写入的完整链路：**

```text
权限目录 PERMISSIONS（未来功能预定义）
   ↓
白名单 ROLE_ASSIGNABLE_PERMISSION_CODES（已交付功能）
   ↓
Service：从白名单生成权限 + 查询已有授权
   ↓
前端：模块导航 + Accordion 资源组 + Checkbox + RadioGroup
   ↓
Server Action：zod → 白名单 → scope → 事务先删后写
   ↓
数据库 RolePermission（roleId + permissionCode + scope）
```

**三个必须记住的原则：**

1. **前端复选框只是配置入口，真正的权限边界必须由服务端校验。** 所有权限编码和数据范围都会在 Action 里重新校验，不信任前端。
2. **domain 不限制普通角色，只影响超管内置绕过范围。** 普通角色通过 RolePermission 表获得一切权限，包括 SYSTEM 域的用户管理/角色管理。
3. **白名单是当前真实开放的边界。** 权限目录可以提前规划未来功能，但只有真正实现的权限才能加入白名单。

下一步，继续在 Service 层落实数据范围的 Prisma 查询条件，让 ALL/OWN/ASSIGNED 真正影响业务数据的可见范围。
