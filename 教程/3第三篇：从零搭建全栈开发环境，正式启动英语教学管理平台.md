# 第三篇：从零搭建全栈开发环境，正式启动英语教学管理平台

> **版本说明**：本文基于 Next.js App Router、Prisma 7 和 PostgreSQL。Prisma 8 目前仍是候选版本（RC），但不锁定版本时安装命令会装到它，命令和配置与本文不一致，因此本文全程锁定 Prisma 7。

前两篇文章，我们分别完成了英语教学管理平台的产品规划和数据库设计。

我们已经明确了系统要解决什么问题，老板、教务、管理员、教师、家长和代理分别需要哪些功能，也梳理了客户、学员、教师、课程、训练、课时和结算等核心业务数据。

这套环境不仅要能够运行前端页面，还要能够连接数据库、执行数据库迁移、运行服务端业务逻辑。后续所有功能开发，都将在这个基础上进行。

## 一、确定开发技术栈

这次我们采用一套统一的 TypeScript 全栈技术体系。

为什么不把前端和后端拆成两个独立项目？

因为这次研发的是一款中小型培训机构管理软件，没有必要一开始就引入复杂的微服务架构。

使用 Next.js，可以在一个项目中完成页面展示、服务端业务处理、权限校验和数据库访问。

我们的技术选型如下：

| 技术 | 用途 |
| --- | --- |
| Next.js | 全栈应用框架 |
| React | 前端页面开发 |
| TypeScript | 统一开发语言 |
| PostgreSQL | 关系型数据库 |
| Prisma 7 | ORM 和数据库迁移 |
| Tailwind CSS | 页面样式 |
| shadcn/ui | 后台界面组件 |
| pnpm | 项目包管理工具 |
| Git | 代码版本管理 |
| Zod | 数据校验和类型定义 |

这里简单介绍一下各个技术的作用。

**Next.js + React**

负责整个应用的页面和服务端运行环境。

例如，用户访问系统首页、登录页面、教师工作台、家长端，都由 Next.js 统一管理。

**TypeScript**

我们不使用纯 JavaScript，而是使用 TypeScript。

TypeScript 可以为变量、函数、对象和业务数据定义类型，减少开发过程中因数据结构不一致导致的问题。

**PostgreSQL**

负责保存系统的业务数据。

例如用户、学员、教师、课程、订单、课时流水等，都会存储在 PostgreSQL 中。

**Prisma 7**

负责连接数据库、定义数据模型、执行数据库迁移，以及在业务代码中访问数据库。

相比直接编写大量 SQL，Prisma 能够让我们通过 TypeScript 的方式操作数据库。

**Tailwind CSS + shadcn/ui**

Tailwind CSS 负责页面样式，shadcn/ui 提供后台系统常用的基础组件，例如按钮、表格、弹窗、表单和下拉选择框。

我们会在此基础上构建自己的业务组件，而不是每个页面都重新编写一套 UI。

**Zod**

Zod 是一个用于数据校验和类型定义的库。

它可以帮助我们在业务代码中定义数据的类型，以及在接收用户输入时进行校验。

> **提示：安装依赖时出现 `Ignored build scripts` 怎么办？**
>
> pnpm 10 开始，默认不再自动运行依赖包的安装脚本，以防止恶意包在本机执行代码。因此安装依赖后，可能看到类似下面的提示：
>
> ```text
> [ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@x.x.x ...
> Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
> ```
>
> 这不是错误，而是安全提示。执行 `pnpm approve-builds`，用空格键勾选需要运行脚本的依赖（例如 `esbuild`），回车确认即可。pnpm 会把选择记录到项目配置中（`package.json` 或 `pnpm-workspace.yaml`），这部分变更应该提交到 Git。
>
> 如果列表里出现了你不认识的包，可以先执行 `pnpm why 包名` 查看它是被谁引入的，再决定是否批准。

## 五、了解项目目录结构

创建项目后，先不要急着写业务功能。

我们需要了解一下 Next.js 项目的基本目录。

当前项目的核心结构如下：

```text
learnenglish/
├── app/
│   ├── favicon.ico
│   ├── globals.css
│   ├── layout.tsx
│   └── page.tsx
│
├── public/
├── node_modules/
│
├── package.json
├── pnpm-lock.yaml
├── tsconfig.json
├── next.config.ts
├── eslint.config.mjs
└── .gitignore
```

> 实际项目中，你可能还会看到 `.next/`（构建缓存）、`next-env.d.ts`（类型声明）、`pnpm-workspace.yaml`，以及 `.agents`、`.claude`、`.cursor`、`AGENTS.md` 等 AI 编程工具生成的配置。这些都可以暂时忽略，不影响本文的步骤。

几个重要目录和文件：

**app/**

Next.js App Router 的核心目录。

页面、布局和路由都在这里组织。

文件夹对应网址路径，文件夹里的 `page.tsx` 决定这个路径显示什么内容。例如：

```text
app/
├── page.tsx
├── login/
│   └── page.tsx
└── admin/
    └── page.tsx
```

对应的访问地址分别是：

```text
/        → app/page.tsx
/login   → app/login/page.tsx
/admin   → app/admin/page.tsx
```

**public/**

存放图片、图标等静态资源。

**package.json**

保存项目依赖、项目脚本和相关配置。

**tsconfig.json**

TypeScript 配置文件。

**app/layout.tsx** 和 **app/page.tsx** 是初学者最容易混淆的两个文件，下面单独讲清楚。

### 1. layout.tsx 与 page.tsx 有什么区别

一句话概括：**layout 是外壳，page 是内容。**

**`layout.tsx`：布局（外壳）**

- 定义页面的整体 HTML 结构，例如 `<html>`、`<body>`、字体、全局样式和页面标题等基础信息。
- 由其下所有页面共用，切换页面时外壳不会重新渲染。
- 通过 `children` 接收当前路由对应的 `page.tsx`，并把它嵌在自己的结构里。
- `app/layout.tsx` 是根布局，必须存在。

```tsx
export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="zh-CN">
      <body>{children}</body>
    </html>
  );
}
```

**`page.tsx`：页面（内容）**

- 对应某一个具体网址的页面内容。
- `app/page.tsx` 对应首页 `/`，`app/login/page.tsx` 对应 `/login`。
- 一个文件夹里没有 `page.tsx`，这个路径就不能被访问。

访问 `/` 时，Next.js 实际渲染的是：

```text
RootLayout
  └── Home（app/page.tsx）
```

访问 `/login` 时：

```text
RootLayout
  └── LoginPage（app/login/page.tsx）
```

外壳不变，里面的内容换了。

简单概括：

- **app/layout.tsx**：整个应用的根布局，负责所有页面共用的 HTML 结构、全局样式和基础元信息。
- **app/page.tsx**：网站根路径 `/` 对应的首页内容，显示在根布局内部。

### 2. 规划多端布局：路由组与独立目录

我们的系统有两种截然不同的界面形态：

- **PC 后台**：老板、教务、管理员、教师、代理使用，进入后左侧是菜单、右侧是内容。
- **家长端 H5**：家长用手机打开，顶部标题加底部 Tab 导航。

这里有一个关键判断：**左侧菜单加右侧内容的框架，不能放在根布局里。**

因为根布局是所有页面共用的，而登录页不需要菜单，家长端的导航形态也完全不同。如果把左右结构写进 `app/layout.tsx`，登录页和家长端也会带上后台菜单。

所以根布局只保留最外层骨架，具体的端形态放到下一层的 `layout.tsx` 中。

Next.js 提供了**路由组**来做这件事：用括号包起来的文件夹，例如 `(dashboard)`，只用来分组和共享布局，**不会出现在网址里**。

```text
app/(dashboard)/students/page.tsx   → 网址是 /students，而不是 /dashboard/students
```

结合我们的业务，后续的目录规划如下：

```text
app/
├── layout.tsx                  ← 根布局：html、body、全局样式（所有端共用）
├── page.tsx                    ← 首页 /，后续可按登录身份跳转到对应端
│
├── (auth)/                     ← 路由组：登录相关，无菜单
│   └── login/page.tsx          → /login
│
├── (dashboard)/                ← 路由组：PC 端后台（左侧菜单 + 右侧内容）
│   ├── layout.tsx              ← 共用的左右布局
│   ├── boss/                   → /boss/...
│   ├── academic/               → /academic/...
│   ├── admin/                  → /admin/...
│   ├── teacher/                → /teacher/...
│   └── agent/                  → /agent/...
│
└── parent/                     ← 家长端 H5，独立目录
    ├── layout.tsx              ← 移动端布局：顶部标题 + 底部 Tab
    ├── page.tsx                → /parent（学习首页）
    ├── lessons/page.tsx        → /parent/lessons
    ├── reports/page.tsx        → /parent/reports
    └── account/page.tsx        → /parent/account
```

这里有几个设计要点：

**第一，路由组不改变网址，真实目录才改变网址。**

`(dashboard)` 带括号，只负责共享布局；`parent` 没有括号，所以网址是 `/parent/...`。家长端保留 `/parent` 前缀，便于分享链接，也方便后续用中间件统一拦截：未登录或非家长身份，不允许访问 `/parent/*`。

**第二，PC 后台的菜单按角色区分。**

老板、教务、教师的菜单项不同。推荐在 `(dashboard)/layout.tsx` 中统一搭好左右框架，再根据当前用户角色渲染不同的菜单配置。外层框架统一，菜单按角色配置，维护起来更省事。如果某个角色的界面差异特别大，也可以在角色目录下再放一个嵌套的 `layout.tsx`。

**第三，家长端适配手机的关键在 layout，而不是目录。**

目录只是隔离了代码。真正让它适配手机的是 `parent/layout.tsx` 的设计，例如：

```tsx
export default function ParentLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <div className="mx-auto flex min-h-screen max-w-md flex-col bg-gray-50">
      <header className="border-b bg-white p-4 text-center font-medium">
        学习中心
      </header>

      <main className="flex-1 p-4">{children}</main>

      <nav className="grid grid-cols-4 border-t bg-white text-center text-sm">
        {/* 底部 Tab：首页 / 课程 / 报告 / 我的 */}
      </nav>
    </div>
  );
}
```

`max-w-md` 限制了最大宽度：在手机上占满屏幕，在电脑上打开时居中显示，不会被拉得过宽。

| 端 | 位置 | 布局特点 |
| --- | --- | --- |
| 登录页 | `(auth)` 路由组 | 无菜单，居中表单 |
| PC 后台 | `(dashboard)` 路由组 | 左侧菜单 + 右侧内容 |
| 家长端 H5 | `parent/` 独立目录 | 顶部标题 + 底部 Tab，限宽适配手机 |

需要强调的是：**这只是规划，现在不需要创建这些目录。** 它们会随着后面的业务模块逐步出现。后续开发登录和工作台时，我们再把这套结构真正落地。

## 六、安装并配置 Prisma 7

Next.js 项目已经运行起来了，接下来让应用能够访问 PostgreSQL。

我们使用 Prisma 7 作为 ORM。

> **重要：一定要锁定 Prisma 的主版本。**
>
> Prisma 8 目前仍是候选版本（RC），但从 2026 年 8 月起，不指定版本直接执行 `pnpm add -D prisma`，会安装到 Prisma 8 的 RC。Prisma 8 采用了全新的 contract-first 工作方式，命令和配置文件都和 Prisma 7 不同，例如 `prisma init` 不再生成 `schema.prisma`，迁移命令也被重命名。如果误装了 8，后面的步骤都会对不上。
>
> 因此本文所有 Prisma 相关依赖，都显式指定 `@7`。

### 1. 安装 Prisma

在项目根目录执行：

```bash
pnpm add -D prisma@7 dotenv
pnpm add @prisma/client@7 @prisma/adapter-pg@7 pg
```

这里安装了五个依赖：

- prisma：Prisma 命令行工具。
- dotenv：让 `prisma.config.ts` 能够读取 `.env` 文件中的环境变量。
- @prisma/client：业务代码中使用的数据库客户端。
- @prisma/adapter-pg：PostgreSQL 数据库适配器。
- pg：Node.js PostgreSQL 驱动。

Prisma 7 使用数据库 Driver Adapter 连接关系型数据库，因此需要安装对应的 PostgreSQL 适配器。

安装完成后，确认版本：

```bash
pnpm prisma --version
```

输出应该是 `7.x.x`。如果显示的是 `8.0.0-rc.xx`，说明装成了 Prisma 8，请重新安装：

```bash
pnpm remove prisma @prisma/client @prisma/adapter-pg
pnpm add -D prisma@7 dotenv
pnpm add @prisma/client@7 @prisma/adapter-pg@7 pg
```

> 注意：新版本的 Prisma 命令行已经不支持 `-v` 参数，查看版本请使用 `--version`。
>
> 如果安装过程中再次出现 `Ignored build scripts` 提示，参考第二章的说明处理即可。

### 2. 初始化 Prisma

执行：

```bash
pnpm prisma init
```

在 Prisma 7 中，直接执行 `init` 即可，默认就是 PostgreSQL，不需要额外指定数据库类型。旧教程中常见的 `--datasource-provider postgresql` 参数，在新版本中可能直接报参数错误，所以这里不再使用。

初始化完成后，项目中应该出现：

```text
learnenglish/
├── prisma/
│   └── schema.prisma
│
├── prisma.config.ts
├── .env
└── ...
```

其中：

- prisma/schema.prisma：定义数据库模型。
- prisma.config.ts：配置 Prisma 的运行参数和数据库连接。
- .env：保存本地开发环境变量。

> **如果 `init` 之后文件不全怎么办？**
>
> 有的版本或环境下，`init` 可能只生成其中一部分文件（例如只有 `prisma.config.ts`）。这不影响后续开发：缺哪个文件，就按照下面第 3、4、5 步手动创建即可，最终保证项目里有这三个文件就行。
>
> 另外，`.env` 在部分编辑器的文件树中会被隐藏，可以在终端用 `dir .env`（Windows）或 `ls -a`（macOS / Linux）确认它是否存在。

### 3. 配置数据库连接

打开（或新建）项目根目录下的 `.env` 文件。

配置 PostgreSQL 连接地址：

```env
DATABASE_URL="postgresql://postgres:你的数据库密码@localhost:5432/learnenglish?schema=public"
```

其中：

- postgres：数据库用户名。
- 你的数据库密码：安装 PostgreSQL 时设置的密码，请替换成自己的。
- localhost：数据库地址。
- 5432：数据库端口。
- learnenglish：数据库名称。

如果数据库密码包含 `@`、`#`、`/` 等特殊字符，需要按照 URL 编码规则处理，否则连接地址会被解析错误。

注意：

`.env` 保存的是本地环境配置，不应该提交到公开 Git 仓库，也不要把真实密码写进文章或截图里。

建议在 `.gitignore` 中确认已经忽略 `.env` 文件。

### 4. 配置 prisma.config.ts

Prisma 7 将数据库连接配置放到了 `prisma.config.ts` 中。

打开该文件，配置如下：

```typescript
import "dotenv/config";
import { defineConfig, env } from "prisma/config";

export default defineConfig({
  schema: "prisma/schema.prisma",

  migrations: {
    path: "prisma/migrations",
  },

  datasource: {
    url: env("DATABASE_URL"),
  },
});
```

这里指定了三个重要内容：

- schema：数据库模型文件的位置。
- migrations：数据库迁移文件的位置。
- datasource：数据库连接地址。

第一行 `import "dotenv/config"` 很关键：Prisma 7 不会自动读取 `.env` 文件，如果缺少这一行，执行 `prisma migrate dev` 时会提示找不到 `DATABASE_URL`。有的版本的 `init` 会自动生成这一行，有则保留，没有就手动补上。

与一些旧版本 Prisma 不同，Prisma 7 不再把数据库连接 URL 写在 schema.prisma 的 datasource 配置块中。

### 5. 配置 schema.prisma

打开：

```text
prisma/schema.prisma
```

配置：

```prisma
generator client {
  provider = "prisma-client"
  output   = "../app/generated/prisma"
}

datasource db {
  provider = "postgresql"
}
```

如果 `init` 生成的 generator 里 provider 是旧的 `prisma-client-js`，或者没有 `output`，请按上面的内容修改。

这里暂时只定义 Prisma Client 的生成位置和数据库类型。

我们把生成的客户端统一放在：

```text
app/generated/prisma
```

这样后续业务代码就可以统一从这个位置导入数据库客户端。

这个目录是由 `prisma generate` 自动生成的，不需要手动修改，也可以考虑把 `/app/generated/prisma` 加入 `.gitignore`，换电脑或在 CI 中重新生成即可。

## 七、建立第一个数据模型

开发环境搭建好之后，我们需要验证 Prisma 是否真的能够创建数据库表。

这次不提前把整个英语教学平台的所有数据表都写出来，而是先建立一个最基础的用户模型。

因为无论老板、教务、管理员、教师、家长还是代理，都需要通过用户账号进入系统。

打开 `prisma/schema.prisma`，添加：

```prisma
model User {
  id           String   @id @default(uuid())
  username     String   @unique
  passwordHash String
  phone        String?
  status       String   @default("ACTIVE")
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt
}
```

这个模型暂时只包含最基本的账号信息。

字段含义：

| 字段 | 含义 |
| --- | --- |
| id | 用户唯一标识 |
| username | 登录账号 |
| passwordHash | 密码哈希 |
| phone | 手机号 |
| status | 账号状态 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |

这里使用 UUID 作为主键，username 设置唯一约束，避免出现重复登录账号。

需要注意，passwordHash 保存的是经过安全哈希处理后的密码，绝不能直接保存明文密码。

这只是为了验证数据库环境而建立的第一个模型。后续我们会继续完善用户、角色、权限和人员档案之间的关系。

## 八、执行数据库迁移

数据模型定义完成后，需要把它真正同步到 PostgreSQL。

首先生成 Prisma Client：

```bash
pnpm prisma generate
```

成功后，项目中会出现 `app/generated/prisma` 目录。

然后执行数据库迁移：

```bash
pnpm prisma migrate dev --name init
```

执行成功后，会发生两件事情：

第一，Prisma 根据 schema.prisma 中的模型生成 SQL 迁移文件。

第二，Prisma 将迁移应用到 PostgreSQL，真正创建 User 数据表。

项目中会出现：

```text
prisma/
├── schema.prisma
└── migrations/
    └── 迁移时间_init/
        └── migration.sql
```

这就是数据库迁移机制。

以后我们增加角色表、权限表、学员表或者课程表，都可以通过修改 schema.prisma，再执行 Migration 来管理数据库结构。

这样数据库结构就不再依赖人工手动创建，而是可以随着项目代码一起进行版本管理。

## 九、在 Next.js 中封装数据库连接

Prisma 已经能够连接数据库了，但我们不应该在每个页面中都重复创建 PrismaClient。

应该统一封装数据库连接。

创建目录：

```text
lib/
└── db.ts
```

在 `lib/db.ts` 中编写：

```typescript
import { PrismaPg } from "@prisma/adapter-pg";
import { PrismaClient } from "@/app/generated/prisma/client";

const connectionString = process.env.DATABASE_URL;

if (!connectionString) {
  throw new Error("DATABASE_URL 环境变量未配置");
}

const adapter = new PrismaPg({
  connectionString,
});

const globalForPrisma = globalThis as unknown as {
  prisma: PrismaClient | undefined;
};

export const db =
  globalForPrisma.prisma ??
  new PrismaClient({
    adapter,
  });

if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = db;
}
```

这里有几个值得注意的地方。

**第一，统一数据库访问入口。**

后续所有业务模块都通过 `db` 访问数据库，而不是各自创建数据库连接。

**第二，使用全局变量缓存 PrismaClient。**

Next.js 开发环境中，代码会频繁热更新。

如果每次热更新都重新创建数据库客户端，就可能产生大量数据库连接。

通过 globalThis 缓存，可以避免开发过程中重复创建客户端。

**第三，使用 PostgreSQL Driver Adapter。**

Prisma 7 通过 PrismaPg 适配器连接 PostgreSQL。

这里不再使用旧版本教程中常见的直接 `new PrismaClient()` 写法。

**第四，`DATABASE_URL` 由 Next.js 自动读取。**

`prisma.config.ts` 中需要 `dotenv/config`，是因为 Prisma 命令行不会自动加载 `.env`；而 `lib/db.ts` 运行在 Next.js 中，Next.js 会自动加载 `.env`，所以这里不需要额外引入 dotenv。

## 十二、常见问题排查

按照教程操作时，下面几个问题最容易遇到。

**1. 提示 `Ignored build scripts: esbuild...`**

这是 pnpm 的安全机制，不是错误。执行 `pnpm approve-builds`，勾选需要运行脚本的依赖并确认即可。

**2. `pnpm prisma --version` 显示的是 8.0.0-rc.xx**

说明装成了 Prisma 8 候选版本。请按第六章的方法卸载后，重新安装 `prisma@7`、`@prisma/client@7`、`@prisma/adapter-pg@7`。

**3. `prisma init` 报 `No flag registered for --datasource-provider`**

新版本 CLI 不再支持这个参数，直接执行 `pnpm prisma init` 即可。

**4. `prisma -v` 报 `No command registered for -v`**

新版本 CLI 不再支持 `-v`，改用 `pnpm prisma --version`。

**5. `init` 之后只生成了 `prisma.config.ts`，没有 `prisma/` 和 `.env`**

手动创建 `prisma/schema.prisma` 和 `.env` 即可，内容见第六章。同时先用 `pnpm prisma --version` 确认没有装成 Prisma 8。

**6. 执行迁移时提示找不到 `DATABASE_URL`**

依次检查：`.env` 是否在项目根目录、变量名是否是 `DATABASE_URL`、`prisma.config.ts` 第一行是否有 `import "dotenv/config"`、是否已经安装 `dotenv`。

**7. 迁移时提示数据库认证失败，或无法连接**

依次检查：PostgreSQL 服务是否已启动、用户名和密码是否正确、密码中的特殊字符是否做了 URL 编码、数据库 `learnenglish` 是否已经创建、端口是否是 5432。

**8. 页面提示 `Cannot find module '@/app/generated/prisma/client'`**

说明还没有生成 Prisma Client，或者 `output` 路径与导入路径不一致。重新执行 `pnpm prisma generate`，并确认 `schema.prisma` 中的 `output` 是 `../app/generated/prisma`。
