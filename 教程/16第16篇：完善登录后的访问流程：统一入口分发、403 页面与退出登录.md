# 第16篇：完善登录后的访问流程：统一入口分发、403 页面与退出登录

上一节完成了权限目录、超级管理员、角色授权和后台菜单权限控制。

现在访问 `/admin/users`，如果当前账号没有对应权限，系统会跳转到 `/forbidden`。

权限拦截已经生效，但整个访问流程还不完整：

- 访问 `/`，仍然显示默认开发首页。
- 登录成功后，固定跳转 `/admin/users`。
- 无权限时只能返回首页，但首页没有权限管理。
- 403 页面没有退出登录入口。

本篇把认证、入口分发、页面授权和退出登录串成一条完整链路：

```text
登录认证 → 身份识别 → 门户分发 → 入口授权 → 页面授权 → 退出登录
```

## 一、先明确完整访问流程

```text
访问网站 /
    │
    ▼
检查当前登录状态
    │
    ├── 未登录 ──────→ /login
    │
    └── 已登录
          │
          ▼
      判断入口权限
          │
          ├── portal.admin ──→ /admin
          │
          ├── portal.parent ─→ /parent
          │
          └── 无入口权限 ────→ /forbidden
```

进入后台之后：

```text
/admin
   │
   ▼
后台统一布局（校验 portal.admin）
   │
   ▼
加载当前用户有权访问的菜单
   │
   ▼
访问具体业务页面
   │
   ▼
检查页面权限
   │
   ├── 有权限 ──→ 正常显示
   │
   └── 无权限 ──→ /forbidden
```

这里有三个不同层次：

- `portal.admin`：是否可以进入统一后台。
- `portal.parent`：是否可以进入家长端。
- `user.view`、`role.view` 等：是否可以使用具体功能。

不能把这三种权限混在一起。

## 二、先说明角色：`SUPER_ADMIN` 是第七个内置角色

本篇会出现 `SUPER_ADMIN`，这里先澄清，避免和第十五篇的 `ADMIN` 混淆。

项目的内置角色一共七个，全部由种子脚本写入：

| 角色编码 | 名称 | 说明 |
|---|---|---|
| `SUPER_ADMIN` | 超级管理员 | 系统内置，负责系统配置，不承担业务操作 |
| `BOSS` | 企业负责人 | 查看经营数据与整体运营 |
| `ACADEMIC` | 教务管理 | 负责学生、课程和教学安排 |
| `ADMIN` | 系统管理员 | 负责系统配置和角色权限管理 |
| `TEACHER` | 教师 | 负责授课和学习记录 |
| `AGENT` | 代理/合作方 | 负责招生渠道与线索报备 |
| `PARENT` | 家长 | 查看孩子学习情况和课程报告 |

`SUPER_ADMIN` 和 `ADMIN` 的区别不在名称，而在授权方式：

| | `SUPER_ADMIN` | `ADMIN` |
|---|---|---|
| SYSTEM 权限 | 身份内置放行，不写入 `RolePermission` | 必须通过角色权限页显式分配 |
| 授权来源 | `evaluatePermission` 中的超级管理员规则 | `RolePermission` 表 |
| 是否可在权限页分配 | 否（`isSystem` 角色） | 是 |
| 创建方式 | `pnpm db:seed:superadmin`，只允许一个入口账号 | `pnpm db:seed` / 后台新建用户 |

`DEFAULT_ROLE_GRANTS` 里 `ADMIN` 默认只获得 `portal.admin`，所以：

- `SUPER_ADMIN` 登录后能看到用户管理、角色管理菜单。
- `ADMIN` 登录后能进入后台，但菜单为空，除非另行分配 `user.view`、`role.view`。

这是故意的设计：`ADMIN` 是一个普通角色，不再是"自动拥有全部系统权限"的隐式特权角色。

## 三、建立统一入口分发服务

新增 `lib/auth/portal-routing.ts`：

```ts
import { evaluatePermission } from "./authorization";

import type { CurrentActor } from "./authorization";

/**
 * 根据当前用户的有效入口权限决定默认访问地址。
 *
 * 同时拥有两个入口时，优先进入统一后台。
 */
export function getPortalDestination(
  actor: CurrentActor
): "/admin" | "/parent" | null {
  if (evaluatePermission("portal.admin", actor).allowed) {
    return "/admin";
  }

  if (evaluatePermission("portal.parent", actor).allowed) {
    return "/parent";
  }

  return null;
}
```

这里不直接判断角色编码：

```ts
// 反面示例
if (actor.activeRoleCodes.includes("ADMIN")) {
  return "/admin";
}
```

原因有两个：

- 用户可能拥有多个角色。
- 角色本身不等于入口权限，角色只是授权的载体。

统一通过 `portal.admin` 和 `portal.parent` 判断，以后新增角色时不需要修改入口分发逻辑。

## 四、把根路径 `/` 改造成入口分发器

修改 `app/page.tsx`，原来的默认开发首页不再承担应用入口职责：

```tsx
import { redirect } from "next/navigation";

import { getCurrentActor } from "@/lib/auth/current-actor";
import { getPortalDestination } from "@/lib/auth/portal-routing";

// 读取会话属于请求时数据，允许阻塞首个响应
export const instant = false;

export default async function HomePage() {
  const actor = await getCurrentActor();

  // 未登录或者用户已经被禁用
  if (!actor) {
    redirect("/login");
  }

  const destination = getPortalDestination(actor);

  // 已登录，但没有任何可用入口
  if (!destination) {
    redirect("/forbidden");
  }

  redirect(destination);
}
```

现在 `/` 不再渲染业务内容，只根据当前登录身份决定去哪里：

| 当前身份 | 访问 `/` |
|---|---|
| `SUPER_ADMIN` | `/admin` |
| `BOSS` | `/admin` |
| `ACADEMIC` | `/admin` |
| `ADMIN` | `/admin` |
| `TEACHER` | `/admin` |
| `AGENT` | `/admin` |
| `PARENT` | `/parent` |
| 已登录但无入口权限 | `/forbidden` |
| 未登录 | `/login` |

### 4.1 `instant = false` 必须逐个路由声明

项目开启了 Cache Components。读取会话属于请求时数据，用到的页面和布局必须显式声明：

```ts
export const instant = false;
```

本篇涉及的四个路由都要写，缺一个构建就会报错：

| 文件 | 原因 |
|---|---|
| `app/page.tsx` | 读会话后做分发 |
| `app/(auth)/login/page.tsx` | 从同步页面变成了 `await getCurrentActor()` |
| `app/forbidden/page.tsx` | 读会话判断入口 |
| `app/(dashboard)/admin/page.tsx` | 读会话过滤快捷入口 |
| `app/(parent)/parent/layout.tsx` | 读会话校验 `portal.parent` |

注意：`instant = false` 只豁免导出它的那一段。父布局写了不能覆盖子路由，子路由仍然要按自己的配置单独验证。这类问题只有 `pnpm build` 才会暴露，所以构建必须进入验证清单。

## 五、增加真正的后台首页 `/admin`

新增 `app/(dashboard)/admin/page.tsx`：

```tsx
import Link from "next/link";
import { redirect } from "next/navigation";

import { adminMenus } from "@/components/layout/menu-config";
import { PageHeader } from "@/components/shared/page-header";
import { evaluatePermission } from "@/lib/auth/authorization";
import { getCurrentActor } from "@/lib/auth/current-actor";

export const instant = false;

export default async function AdminHomePage() {
  const actor = await getCurrentActor();

  if (!actor) {
    redirect("/login");
  }

  const items = adminMenus.flatMap((group) =>
    group.items
      .filter((item) => evaluatePermission(item.permission, actor).allowed)
      .map((item) => ({
        ...item,
        group: group.title,
      }))
  );

  return (
    <div className="space-y-6">
      <PageHeader
        title="后台工作台"
        description={`欢迎回来，${actor.name}`}
      />

      {items.length > 0 ? (
        <div className="grid gap-4 sm:grid-cols-2 lg:grid-cols-3">
          {items.map((item) => (
            <Link
              key={item.href}
              href={item.href}
              className="rounded-lg border bg-card p-5 transition-colors hover:bg-accent"
            >
              <div className="font-medium">{item.title}</div>
              <div className="mt-2 text-sm text-muted-foreground">
                {item.group}
              </div>
            </Link>
          ))}
        </div>
      ) : (
        <div className="rounded-lg border bg-card p-6 text-sm text-muted-foreground">
          当前账号尚未获得具体功能权限，请联系超级管理员配置。
        </div>
      )}
    </div>
  );
}
```

三个细节：

1. **`/admin` 只要求 `portal.admin`。** 它是统一后台的入口，不代表可以访问所有业务功能，快捷入口仍然按具体权限过滤。
2. **没有功能权限也能进入。** 只拿到 `portal.admin` 的账号会看到明确提示，而不是被踢到 403 页面。
3. **外层用 `<div>` 而不是 `<main>`。** 后台布局已经提供了主内容区，页面再套 `main` 会产生嵌套。同时统一使用 `PageHeader`，与其他后台页面保持一致。

另外，`adminMenus` 只收录已经实现的页面（当前是用户管理和角色管理），避免快捷入口点进去是 404。以后每完成一个模块再加菜单项。

## 七、统一权限判断结构

第十五篇的 `PermissionDecision` 是可选字段结构，调用方需要额外判断 `!decision.actor`。本篇改成判别联合，让类型系统自己保证：

```ts
export type PermissionDenialCode = "UNAUTHENTICATED" | "FORBIDDEN";

/**
 * allowed 为 true 时一定有 actor 和 scopes；
 * allowed 为 false 时一定有拒绝原因 code。
 */
export type PermissionDecision =
  | {
      allowed: true;
      actor: CurrentActor;
      scopes: DataScope[];
    }
  | {
      allowed: false;
      code: PermissionDenialCode;
      actor: CurrentActor | null;
    };
```

对应地，`evaluatePermission` 和 `checkPermission` 的拒绝分支改为：

```ts
return {
  allowed: false,
  code: "FORBIDDEN",
  actor,
};
```

```ts
return {
  allowed: false,
  code: "UNAUTHENTICATED",
  actor: null,
};
```

好处是调用方写 `if (!decision.allowed)` 之后，`decision.actor` 自动收窄为 `CurrentActor`，不再需要 `!decision.actor` 这类多余判断，也不会出现"放行但 actor 为空"的中间状态。

测试里同样不要用 `expect(decision.allowed).toBe(true)` 之后直接访问 `decision.scopes`，类型不会因为断言而收窄。写一个小助手：

```ts
function expectAllowed(decision: PermissionDecision) {
  expect(decision.allowed).toBe(true);

  if (!decision.allowed) {
    throw new Error(`期望放行，实际被拒绝：${decision.code}`);
  }

  return decision;
}
```

## 八、统一页面权限守卫

`lib/auth/authorization.ts` 中的 `requirePagePermission` 改为统一跳转：

```ts
/**
 * 页面权限守卫：未登录跳转登录页，无权限统一跳转 403 页面。
 *
 * 只能用于页面和布局，不能用于 Server Action 或 Service：
 * 这里通过 redirect 抛异常改变导航，在 Action 中会中断返回值。
 */
export async function requirePagePermission(
  permissionCode: PermissionCode
): Promise<CurrentActor> {
  const decision = await checkPermission(permissionCode);

  if (!decision.allowed) {
    redirect(decision.code === "UNAUTHENTICATED" ? "/login" : "/forbidden");
  }

  return decision.actor;
}
```

这样页面只需要声明自己需要什么权限：

```ts
await requirePagePermission("user.view");
```

## 九、Server Action 必须使用不跳转的守卫

页面守卫只负责页面访问。Service 和 Server Action 仍然必须独立检查权限，因为用户可以绕过前端直接调用服务端操作。

但 **Server Action 不能直接调用 `requirePagePermission`**：

- 它内部用 `redirect()` 抛异常改变导航。
- 在 Action 里抛出跳转，会中断正常的返回值，客户端拿不到 `{ success: false }`，toast 流程失效。

因此新增一个不跳转的守卫：

```ts
export type ActionPermissionResult =
  | { ok: true; actor: CurrentActor; scopes: DataScope[] }
  | { ok: false; message: string };

/**
 * Server Action / Service 的权限守卫：不跳转，返回结构化失败结果。
 */
export async function requireActionPermission(
  permissionCode: PermissionCode
): Promise<ActionPermissionResult> {
  const decision = await checkPermission(permissionCode);

  if (!decision.allowed) {
    return {
      ok: false,
      message:
        decision.code === "UNAUTHENTICATED"
          ? "登录状态已失效，请重新登录"
          : "当前账号没有执行该操作的权限",
    };
  }

  return {
    ok: true,
    actor: decision.actor,
    scopes: decision.scopes,
  };
}
```

Action 的写法：

```ts
export async function setUserStatusAction(
  userId: string,
  status: UserStatus
): Promise<UserActionResult> {
  const guard = await requireActionPermission("user.disable");

  if (!guard.ok) {
    return { success: false, message: guard.message };
  }

  // 后续业务逻辑
}
```

两种守卫的分工：

| 守卫 | 使用位置 | 失败行为 |
|---|---|---|
| `requirePagePermission` | 页面、布局 | `redirect()` 跳转 |
| `requireActionPermission` | Server Action、Service | 返回 `{ ok: false, message }` |

## 十、修复登录成功后的跳转

这里有两处需要一起改，只改一处仍然会把所有人送到用户管理页。

### 10.1 去掉 `callbackURL`

如果登录调用里带了固定回调地址：

```ts
// 错误写法
await authClient.signIn.username({
  username,
  password,
  callbackURL: "/admin/users",
});
```

Better Auth 客户端在登录成功后会按 `callbackURL` 跳转。这样所有人仍然会被送到 `/admin/users`：

- 家长先落到后台，再被布局踢到 403。
- 普通角色登录后直接看到无权限页面。

必须删除 `callbackURL`，把跳转交给后面的 `router.replace("/")`：

```ts
const result = await authClient.signIn.username({
  username,
  password,
});
```

### 10.2 登录成功后统一进入 `/`

`features/auth/components/login-form.tsx`：

```ts
// 登录成功后统一进入根路径，由服务端入口分发器决定进入哪个门户
router.replace("/");
router.refresh();
```

这样以后增加新角色，不需要再修改登录组件。

### 10.3 已登录用户访问登录页

修改 `app/(auth)/login/page.tsx`：

```tsx

  return (
    <main className="flex min-h-screen items-center justify-center bg-background p-6">
      <div className="w-full max-w-md space-y-8 rounded-xl border bg-card p-8 shadow-sm">
        <div className="space-y-2 text-center">
          <h1 className="text-2xl font-bold">启航英语</h1>
          <p className="text-sm text-muted-foreground">教学管理平台</p>
        </div>

        <LoginForm />
      </div>
    </main>
  );
}
```

已经登录的用户访问 `/login`，会自动进入自己的门户。

## 十一、重做 403 无权限页面

403 页面不能简单提供一个返回 `/` 的链接。

因为用户可能根本没有任何门户权限，返回 `/` 后又会重新跳回 `/forbidden`，形成死循环。

正确做法是根据用户实际拥有的入口权限，决定是否显示返回按钮：

```tsx
import Link from "next/link";
import { redirect } from "next/navigation";

import { SignOutButton } from "@/components/layout/sign-out-button";
import { buttonVariants } from "@/components/ui/button";
import { getCurrentActor } from "@/lib/auth/current-actor";
import { getPortalDestination } from "@/lib/auth/portal-routing";

export const metadata = {
  title: "无权访问",
};

export const instant = false;

export default async function ForbiddenPage() {
  const actor = await getCurrentActor();

  if (!actor) {
    redirect("/login");
  }

  const destination = getPortalDestination(actor);

  return (
    <main className="flex min-h-screen items-center justify-center bg-background p-6">
      <div className="w-full max-w-md space-y-5 rounded-xl border bg-card p-8 text-center shadow-sm">
        <h1 className="text-2xl font-bold">无权访问</h1>

        <p className="text-sm text-muted-foreground">
          当前账号没有访问该页面的权限，请联系超级管理员。
        </p>

        {destination ? (
          <Link href={destination} className={buttonVariants()}>
            返回可访问工作台
          </Link>
        ) : (
          <p className="text-sm text-muted-foreground">
            当前账号没有已授权的系统入口。
          </p>
        )}

        <div className="flex justify-center">
          <SignOutButton showLabel />
        </div>
      </div>
    </main>
  );
}
```

现在出现 403 时：

- 有后台入口权限：返回 `/admin`。
- 只有家长端入口权限：返回 `/parent`。
- 两个入口都没有：不显示返回按钮，只提示"没有已授权的系统入口"。
- 无论哪种情况，都可以退出登录。

按钮统一使用 `buttonVariants()`，不再手写一长串 `inline-flex h-10 ...` 样式，避免和项目里其他按钮不一致。

### 11.1 关于"跳转 403"和真实 403 状态码的取舍

当前实现是 `redirect("/forbidden")`：

- 浏览器地址会变成 `/forbidden`。
- 页面响应状态码是 200，不是 403。
- 原始访问地址丢失。

Next.js 提供 `forbidden()` 可以在原地址返回 403 状态码，但需要开启实验性开关 `experimental.authInterrupts`，第十五篇已经说明。

两种方案没有绝对对错：

| 方案 | 优点 | 代价 |
|---|---|---|
| `redirect("/forbidden")` | 稳定、可自定义页面、不依赖实验特性 | URL 变为 `/forbidden`，状态码 200 |
| `forbidden()` | 保留原地址，语义正确的 403 | 实验特性，可用渠道受限 |

本篇选择前者。需要说明的是：**这个页面叫 403 页面，但它的 HTTP 状态码仍然是 200。** 如果项目后续对 SEO 或监控有严格的状态码要求，再考虑切换到 `forbidden()`。

另外，自己创建的 `app/forbidden/page.tsx` 与框架约定的 `app/forbidden.tsx`（`forbidden()` 的兜底文件）名字很像，容易混淆。如果团队觉得有歧义，可以改名为 `/no-access` 并同步修改守卫里的跳转地址，功能不变。

## 十二、完善退出登录按钮

`components/layout/sign-out-button.tsx` 使用 Better Auth 的 `authClient.signOut()`，本篇补两处稳健性：

```tsx
"use client";

import { LogOut } from "lucide-react";
import { useState } from "react";
import { toast } from "sonner";

import { Button } from "@/components/ui/button";
import { authClient } from "@/lib/auth-client";

type Props = {
  showLabel?: boolean;
};

export function SignOutButton({ showLabel = false }: Props) {
  const [loading, setLoading] = useState(false);

  async function handleSignOut() {
    setLoading(true);

    try {
      const result = await authClient.signOut();

      if (result.error) {
        toast.error("退出登录失败，请重试");
        return;
      }

      // 整页跳转而不是 router.replace：
      // 彻底丢弃客户端路由缓存，避免按返回键看到受保护页面的旧内容。
      // eslint-disable-next-line @next/next/no-location-assign-relative-destination
      window.location.assign("/login");
    } catch {
      toast.error("退出登录失败，请检查网络后重试");
    } finally {
      setLoading(false);
    }
  }

  return (
    <Button
      variant="ghost"
      size={showLabel ? "default" : "icon-sm"}
      onClick={handleSignOut}
      disabled={loading}
      aria-label="退出登录"
    >
      <LogOut />
      {showLabel && <span>退出登录</span>}
    </Button>
  );
}
```

两处改进：

1. **补 `catch`。** 网络异常时 `signOut()` 会抛出，原来没有捕获，用户点击后没有任何反馈。
2. **整页跳转 `window.location.assign`。** `router.replace` 加 `router.refresh` 仍可能保留客户端路由缓存，按浏览器返回键存在看到旧页面的可能。整页跳转会重建整个客户端状态。Next.js 的 lint 规则默认建议用 `router`，这里显式关闭该提示并注明原因。

另外确认按钮组件的 `size="icon-sm"` 变体确实存在。项目当前的 `Button` 已包含该尺寸，后台顶栏继续使用图标按钮，403 页面使用 `showLabel` 带文字的按钮。

退出登录必须由 Better Auth 清除服务端会话，不能只通过跳转登录页来模拟退出。

## 十三、自动化测试

`getPortalDestination` 是纯函数，非常适合表驱动测试，能直接验证"停用的角色不给入口"：

```ts
import { DataScope } from "@/app/generated/prisma/client";

import { getPortalDestination } from "./portal-routing";

import type { CurrentActor } from "./authorization";
import type { PermissionCode } from "./permissions";

function createActor(permissionCodes: PermissionCode[]): CurrentActor {
  return {
    userId: "user-1",
    name: "测试用户",
    email: "user@example.com",
    isActive: true,
    roleCodes: [],
    activeRoleCodes: [],
    grants: permissionCodes.map((code) => ({
      permissionCode: code,
      scope: DataScope.ALL,
    })),
  };
}

describe("getPortalDestination", () => {
  it.each<{
    label: string;
    grants: PermissionCode[];
    expected: "/admin" | "/parent" | null;
  }>([
    { label: "只有后台入口", grants: ["portal.admin"], expected: "/admin" },
    { label: "只有家长端入口", grants: ["portal.parent"], expected: "/parent" },
    {
      label: "同时拥有两个入口",
      grants: ["portal.admin", "portal.parent"],
      expected: "/admin",
    },
    {
      label: "只有业务权限、没有入口权限",
      grants: ["student.view"],
      expected: null,
    },
    { label: "没有任何授权", grants: [], expected: null },
  ])("$label 时分发到 $expected", ({ grants, expected }) => {
    expect(getPortalDestination(createActor(grants))).toBe(expected);
  });

  it("角色被停用后授权不再生效，无法进入任何门户", () => {
    const actor: CurrentActor = {
      ...createActor([]),
      roleCodes: ["PARENT"],
      activeRoleCodes: [],
    };

    expect(getPortalDestination(actor)).toBeNull();
  });
});
```

停用账号的过滤发生在 `getCurrentActor` 阶段：只有启用角色的授权才会进入 `actor.grants`，所以分发函数不需要重复判断角色状态。

## 十五、后续优化

### 15.1 登录后回到原来的目标页面

当前未登录访问 `/admin/users/xxx/edit`，登录后只会进入 `/`，再分发到 `/admin`，原始目的地丢失。

后续可以用 `callbackUrl` 参数携带目标地址，但必须校验：

- 必须以 `/` 开头。
- 不能以 `//` 开头（协议相对地址）。
- 最好只允许白名单前缀，例如 `/admin`。

否则会产生开放重定向漏洞。

### 15.2 门户切换入口

同时拥有后台和家长端权限时，本篇固定优先进入后台。教师身份的家长就永远到不了家长端。

后续可以在顶栏增加"切换门户"按钮，调用 `getPortalDestination` 的另一分支实现。当前先保持简单。

## 十六、本篇完成后的整体流程

```text
                  用户访问网站
                       │
                       ▼
                    根路径 /
                       │
                 获取 CurrentActor
                       │
            ┌──────────┴──────────┐
            │                     │
          未登录                已登录
            │                     │
            ▼                     ▼
         /login              判断入口权限
                                  │
                     ┌────────────┼────────────┐
                     │            │            │
                 portal.admin portal.parent   无权限
                     │            │            │
                     ▼            ▼            ▼
                  /admin       /parent      /forbidden
                     │            │            │
                     ▼            ▼            ├── 返回可访问入口
                  后台布局      家长布局       └── 退出登录
                     │
                     ▼
                 页面权限检查
                     │
              ┌──────┴──────┐
              │             │
            通过          不通过
              │             │
              ▼             ▼
           业务页面       /forbidden
```

本篇完成之后，系统不再只是保护几个后台页面，而是有了一条完整的访问链路：

**登录认证 → 身份识别 → 门户分发 → 入口授权 → 页面授权 → 退出登录。**

后续新增业务模块时，只需要继续声明对应的页面权限和操作权限，不需要重新设计整个登录访问流程。
