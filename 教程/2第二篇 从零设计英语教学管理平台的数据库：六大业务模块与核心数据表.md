# 从零设计英语教学管理平台的数据库：六大业务模块与核心数据表

> **修订说明**：本文已与第一篇的产品规划逐项对照。相比初版，主要改动有：补充了「教师接单」相关数据表；课时账户增加「课时批次」以支持有效期；课程区分「计划」与「实际教学记录」，并区分计划教师与实际授课教师；客户归属不再只限于代理；补充客户成交后到家长、学员的转化关系；新增「学员单词掌握状态」表；补充内部员工档案；明确单机构前提、命名约定和分期建表。

上一篇文章，我们介绍了准备研发的英语教学管理平台。

这是一款面向中小型英语培训机构的软件，涉及老板、教务、管理员、教师、家长和代理六种角色，覆盖客户开发、学员报名、教师管理、课程排课、教学训练、学习报告、课时管理和教师结算等业务。

当我们准备真正开发这款软件时，首先要解决一个问题：

**这么多角色、这么多业务，数据库应该如何设计？**

如果只是开发一个简单的信息管理系统，可能只需要用户表、商品表、订单表，就能完成基本的增删改查。

但真实业务系统远没有这么简单。

例如，一名学员可能有多个家长，一名教师可能负责多个学员，一名学员可能购买多次课程，每次课程又会产生教学记录、学习报告和课时扣减记录。

这些数据之间存在复杂的关联。

如果数据库设计不合理，后续开发就会不断出现重复数据、数据不一致、业务关系混乱等问题。

这篇文章，我们就从实际业务出发，设计这款英语教学管理平台的数据库。

## 一、先确定数据库设计的整体思路

数据库设计不是看到一个页面，就创建一张表。

正确的做法应该是先分析业务，再识别业务对象，最后确定数据之间的关系。

例如，机构有一个学员管理页面。

这个页面展示学员姓名、年级、联系方式、负责教师、剩余课时等信息。

但这些信息实际上来自不同的业务对象：

- 学员姓名、年级属于学员档案。
- 家长联系方式属于家长档案。
- 负责教师属于教师与学员之间的业务关系。
- 剩余课时属于学员课时账户。
- 课程安排属于排课业务。

如果把这些信息全部放在一张 Student 表里，刚开始开发似乎很方便，但随着业务增加，就会产生大量冗余。

因此，我们先把整个系统划分为六个业务模块。

| 业务模块 | 核心业务 | 主要数据对象 |
| --- | --- | --- |
| 系统基础管理 | 账号、角色、权限、机构配置 | 用户、角色、权限、员工档案 |
| 招生与客户管理 | 客户线索、跟进、代理、报名、订单 | 客户、跟进记录、报名、订单 |
| 学员与教师管理 | 学员档案、教师档案、接单与师生关系 | 学员、教师、授课需求、关系记录 |
| 教学与课程管理 | 排课、授课、训练、复习、报告 | 课程、训练任务、掌握状态 |
| 课时与财务管理 | 课时批次、课时流水、教师结算 | 课时批次、流水、结算单 |
| 家长服务 | 家长账号、课程记录、学习反馈 | 家长、家长学员关系 |

这里需要特别注意：

这六个模块是按照业务职责划分的，并不意味着每个模块只能使用自己的数据表。

例如，教师授课会涉及教师表、学员表、课程表、教学记录表和课时流水表。

真正的业务系统，往往是多个模块共同维护一条业务链。

### 动手建表之前，先定下四个前提

**1. 单机构还是多机构？**

这是越早决定越好的架构问题。如果将来要把系统卖给多家机构，每张业务表都需要增加机构标识（例如 organizationId），所有查询都要带上机构条件，后期再补会非常痛苦。

本系列的前提是：**先服务一家机构**，机构信息放在系统配置中，业务表不增加机构标识。如果你的产品目标是多机构 SaaS，需要在设计阶段就为所有业务表加上机构维度。

**2. 命名约定**

文章中的表名使用下划线加复数形式（例如 `teacher_students`），这是数据库里的实际表名。在 Prisma 中，模型名使用大驼峰单数（例如 `TeacherStudent`），再通过 `@@map("teacher_students")` 映射到实际表名。上一篇创建的 `User` 模型对应的就是 `users` 表。

**3. 主键、金额与时间**

主键统一使用 UUID；金额统一使用整数「分」保存，或使用 Decimal，不使用浮点数；时间统一保存为带时区的时间，展示时再转换。

**4. 不要一次建完所有表**

下面的设计是完整蓝图，但开发时应该按阶段推进：

| 阶段 | 内容 | 对应模块 |
| --- | --- | --- |
| 第一期 | 账号权限、学员、家长、教师、排课、课程、课时 | 基础管理、学员教师、课程基础、课时 |
| 第二期 | 词库、训练、复习、学习报告、家长端 | 教学训练、家长服务 |
| 第三期 | 客户招生、代理、订单收款、教师结算 | 招生、财务 |

## 二、系统基础管理：解决谁能登录、谁能操作的问题

任何一个管理系统，都需要统一的账号管理和权限控制。

这里首先要区分两个概念：

**用户账号不等于业务人员档案。**

例如：

- 教师有自己的教师档案，也需要一个登录账号。
- 家长有自己的家长档案，也需要一个登录账号。
- 代理有自己的代理档案，也需要一个登录账号。
- 老板、教务、管理员这类内部员工，同样需要员工档案。

如果直接把教师信息、家长信息和账号信息混在一起，后续账号停用、人员离职、重新合作时，就很难维护。

因此，系统基础管理建议设计以下数据表。

| 数据表 | 主要用途 |
| --- | --- |
| users | 系统登录账号 |
| roles | 系统角色 |
| permissions | 系统权限 |
| user\_roles | 用户与角色关联 |
| role\_permissions | 角色与权限关联 |
| staff\_profiles | 内部员工档案（老板、教务、管理员） |
| departments | 机构部门或组织结构 |
| system\_settings | 系统配置与机构基本信息 |
| audit\_logs | 重要操作审计记录 |
| notifications | 系统消息通知 |

### 1. 用户表 users

保存所有能够登录系统的账号信息。

核心字段：

- id：用户主键
- username：登录账号
- passwordHash：密码哈希
- phone：手机号
- status：账号状态
- lastLoginAt：最后登录时间
- createdAt：创建时间

这里不直接放教师姓名、家长孩子信息等业务字段。

### 2. 角色与权限

系统有六种主要角色：

- 老板
- 教务
- 管理员
- 教师
- 家长
- 代理

但角色与权限不应该简单地写死在代码里。

建议使用三张表：

- roles：定义角色。
- permissions：定义系统操作权限。
- role\_permissions：定义角色可以执行哪些操作。

例如，教师可以查看自己的课程、提交教学记录；家长可以查看孩子的学习报告；代理可以录入自己开发的客户。

除了功能权限，还需要控制数据范围。

例如，教师只能查看自己负责的学员，家长只能查看与自己建立关联的孩子，代理只能查看授权范围内的客户。

因此，权限控制不能只依赖前端是否显示按钮，还必须在服务端进行验证。

### 3. 人员档案与账号关联

建议将业务人员档案独立设计：

| 数据表 | 主要用途 |
| --- | --- |
| staff\_profiles | 内部员工档案（姓名、部门、岗位） |
| teachers | 教师档案 |
| parents | 家长档案 |
| agents | 代理档案 |

这些档案通过 userId 与 users 建立关联。

这样即使一个教师暂时停止合作，也可以停用账号、保留教师档案和历史授课记录。

如果未来重新合作，也不需要重新创建一个教师身份。

## 三、招生与客户管理：记录客户从哪里来、如何成交

招生业务的核心不是简单地记录一个家长的手机号，而是完整记录客户从产生意向到报名成交的过程。

建议设计以下数据表：

| 数据表 | 主要用途 |
| --- | --- |
| customers | 客户线索 |
| customer\_follow\_ups | 客户跟进记录 |
| customer\_assignments | 客户分配及归属变更记录 |
| registrations | 学员报名记录 |
| course\_packages | 可售课程包 |
| orders | 课程购买订单 |
| order\_items | 订单明细（购买了哪些课程包） |
| payments | 实际收款记录 |

### 1. 客户表 customers

保存潜在客户的基本信息。

主要字段：

- id：客户 ID
- name：客户联系人姓名
- phone：联系电话
- sourceType：来源渠道类型，例如代理、机构自建、转介绍
- sourceAgentId：最初获客代理（来源为代理时才有值）
- ownerUserId：当前负责跟进的账号
- status：客户状态
- createdAt：创建时间

这里有两个容易忽略的问题：

**第一，客户不一定来自代理。**

第一篇说过，客户可能来自不同代理，也可能由机构自己开发。因此不能把负责人字段设计成只能指向代理。负责人统一指向 users：可能是代理的账号，也可能是教务或老板的账号。代理只是来源渠道的一种。

**第二，最初获客的人，不一定是最后成交的人，也不一定是当前维护客户的人。**

例如，客户最初由代理 A 开发，后来转交给代理 B 维护，最终由机构内部人员完成报名。

如果只在客户表中保存一个负责人字段，就无法完整记录客户归属的变化。

因此，需要通过 customer\_assignments 记录客户归属和负责人变更历史：谁在什么时间转给了谁，原因是什么。

### 2. 客户跟进记录 customer\_follow\_ups

客户从第一次接触到最终报名，可能经历多次沟通。

每次沟通都应该形成独立记录。

主要字段：

- customerId：所属客户
- followUpUserId：跟进人员
- content：沟通内容
- followUpType：沟通方式
- nextFollowUpAt：下次跟进时间
- createdAt：跟进时间

这样就能还原客户的整个跟进过程。

### 3. 客户如何变成家长和学员

`customers` 是销售线索，`parents` 是家长档案，`students` 是学员档案。这三者是不同的概念，成交时需要明确它们之间如何衔接，否则同一个人会在不同表里重复出现。

建议的处理方式：

1. 客户决定报名时，教务创建一条报名记录 registrations。
2. 报名记录同时关联 customerId（来自哪个线索）、studentId（为哪个孩子报名）、parentId（哪位家长办理）。
3. 如果家长已经存在（例如续费或第二个孩子报名），关联已有家长档案，而不是重新创建；如果是新家长，则创建家长档案并为其开通登录账号。
4. 一个客户可以有多个孩子，也可以为同一个孩子多次报名，因此报名记录不能直接写在客户表里。

### 4. 订单、订单明细与收款

订单表示客户购买了什么，收款表示机构实际收到了多少钱。

订单本身又需要说明购买的是哪种课程。例如机构销售「50 课时正式课包」「10 课时体验包」，这些可售商品保存在 course\_packages 中，订单通过 order\_items 引用课程包，并保存下单时的价格和课时数快照。

例如：

家长购买了一份价值 3000 元的课程订单，可能分两次付款。

那么：

- orders 保存一笔 3000 元的订单。
- order\_items 记录这笔订单买了哪个课程包、多少课时。
- payments 保存两笔实际收款记录。

不能因为创建了订单，就直接认为机构已经收到全部款项。

只有收款确认后，才能按照业务规则为学员增加可用课时。

## 四、学员与教师管理：建立人与人之间的业务关系

这是整个系统最基础、也最容易设计错误的部分。

### 1. 学员表 students

学员是实际接受教学服务的人。

主要字段：

- id：学员 ID
- name：学员姓名
- gender：性别
- grade：年级
- school：学校
- textbook：使用教材
- status：学员状态

这里不直接保存家长手机号，也不直接保存教师姓名。

因为一个学员可能有多个家长，也可能在不同阶段由不同教师负责。

### 2. 家长表 parents

家长是学员的监护人或家庭联系人。

主要字段：

- id：家长 ID
- name：家长姓名
- phone：联系电话
- userId：关联登录账号

### 3. 家长与学员关系表 parent\_students

家长与学员之间不是简单的一对一关系。

例如：

- 一个孩子可以关联爸爸和妈妈。
- 一个家长可以管理多个孩子。
- 多个家庭成员可能共同关注一个孩子。

因此，应该通过中间表建立多对多关系。

主要字段：

- parentId：家长 ID
- studentId：学员 ID
- relationship：关系类型
- isPrimary：是否主要联系人
- createdAt：关联时间

### 4. 教师接单：从授课需求到正式分配

第一篇规划了完整的接单流程：教务发布授课需求，教师响应，教务确认人选，管理员完成正式分配。这个流程本身需要数据表承载，师生关系是它的**结果**，而不是凭空产生的。

| 数据表 | 主要用途 |
| --- | --- |
| teaching\_demands | 授课需求（为哪个学员找教师） |
| teaching\_demand\_responses | 教师对需求的响应 |

**teaching\_demands** 的主要字段：

- studentId：需要授课的学员
- publishedByUserId：发布人（教务）
- gradeRequirement、textbook、timeRequirement：年级、教材和时间要求
- status：需求状态
- selectedTeacherId：教务确认的教师
- assignedByUserId、assignedAt：管理员正式分配的操作人和时间

需求状态建议包含：已发布、待确认、待分配、已分配、已关闭。

**teaching\_demand\_responses** 的主要字段：

- demandId：所属需求
- teacherId：响应的教师
- willing：是否愿意接单
- remark：教师备注
- respondedAt：响应时间

同一教师对同一需求只能响应一次，需要为 demandId 和 teacherId 设置唯一约束。

### 5. 教师与学员关系表 teacher\_students

需求被正式分配后，生成教师与学员的负责关系。

主要字段：

- teacherId：教师 ID
- studentId：学员 ID
- demandId：来源的授课需求
- status：关系状态
- startDate：开始负责日期
- endDate：结束负责日期

为什么不直接在 students 表中增加 teacherId？

因为教师可能负责多个学员，一个学员也可能在不同阶段由不同教师负责。

通过独立关系表，可以保存师生关系的建立、暂停和结束历史。

需要注意，教师与学员关系表示业务上的负责关系，而每一节课程还需要单独保存授课教师。

不能因为后来更换了负责教师，就把历史课程的授课教师一起修改。

## 五、教学与课程管理：系统最核心的业务模块

这部分是整个英语教学管理平台最重要的内容。

机构真正交付给家长的不是一条订单记录，而是持续发生的教学服务。

因此，需要围绕课程、教学任务、训练记录和学习报告建立完整的数据关系。

建议设计以下数据表：

| 数据表 | 主要用途 |
| --- | --- |
| courses | 课程实例（排出来的每一节课） |
| course\_changes | 调课、补课、换教师、取消的变更记录 |
| course\_records | 教师提交的实际教学记录 |
| schedule\_requirements | 学员可上课时间与排课需求 |
| teacher\_availabilities | 教师可授课时间 |
| schedule\_plans | 周期或批量排课计划 |
| wordbooks | 单词词库 |
| words | 基础单词 |
| wordbook\_words | 词库与单词关联 |
| wordbook\_requests | 教师词库申请 |
| student\_wordbooks | 学员词库授权 |
| training\_tasks | 教学训练任务 |
| training\_records | 单词训练记录 |
| articles | 文章资源 |
| article\_sentences | 文章句子 |
| article\_training\_records | 文章训练记录 |
| student\_word\_progress | 学员单词掌握状态 |
| review\_plans | 复习计划 |
| review\_records | 复习记录 |
| course\_reports | 课程学习报告 |

### 1. 课程表 courses：计划与实际要分开

课程是教务管理的核心对象。

每一节课程都应该是一条独立记录。

主要字段：

- id：课程 ID
- studentId：学员 ID
- scheduledTeacherId：排课时指定的计划教师
- actualTeacherId：实际授课教师，课程完成时确认
- courseType：课程类型，例如体验课、正式课
- startTime、endTime：开始和结束时间
- meetingUrl：线上会议地址
- status：课程状态
- schedulePlanId：所属排课计划
- originalCourseId：如果是补课，指向被补的原课程
- createdAt：创建时间

这里有三个要点。

**第一，计划教师和实际教师是两个概念。**

排课时只有计划教师，但实际上可能出现代课、临时换人。如果只有一个 teacherId 字段，就无法区分「安排谁上」和「实际谁上了」，教师课时费也就无法准确核算。教师课时费应该依据实际授课教师计算。

**第二，课程类型和课程状态是两个不同的概念。**

课程类型用于区分体验课和正式课。

课程状态用于表示待上课、已完成、已取消等业务状态。

不能把两者混在一个字段中。

**第三，调课、补课、换教师、取消都要有变更记录。**

不要只修改课程表的时间或状态。每次变更都应该在 course\_changes 中记录：变更类型、变更前的值、变更后的值、变更原因和操作人。这样家长投诉「课怎么变了」时，机构才能查清楚。

### 2. 教学记录 course\_records：课程是计划，记录是事实

courses 保存的是排出来的课程，而 course\_records 保存教师实际完成教学后提交的记录。

主要字段：

- courseId：所属课程（唯一，一节课最多一条教学记录）
- teacherId：提交记录的教师
- content：本次教学内容
- progress：学习进度
- performance：课堂表现
- submittedAt：提交时间

这里需要事先定好一条关键业务规则：**课程什么时候算「完成」，由谁确认？**

建议的流程是：教师提交教学记录，教务确认课程完成。课程被确认完成，才是触发学员扣课时和教师计费的业务事件。这个规则一旦确定，后面的课时流水和教师费用都要围绕它来设计。

### 3. 排课计划

对于培训机构来说，排课不仅有单次安排，还存在大量周期排课。

例如：

某个学员每周一、三、五晚上 19:00 上课，持续三个月。

如果每次都人工创建课程，效率会很低。

因此可以通过 schedule\_plans 保存周期排课规则，再根据规则生成具体课程实例。

同时，学员的可上课时间（schedule\_requirements）和教师的可授课时间（teacher\_availabilities）也需要独立记录。

排课时，系统需要检查：

- 教师是否处于可授课状态。
- 教师在对应时间是否有其他课程。
- 学员在对应时间是否有其他课程。
- 教师是否请假。
- 是否超过教师每日或每周授课负荷。

需要强调，排课计划只是生成课程的依据，真正发生的课程仍然应该保存在 courses 中。

### 4. 词库与单词

单词训练是本系统的重要教学功能。

首先需要区分三个概念：

- Word：一个基础单词。
- Wordbook：一个词库。
- WordbookWord：某个词库包含哪些单词。

为什么需要拆成三张表？

因为同一个单词可能同时出现在多个词库中。

例如，单词 apple 可能出现在人教版三年级词库，也可能出现在自然拼读词库。

如果把单词直接存储在词库表中，就会产生大量重复数据。

因此：

words 保存基础单词信息，wordbooks 保存词库信息，wordbook\_words 负责建立词库和单词之间的多对多关系，词库内的顺序也由它独立维护。

### 5. 学员词库授权

不是所有教师都可以随意使用所有词库。

教师可能需要先为学员申请某个词库，再由管理员审核。

因此，需要区分：

- wordbook\_requests：教师申请记录。
- student\_wordbooks：学员已经获得的词库授权。

申请不等于授权，审核通过后才能正式使用。

这也是一个典型的业务状态流转问题。

### 6. 单词训练记录

单词训练不是简单地把一个单词标记为认识或不认识。

系统需要知道：

- 哪个学员参加了训练？
- 哪位教师组织了训练？
- 本次训练属于哪一节课程？
- 本次训练使用了哪个词库？
- 训练包含哪些单词？
- 每个单词训练了几次？
- 最终掌握情况如何？

因此，训练任务和训练记录需要分开。

training\_tasks 表示一次完整训练任务（并关联到具体课程），training\_records 表示任务中每个单词的实际训练情况。

这样才能支持历史训练查询、学习统计和后续复习安排。

### 7. 学员单词掌握状态 student\_word\_progress

训练记录记录的是「发生过什么」，是一条条历史事件。但复习需要回答的是另一个问题：**这个学员的这个单词，现在掌握到什么程度，下次什么时候该复习？**

这是一份按「学员 + 单词」聚合的当前状态，不能每次都从历史训练记录里重新计算。因此需要独立的 student\_word\_progress 表。

主要字段：

- studentId、wordId：学员和单词（联合唯一）
- status：学习中、已掌握等
- leitnerBox：莱特纳盒子编号
- nextReviewAt：下次复习时间
- firstLearnedAt、lastTrainedAt：首次学习和最近训练时间
- manuallyAdjusted：教师是否手动调整过

训练记录是依据，掌握状态是结果。家长端的「待复习单词」，就是从这张表中查询 nextReviewAt 已到期的记录得到的。

### 8. 复习体系

系统需要记录学生哪些单词还没有掌握，以及下一次什么时候需要复习。

这里需要特别注意：

莱特纳盒子复习法和 21 天记忆法是两套不同的复习机制。

不能把它们简单地设计成一个复习状态字段。

建议保留独立的复习计划（review\_plans）和复习记录（review\_records），并通过复习类型区分不同算法。

莱特纳盒子需要记录单词所在盒子、下次复习时间以及教师手动调整情况。

21 天记忆法则需要记录独立的训练日期、复习阶段和完成情况。

这样才能避免两套复习规则互相覆盖。

### 9. 课程学习报告

每节课程完成后，系统需要形成学习报告。

报告应该关联具体课程，并记录本次教学内容、训练成果、掌握情况和后续学习建议。

家长查看的不是教师随意填写的一段文字，而是能够追溯到实际教学活动的学习结果。

## 六、课时与财务管理：让每一笔钱都有依据

培训机构有两个重要的财务对象：

一个是学员购买的课时，另一个是教师完成课程后应获得的课时费。

这两件事都与课程有关，但不能直接合并。

建议设计以下数据表：

| 数据表 | 主要用途 |
| --- | --- |
| student\_hour\_lots | 学员课时批次（含来源和有效期） |
| student\_hour\_transactions | 学员课时变动流水 |
| student\_hour\_accounts | 学员课时汇总（可选的缓存表） |
| teacher\_pay\_rules | 教师课时费规则 |
| teacher\_lesson\_fees | 单节课程教师费用明细 |
| teacher\_settlements | 教师月度结算单 |
| teacher\_settlement\_items | 结算单明细 |
| teacher\_settlement\_adjustments | 结算调整记录 |
| teacher\_payments | 教师付款记录 |

### 1. 学员课时：批次、流水与余额

第一篇规划了家长端的「课时账户」和「有效期提醒」。要支持有效期，只保存一个余额数字是不够的。

因为不同订单购买的课时，有效期往往不同；赠送课时、补偿课时可能有自己的期限；体验课时和正式课时也可能需要区分。

因此，建议引入**课时批次** student\_hour\_lots：每一次课时的增加，形成一个批次。

主要字段：

- studentId：学员 ID
- orderItemId：来源订单明细（赠送或补偿时为空）
- sourceType：来源类型，例如购买、赠送、补偿
- totalHours：该批次总课时
- remainingHours：该批次剩余课时
- expiresAt：有效期截止时间
- status：批次状态

学员当前可用课时，等于所有未过期批次的剩余课时之和。

例如：

某学员购买了 50 节课程，已经上了 12 节，那么该批次剩余 38 节。

但系统不能只保存批次余额。

还必须有 student\_hour\_transactions 记录每次课时变化，并记录变动发生在哪个批次上。

例如：

- 购买课程增加 50 节。
- 完成课程扣减 1 节。
- 误扣后冲正返还 1 节。
- 机构赠送课程增加 2 节。
- 批次过期，剩余课时作废。

每一次变动都要有来源、有时间、有操作人。

扣课时的规则也需要提前约定，例如优先扣减最先到期的批次。

**账户余额是当前结果，流水才是变化依据。**

如果为了查询方便，保留 student\_hour\_accounts 作为汇总缓存，它必须和批次、流水在同一个事务中更新，并且可以随时根据流水重新计算校验。

另外，同一节课程只能扣一次课时。需要通过唯一约束或幂等键，保证重复提交「课程完成」操作时，不会重复扣课。

### 2. 教师课时费规则

不同教师可能有不同的课时费标准。

例如：

- 教师 A：体验课 30 元/节，正式课 50 元/节。
- 教师 B：体验课 40 元/节，正式课 60 元/节。

因此，需要 teacher\_pay\_rules 保存教师课时费规则。

规则还应该记录生效时间。

如果教师后续调整单价，历史课程仍然应该按照当时生效的规则计算，不能因为修改了当前单价，就导致以前的结算金额发生变化。

### 3. 单节课程费用明细

每节课程被确认完成后，系统根据实际授课教师和课程类型生成教师费用明细。

teacher\_lesson\_fees 保存：

- 课程 ID
- 实际授课教师 ID
- 课程类型
- 计费规则
- 当时适用的单价
- 实际计费金额
- 计费状态
- reversalOfId：如果是冲正记录，指向被冲正的费用

这里必须保存单价和金额快照。

不能在月底结算时，再拿教师当前的单价重新计算历史课程。

同时，同一节课程只能产生一条正常的计费记录，需要通过唯一约束防止重复计费。

课程被更正时（例如误标为完成），不修改原费用记录，而是生成一条反向的冲正记录。已经进入结算单的费用，更不能直接改动，只能通过结算调整记录来处理。

### 4. 教师月度结算

每个月，机构需要与兼职教师核对实际授课数量和课时费。

teacher\_settlements 保存结算单主信息。

teacher\_settlement\_items 保存结算单中的每节课程明细。

teacher\_settlement\_adjustments 保存结算金额的调整。

teacher\_payments 保存实际付款记录。

这样就可以支持：

- 月度课时费统计。
- 教师核对结算单。
- 结算金额调整。
- 全额付款。
- 部分付款。
- 分批付款。
- 付款记录追踪。

结算单不等于付款记录。

机构确认应该支付多少钱，与机构实际支付了多少钱，是两个不同的业务事实。

## 七、六大模块之间的数据关系

上面介绍了主要数据表，现在我们把它们放在一起看。

整个系统的核心业务链可以概括为：

```text
系统基础管理
  users / roles / permissions
  员工档案、教师档案、家长档案、代理档案
        |
招生与客户
  customers → 跟进、归属变更
        → registrations → orders → payments
        |        （成交时关联或创建家长、学员）
        |
学员与教师
  parents ←→ students
  teaching_demands → 教师响应 → teacher_students
        |
教学与课程
  schedule_plans → courses（计划）→ course_records（实际）
  词库授权 → 训练任务 → student_word_progress → 复习 → 学习报告
        |
课时与财务
  收款确认 → student_hour_lots → 课时流水
  课程确认完成 → 扣减课时
               → teacher_lesson_fees → 月度结算 → 教师付款
```

这张图展示的是业务之间的关联关系，并不是严格的数据库外键关系图。

真正落到数据库时，还需要明确每张表的主键、外键、唯一约束和索引。

## 八、数据库设计中最值得关注的六个问题

对于一个真实项目来说，数据库表创建出来并不代表设计完成。

还需要考虑业务数据在各种情况下是否能够保持一致。

### 1. 不要把所有信息塞进一张表

例如，不要把学员姓名、家长电话、教师姓名、课程时间和课时余额全部塞进 students 表。

这些信息属于不同业务对象。

应该根据业务实体建立独立的数据表，再通过关联关系连接。

这样才能支持后续业务扩展。

### 2. 重要业务必须保留历史记录

例如：

- 学员更换教师，应该保留原来的师生关系。
- 教师调整课时费，不能影响历史课程费用。
- 客户转交负责人，应该保留归属变化记录。
- 课程调课、换教师，应该保留变更记录。
- 学员课时发生变化，应该保留完整流水。

对于真实业务系统来说，当前状态固然重要，但历史变化同样重要。

### 3. 业务状态不能随意修改

例如，一节课程可能经历：

待上课 → 已完成。

也可能经历：

待上课 → 已取消。

已完成的课程不能随意修改回待上课状态，更不能通过重复提交完成操作，导致学员被重复扣课、教师被重复计费。

因此，重要业务操作需要有明确的状态流转规则，并在服务端进行校验。

### 4. 金额和课时必须保持准确

金额字段不能使用普通浮点数随意计算。

数据库中应该使用 Decimal 等精确数值类型，或者统一使用整数分保存金额。

课时也不能仅仅依靠前端计算。

课程完成、学员扣课、教师计费等操作需要在服务端协调处理，并通过事务、唯一约束和幂等机制防止重复执行。

### 5. 出错时用冲正，而不是直接修改

误扣课时、误生成教师费用、已结算金额需要调整，这些都是真实业务中一定会发生的事情。

正确的做法是增加一条方向相反的记录（冲正流水、冲正费用、结算调整），并保留原始记录，而不是回头修改或删除历史数据。这样每一笔钱、每一个课时的变化都能追溯，对账时才有依据。

### 6. 权限必须落实到数据访问层

家长只能查看自己关联的学员。

教师只能查看自己负责范围内的教学数据。

代理只能查看授权范围内的客户。

这些规则不能仅仅依赖前端隐藏菜单或按钮。

每次查询、修改和业务操作，都必须在服务端验证当前用户身份、角色和数据归属。

## 九、总结：数据库设计决定了软件能够走多远

这次英语教学管理平台的数据库设计，核心不是创建多少张表，而是把真实业务中的人物、关系、过程和结果准确地表达出来。

我们可以把整个系统理解为三个层次：

**第一层：基础数据。**

用户、教师、家长、代理、学员、词库和单词等基础信息。

**第二层：业务过程。**

客户跟进、报名、接单、排课、授课、单词训练、复习和结算等业务活动。

**第三层：业务结果。**

学习报告、学员课时余额、教师应付费用、实际付款和经营统计。

这三层数据相互关联，才能构成一个真正可运行的业务系统。

在正式用 Prisma 建模之前，建议先和业务方确认下面几条规则，因为它们会直接影响表结构：

- 课时是否需要有效期？有效期按订单还是按课时类型计算？
- 课程「完成」由谁确认？教师提交记录后是否还需要教务审核？
- 体验课是否扣减学员课时？课时费是否按体验课单独计算？
- 系统是只服务一家机构，还是将来要提供给多家机构使用？

对于全栈开发者来说，这也是一个很好的实践案例。

因为数据库设计不是把页面上的字段搬到数据库，而是理解业务之后，把业务对象、业务关系和业务规则转换成数据结构。

下一步，我们就可以基于这套设计，按照分期计划，先使用 Prisma 定义第一期的数据模型，通过实际业务开发逐步验证这些数据关系是否合理。
