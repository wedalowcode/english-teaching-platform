# 第十篇：搭建后台管理系统整体框架，实现左侧导航与右侧工作区

前面几篇，我们一直在实现用户管理模块。

从用户列表、用户新增、编辑、重置密码，到启用、停用、删除和详情查看，已经完成了一组比较完整的用户管理功能。

但现在有一个明显的问题：每个页面都是独立存在的。

打开用户列表，看到的是用户列表；进入编辑页面，又是另一套页面。如果继续增加角色管理、权限管理、学员管理、教师管理等功能，就会出现大量重复的页面结构。

现代后台管理系统通常不会这样设计。

不管进入哪个业务模块，页面都会保留统一的导航和操作区域，只有中间的业务内容发生变化。

本篇就来搭建这套通用框架：左侧导航、顶部信息栏、右侧工作区，以及页面统一的标题区。

## 前置条件

本篇依赖前几篇的成果，开始之前请确认：

- 用户管理三个页面已存在：`/admin/users`、`/admin/users/new`、`/admin/users/[id]/edit`。
- `components/ui/` 下的基础组件都是通过 shadcn 生成的，不手写。
- 项目已配置 Tailwind CSS v4，主题变量集中在 `app/globals.css`。

另外先明确一个定位：

**后台面向桌面浏览器，不做手机适配。**

家长端在规划中是独立的 H5 页面，和这个管理后台不是同一套界面，所以这里不需要考虑移动端的折叠菜单。侧边栏的折叠能力只是桌面端的一个便利功能，不是移动端方案。

## 一、先明确整体布局

目标布局是经典的后台结构：

```text
┌──────────────┬───────────────────────────────────────────┐
│              │  机构名称   校区   当前用户                │
│              ├───────────────────────────────────────────┤
│  英语教学平台 │                                           │
│              │  面包屑                                   │
│  系统设置     │  页面标题                                  │
│    用户管理   │  页面说明                    页面操作按钮  │
│              │                                           │
│              │  ┌───────────────────────────────────────┐│
│              │  │                                       ││
│              │  │             页面业务内容              ││
│              │  │                                       ││
│              │  └───────────────────────────────────────┘│
└──────────────┴───────────────────────────────────────────┘
```

整体分为三个部分：

**1. 左侧导航 Sidebar**

负责展示系统品牌、业务模块和菜单。菜单按业务领域分组，当前先有「系统设置 / 用户管理」一组。

**2. 顶部信息栏 Topbar**

负责展示机构名称、校区和当前登录身份，同时提供侧边栏的展开/收起按钮。

**3. 右侧工作区 Content**

这是整个系统真正的业务工作区。不同路由对应不同页面，但都共享同一套外壳。

这些页面共享同一套布局：

```text
/admin/users
/admin/users/new
/admin/users/[id]/edit
```

### 关于 `/admin/` 这个前缀

`/admin/` 是**管理员**的入口，不是「所有角色的后台都放在这里」。

按照第三篇的角色规划，未来不同角色会有各自的目录，例如：

```text
/admin/        # 管理员：用户、角色权限、系统设置
/academic/     # 教务：学员、教师、排课
/boss/         # 校长：经营概览、财务
/teacher/      # 教师：我的课程、课程记录
```

这些角色入口可以共用同一个路由组的布局，但菜单内容各自不同。本篇先把管理员的框架搭好，其他角色在做到对应模块时再建目录。

### 菜单先只放已经存在的页面

一个常见的新手错误，是先把「完整菜单」一次性写进配置，结果大部分链接点进去都是 404。

本篇只把**已经实现的页面**放进菜单：

```text
系统设置
  └── 用户管理  →  /admin/users
```

其余模块（角色权限、学员管理、教师管理、订单、财务等）在做到对应章节时再加进配置。菜单配置只是一份数据，增加一项的成本很低，没必要提前占位。

如果确实需要在界面上体现完整的产品结构，正确做法是把未实现的项标成「即将上线」的禁用项，而不是做成可以点击、会跳 404 的链接。本篇不做这种展示。

## 二、目录结构

改造后的目录如下：

```text
app/
├── layout.tsx
├── globals.css
└── (dashboard)/
    ├── layout.tsx                    # 后台外壳，本篇新增
    └── admin/
        └── users/
            ├── page.tsx              # 用户列表
            ├── new/
            │   └── page.tsx          # 新增用户
            └── [id]/
                └── edit/
                    └── page.tsx      # 编辑用户

components/
├── layout/
│   ├── menu-config.ts                # 菜单数据
│   ├── admin-sidebar.tsx             # 左侧导航
│   └── admin-topbar.tsx              # 顶部信息栏
├── shared/
│   └── page-header.tsx               # 页面标题区，本篇新增
└── ui/
    ├── sidebar.tsx                   # shadcn 生成
    ├── separator.tsx                 # shadcn 生成
    └── tooltip.tsx                   # shadcn 生成

hooks/
└── use-mobile.ts                     # shadcn 生成
```

注意这里没有 `components/layout/admin-layout.tsx`。

布局只用一层：`app/(dashboard)/layout.tsx` 直接组合侧边栏、顶栏和内容区。再包一层 `AdminLayout` 组件只是把 `children` 原样转交，多一个文件、多一次跳转，没有实际收益。布局层的代码应该尽量短、一眼能看懂。

### 路由组的作用

`app/(dashboard)` 中的括号表示 Route Group，它帮助组织路由结构，但不会出现在浏览器地址中。

例如：

```text
app/(dashboard)/admin/users/page.tsx
```

实际访问地址仍然是：

```text
/admin/users
```

把需要后台外壳的页面统一放进 `(dashboard)` 路由组，由其中唯一的 `layout.tsx` 提供外壳。以后新增业务模块，不需要重复编写侧边栏和顶栏。

## 三、添加 shadcn 的 Sidebar

侧边栏不手写，直接使用 shadcn 提供的组件：

```bash
pnpm dlx shadcn@latest add sidebar
```

这条命令会生成或更新四个文件：

- `components/ui/sidebar.tsx`：Sidebar、SidebarProvider、SidebarInset、SidebarMenu 等一整套组件。
- `components/ui/separator.tsx`：分隔线。
- `components/ui/tooltip.tsx`：折叠成图标时，用来显示菜单名称的提示。
- `hooks/use-mobile.ts`：内部用于判断是否为窄屏。

当前项目使用的是 Base UI 版 shadcn，组件用 `render` 属性组合，而不是 `asChild`。写法和前面几篇的 `Sheet`、`DropdownMenu` 一致：

```tsx
<SidebarMenuButton render={<Link href="/admin/users" />}>
  用户管理
</SidebarMenuButton>
```

生成后如果 `components/ui/*.tsx` 里出现：

```ts
import { cn } from "cn"
```

统一改成：

```ts
import { cn } from "@/lib/utils"
```

和第九篇的处理保持一致。

用现成组件而不是手写，主要有几个实际差别：

- 宽度、固定定位、折叠状态由组件统一管理，不需要自己写 `w-60` 再在另一处写 `ml-60`，改一处漏一处。
- 自带的折叠成图标模式，以及折叠后的 tooltip。
- 颜色使用主题变量，不把十六进制颜色写死在组件里。

## 四、把配色写进主题变量

侧边栏用深色、内容区用浅色，这个方向保留。但颜色不要写成 `bg-[#101B3C]` 这类任意值，而是填进 `app/globals.css` 的主题变量里。

`@theme inline` 中已经有一组 `--color-sidebar-*` 映射，这是添加 sidebar 组件时生成好的。需要改的是 `:root` 里的实际色值：

```css
:root {
  --background: #f3f6fc;
  --foreground: #172033;
  --card: #ffffff;
  --card-foreground: #172033;

  --primary: #2563eb;
  --primary-foreground: #ffffff;

  --muted-foreground: #64748b;
  --accent: #e8eefb;
  --accent-foreground: #1d4ed8;

  --destructive: #dc2626;
  --border: #d9e2f0;
  --input: #d9e2f0;
  --ring: #2563eb;

  --sidebar: #101b3c;
  --sidebar-foreground: #e2e8f5;
  --sidebar-primary: #1d4ed8;
  --sidebar-primary-foreground: #ffffff;
  --sidebar-accent: #1d4ed8;
  --sidebar-accent-foreground: #ffffff;
  --sidebar-border: #24325b;
  --sidebar-ring: #2563eb;
}
```

本篇实际用到的语义如下：

| 主题变量 | 色值 | 用途 |
|---|---|---|
| `--sidebar` | `#101B3C` | 侧边栏背景，深海军蓝 |
| `--sidebar-primary` | `#1D4ED8` | 品牌标识（顶部 EE 图标） |
| `--sidebar-accent` | `#1D4ED8` | 当前菜单与悬停项的背景 |
| `--sidebar-foreground` | `#E2E8F5` | 侧边栏文字 |
| `--background` | `#F3F6FC` | 内容区背景，浅蓝灰 |
| `--card` | `#FFFFFF` | 顶栏和业务面板 |
| `--foreground` | `#172033` | 标题文字 |
| `--muted-foreground` | `#64748B` | 说明、辅助文字 |
| `--primary` | `#2563EB` | 主操作按钮 |
| `--border` | `#D9E2F0` | 区域边界 |
| `--destructive` | `#DC2626` | 删除等危险操作 |

这样写的好处很直接：以后要调整主色，只改 `:root` 一处，侧边栏、按钮、徽标、表格边框会一起变，不会出现「手写的十六进制颜色和 shadcn 组件的主题色对不上」的情况。组件里只写语义类名，例如 `bg-sidebar`、`text-sidebar-foreground`、`border-sidebar-border`、`bg-card`、`text-muted-foreground`。

这里有一个原则：

**颜色不是装饰，而是信息层级的一部分。**

当前菜单要比其他菜单突出，主操作要比普通操作突出，危险操作要有明确的风险色。用主题变量表达这层含义，比到处写颜色值更可靠。

## 五、菜单配置

菜单属于系统配置，不要散落在 Sidebar 组件里。

新建 `components/layout/menu-config.ts`：

```tsx
import { Users } from "lucide-react";

import type { LucideIcon } from "lucide-react";

export type MenuItem = {
  title: string;
  href: string;
  icon: LucideIcon;
};

export type MenuGroup = {
  title: string;
  items: MenuItem[];
};

/**
 * 只收录当前已经实现页面的菜单。
 * 新增业务模块时再往对应分组里添加，避免菜单链接指向 404。
 */
export const adminMenus: MenuGroup[] = [
  {
    title: "系统设置",
    items: [
      {
        title: "用户管理",
        href: "/admin/users",
        icon: Users,
      },
    ],
  },
];

export function getMenuBreadcrumb(href: string): string[] {
  for (const group of adminMenus) {
    const item = group.items.find((menuItem) => menuItem.href === href);

    if (item) {
      return [group.title, item.title];
    }
  }

  return [];
}
```

这里有三个设计点。

第一，菜单配置与渲染分离。以后改菜单名称、图标、路由，只改这个文件。

第二，顺手导出 `getMenuBreadcrumb`。页面的面包屑（「系统设置 / 用户管理」）不再手写字符串，而是从菜单配置推导出来。否则菜单改名之后，面包屑还停留在旧文案，两边永远在维护两份数据。

第三，图标目前存的是组件函数（`LucideIcon`）。这里有一个将来会踩的坑：

**组件函数不能跨服务端和客户端的边界传递。**

以后接入角色权限，如果打算在服务端按角色过滤菜单，再把过滤结果传给客户端侧边栏，`icon` 字段会因为无法序列化而报错。届时有两种解法：

- 过滤逻辑放在客户端，服务端只返回角色；
- 或者把 `icon` 改成图标名称字符串（如 `"Users"`），在客户端再映射成组件。

现在不必改，但要知道这个约束，避免以后返工。

## 六、实现左侧导航

新建 `components/layout/admin-sidebar.tsx`：

```tsx
"use client";

import Link from "next/link";
import { usePathname } from "next/navigation";

import {
  Sidebar,
  SidebarContent,
  SidebarGroup,
  SidebarGroupContent,
  SidebarGroupLabel,
  SidebarHeader,
  SidebarMenu,
  SidebarMenuButton,
  SidebarMenuItem,
} from "@/components/ui/sidebar";

import { adminMenus } from "./menu-config";

export function AdminSidebar() {
  const pathname = usePathname();

  function isActive(href: string) {
    return pathname === href || pathname.startsWith(`${href}/`);
  }

  return (
    <Sidebar collapsible="icon">
      <SidebarHeader className="h-16 flex-row items-center gap-3 border-b border-sidebar-border px-4 group-data-[collapsible=icon]:justify-center group-data-[collapsible=icon]:px-2">
        <div className="flex size-9 shrink-0 items-center justify-center rounded-lg bg-sidebar-primary text-sm font-bold text-sidebar-primary-foreground">
          EE
        </div>

        <div className="min-w-0 group-data-[collapsible=icon]:hidden">
          <div className="truncate text-sm font-semibold text-sidebar-foreground">
            英语教学平台
          </div>
          <div className="truncate text-xs text-sidebar-foreground/60">
            TEACHING MANAGEMENT
          </div>
        </div>
      </SidebarHeader>

      <SidebarContent>
        <nav aria-label="后台主菜单">
          {adminMenus.map((group) => (
            <SidebarGroup key={group.title}>
              <SidebarGroupLabel className="text-xs font-semibold tracking-wide text-sidebar-foreground/60">
                {group.title}
              </SidebarGroupLabel>

              <SidebarGroupContent>
                <SidebarMenu>
                  {group.items.map((item) => {
                    const active = isActive(item.href);
                    const Icon = item.icon;

                    return (
                      <SidebarMenuItem key={item.href}>
                        <SidebarMenuButton
                          render={<Link href={item.href} />}
                          isActive={active}
                          tooltip={item.title}
                          aria-current={active ? "page" : undefined}
                        >
                          <Icon />
                          <span>{item.title}</span>
                        </SidebarMenuButton>
                      </SidebarMenuItem>
                    );
                  })}
                </SidebarMenu>
              </SidebarGroupContent>
            </SidebarGroup>
          ))}
        </nav>
      </SidebarContent>
    </Sidebar>
  );
}
```

几个关键点。

### 1. 为什么是 Client Component

菜单需要根据当前路由高亮，所以用 `usePathname()` 获取地址。

匹配规则：

```tsx
pathname === href || pathname.startsWith(`${href}/`)
```

后面的 `startsWith(`${href}/`)` 带了一个斜杠，这一步很重要。如果不带斜杠，`/admin/users` 会错误地匹配到 `/admin/users-new` 这类前缀相同的路由。带上斜杠后，只有真正的子路由才会命中：

```text
/admin/users           → 匹配
/admin/users/new       → 匹配
/admin/users/123/edit  → 匹配
/admin/users-archive   → 不匹配
```

因此进入新增或编辑页面时，「用户管理」菜单依然保持高亮。

### 2. 选中态交给 `isActive`

shadcn 的 `SidebarMenuButton` 提供 `isActive` 属性，选中时的背景、文字颜色会走 `--sidebar-accent`、`--sidebar-accent-foreground` 主题变量，不需要自己判断类名组合。

同时补两个可访问性细节：

- 导航容器加 `aria-label`，让读屏软件知道这是一级主菜单。
- 当前项加 `aria-current="page"`，明确告知当前所在页面。

### 3. 折叠由 `collapsible="icon"`

`collapsible="icon"` 表示侧边栏可以收起成一条只有图标的窄栏。收起后鼠标悬停在图标上，会通过 `tooltip` 显示菜单名称。

宽度、固定定位、动画、折叠状态全部由组件处理，组件里不再出现 `w-60` 和 `ml-60` 这种两处写死的数字。

### 4. 字号不要低于 12px

侧边栏是深色背景，小字对比度本来就不高。菜单分组标签用 `text-xs`（12px）就够小，不要用 `text-[10px]`、`text-[11px]` 这类更小的值。

### 5. 侧边栏底部不要重复品牌信息

顶部 `SidebarHeader` 已经展示了平台名称。底部再放一个「英语教学管理平台 / 管理端工作空间」的小卡片，属于同一信息的重复，删掉即可。

### 6. 图标要能区分

如果多个菜单使用同一个图标（例如代理管理、教师管理、用户管理都用 `Users`），用户很难凭图标区分模块。每个模块应尽量选用语义不同的图标。

```tsx
        </div>
      </div>
    </header>

```

这里只放两类内容：

- **真实存在的能力**：`SidebarTrigger`，用来展开或收起侧边栏。
- **静态展示**：机构名称、校区、当前用户。

刻意不放的东西：

- 带 `Ctrl K` 提示的搜索框。没有对应的快捷键，也没有搜索功能。
- 带红点的消息铃铛。红点暗示有未读消息，实际是假的。
- 带下拉箭头的用户按钮。箭头暗示有菜单，实际点开没有内容，也没有「退出登录」。

这些「看起来能用、实际不能用」的界面元素，比缺少功能更糟糕：用户会反复点击，然后认为系统坏了。等真正做认证、消息、全局搜索时，再按那时的需求补上。

## 八、组合布局

打开 `app/(dashboard)/layout.tsx`，直接在这里组合三部分：

```tsx
import { Suspense, type ReactNode } from "react";

import { AdminSidebar } from "@/components/layout/admin-sidebar";
import { AdminTopbar } from "@/components/layout/admin-topbar";
import { SidebarInset, SidebarProvider } from "@/components/ui/sidebar";

type DashboardLayoutProps = {
  children: ReactNode;
};

export default function DashboardLayout({ children }: DashboardLayoutProps) {
  return (
    <SidebarProvider>
      {/* Sidebar 内部使用 usePathname，必须包在 Suspense 中，原因见第十节 */}
      <Suspense fallback={null}>
        <AdminSidebar />
      </Suspense>

      <SidebarInset className="min-w-0">
        <AdminTopbar />

        <div className="min-w-0 flex-1 p-6">{children}</div>
      </SidebarInset>
    </SidebarProvider>
  );
}
```

几处需要解释。

### 1. `SidebarProvider`

它提供侧边栏的展开/收起状态，以及一些 CSS 变量，供 `Sidebar` 和 `SidebarInset` 使用。侧边栏内部用 `position: fixed`，`SidebarInset` 负责占据剩余空间，两者配合完成布局，不需要手动写左边距。

### 2. `SidebarInset` 本身就是 `<main>`

这一点很关键。`SidebarInset` 渲染出来的根元素就是 `<main>`，所以布局里只写一个普通的 `<div>` 包 `children`，**页面内部不能再出现 `<main>`**。

一个 HTML 文档只能有一个 `<main>` 元素，嵌套的 `<main>` 是不合法的。如果把旧的 `<main>` 保留下来，浏览器会把结构纠正成不可预测的样子，读屏软件也会困惑。

### 3. `min-w-0` 防止内容撑破布局

`SidebarInset` 和内容容器都加了 `min-w-0`。Flex 布局的子项默认 `min-width: auto`，当里面出现宽表格时，会把容器撑破，导致横向滚动条出现在整个页面上。加上 `min-w-0` 后，超宽内容会在自己的容器里滚动。

### 4. 旧页面要同步修改

新布局已经有 `p-6` 内边距，而现有三个页面最外层原来是 `<main className="space-y-6 p-6">`。如果原样保留：

- 出现嵌套 `<main>`；
- 内边距叠加成 48px，内容和边缘的距离明显偏大。

需要把三个页面最外层改成 `<div>` 并去掉自己的 `p-6`：

```text
app/(dashboard)/admin/users/page.tsx
app/(dashboard)/admin/users/new/page.tsx
app/(dashboard)/admin/users/[id]/edit/page.tsx
```

改动前后对比：

```tsx
// 改之前
<main className="space-y-6 p-6">
  ...
</main>

// 改之后
<div className="space-y-6">
  ...
</div>
```

这只是容器和间距的调整，业务逻辑不变。

## 九、抽取统一的页面标题区

框架搭好后，页面内容也要形成统一规范。

建议每个业务页面采用以下结构：

```text
页面标题区
    ├── 面包屑
    ├── 页面标题
    ├── 页面说明
    └── 页面操作按钮

统计区域（可选）

筛选区域（可选）

业务内容区域
```

但如果每个页面都手写这段标题区，就是在重复前一篇里刚说要避免的重复劳动，而且容易出现标题字号、间距不一致。

抽成一个共用组件，新建 `components/shared/page-header.tsx`：

```tsx
import type { ReactNode } from "react";

type PageHeaderProps = {
  title: string;
  description?: string;
  breadcrumb?: string[];
  actions?: ReactNode;
};

export function PageHeader({
  title,
  description,
  breadcrumb,
  actions,
}: PageHeaderProps) {
  return (
    <div className="flex flex-wrap items-end justify-between gap-4">
      <div>
        {breadcrumb && breadcrumb.length > 0 && (
          <p className="mb-1 text-xs text-muted-foreground">
            {breadcrumb.join(" / ")}
          </p>
        )}

        <h1 className="text-xl font-semibold tracking-tight text-foreground">
          {title}
        </h1>

        {description && (
          <p className="mt-1 text-sm text-muted-foreground">{description}</p>
        )}
      </div>

      {actions && <div className="flex items-center gap-2">{actions}</div>}
    </div>
  );
}
```

页面里只写一行：

```tsx
<PageHeader
  breadcrumb={getMenuBreadcrumb("/admin/users")}
  title="用户管理"
  description="管理系统用户账号、状态及登录信息。"
  actions={
    <Link href="/admin/users/new" className={buttonVariants()}>
      新增用户
    </Link>
  }
/>
```

三个细节：

**面包屑从菜单配置推导。** `getMenuBreadcrumb("/admin/users")` 返回 `["系统设置", "用户管理"]`，菜单改名时面包屑自动跟着变。新增、编辑页在末尾追加一段：

```tsx
breadcrumb={[...getMenuBreadcrumb("/admin/users"), "新增用户"]}
```

**标题样式统一。** `text-xl font-semibold` 和前几篇页面的标题层级保持一致。不要在不同页面之间混用 `text-2xl font-bold`。

**不要把表格套进第二层卡片。** 用户列表本身已经用 `rounded-md border bg-card` 画出外框。如果在 `PageHeader` 下面再包一个白色 `rounded-xl border` 卡片，就会出现两层边框、两层圆角。页面标题区与业务内容之间保持 `space-y-6` 的间距即可。

改造后的列表页大致是：

```tsx
export default function UsersPage({ searchParams }: Props) {
  return (
    <div className="space-y-6">
      <PageHeader
        breadcrumb={getMenuBreadcrumb("/admin/users")}
        title="用户管理"
        description="管理系统用户账号、状态及登录信息。"
        actions={
          <Link href="/admin/users/new" className={buttonVariants()}>
            新增用户
          </Link>
        }
      />

      <Suspense fallback={<UserListSkeleton />}>
        <UserList searchParams={searchParams} />
      </Suspense>
    </div>
  );
}
```

## 十、`usePathname` 必须包在 `Suspense` 中

这是本篇唯一一个不在开发环境暴露、只在构建阶段报错的问题。

前几篇已经处理过「动态数据没有放进 `Suspense`」的构建错误，侧边栏这里是同一类问题的另一种表现：`usePathname()` 读取的地址只在运行时可用，无法在预渲染阶段求值。

只加布局、不做处理时，`pnpm build` 会直接失败：

```text
Error: Route "/admin/users/[id]/edit": Next.js encountered URL data usePathname()
in a Client Component outside of <Suspense>.
This blocks prerendering because the value is only available at runtime.
```

动态参数路由（`/admin/users/[id]/edit`）会触发这个检查，所以必须在 `app/(dashboard)/layout.tsx` 里把侧边栏包进 `Suspense`：

```tsx
<SidebarProvider>
  <Suspense fallback={null}>
    <AdminSidebar />
  </Suspense>

  <SidebarInset className="min-w-0">
    ...
  </SidebarInset>
</SidebarProvider>
```

`fallback={null}` 表示预渲染时先不输出侧边栏，等页面流式渲染时再补上。这不会造成布局跳动：`SidebarInset` 的位置由 `SidebarProvider` 提供的 CSS 变量决定，和侧边栏是否已经渲染无关。

开发环境一定要配合 `pnpm build` 验证。`pnpm dev` 能打开页面，不代表构建能通过，这类预渲染问题只在构建阶段报出。

## 十二、这一篇真正解决了什么问题？

到这里，后台管理系统的第一版框架完成了。

之前每个页面都需要单独处理布局，现在统一交给 Next.js Layout；标题区交给 `PageHeader`；颜色交给主题变量；侧边栏交给 shadcn。

这种结构的好处不只是减少重复代码，更重要的是给后续模块建立了统一标准：

```text
用户管理
角色管理
学员管理
教师管理
代理管理
订单管理
财务管理
词库管理
```

每个模块只需实现自己的业务内容，外壳和标题区自动复用。

同时也要诚实说明，当前还有这些能力没有接入：

1. 菜单仍是静态配置，没有根据角色权限过滤。接入时注意本篇提到的图标序列化问题。
2. 顶部用户信息是演示数据，还没有接入真实登录会话。
3. 没有搜索、消息通知、用户菜单和退出登录入口。这些等对应功能实现后再加，不提前放假入口。
4. 其他角色的入口（`/academic`、`/boss`、`/teacher`）尚未建立。
5. 移动端不适配。后台面向桌面浏览器，家长端是独立的 H5 页面。

**一个成熟的后台系统，首先是统一、诚实的页面框架，然后才是在框架上持续增加真实可用的业务能力。**
