# 第九篇：实现用户详情抽屉，让列表操作更简洁

前面几篇，我们已经完成了用户管理的主要操作：

- 用户新增
- 用户资料编辑
- 管理员重置密码
- 用户启用、停用与删除

现在回到用户管理列表，虽然功能已经比较完整，但操作区域也逐渐变得拥挤。

目前每一行用户记录后面，都有编辑、重置密码、启用/停用和删除等操作。随着功能继续增加，列表会越来越像一个操作按钮集合。

本篇做两项调整：

1. 增加用户详情查看功能，点击「查看」后，从页面右侧弹出抽屉，展示用户详细资料。
2. 优化列表操作区域，把低频的重置密码、启用/停用和删除收进「更多」菜单。

最终列表的操作区域变成：

```text
┌─────────────────────────────────────────────┐
│ 用户名       手机号       状态       操作    │
├─────────────────────────────────────────────┤
│ admin        13800138000  启用   查看 编辑 更多 │
│ teacher01    13900139000  启用   查看 编辑 更多 │
└─────────────────────────────────────────────┘
```

手机号这里先原样显示完整号码。等后续用户量变大、手机号成为敏感信息后，再在列表里做脱敏（如 `138****8888`），详情抽屉里保留完整值，这是更常见的做法。

## 前置条件

本篇依赖第八篇修订版的几个改动，如果还没同步会直接报错：

- `sonner` 已安装，`app/layout.tsx` 里挂了 `<Toaster />`。
- `setUserStatusAction` 和 `deleteUserAction` 返回 `{ success, message }`，不再 `redirect`。
- `UserResetPasswordDialog` 支持 `open`、`onOpenChange`、`hideTrigger` 三个外部控制属性。
- `constants.ts` 已有 `USER_STATUS_LABEL`。本篇会继续在这里补充状态样式映射和日期格式化函数。

## 一、先明确本次改造的结构

本次不改变原有的业务逻辑，主要调整前端交互和用户详情查询。

涉及的文件如下：

```text
components/
└── ui/
    ├── sheet.tsx               # 新增：shadcn 右侧抽屉
    └── dropdown-menu.tsx       # 新增：shadcn 下拉菜单

features/
└── users/
    ├── constants.ts            # 补充状态样式映射和日期格式化
    ├── service.ts              # 扩展用户列表查询字段
    └── components/
        ├── user-list.tsx       # 调整列表操作区域
        ├── user-detail-drawer.tsx  # 新增：用户详情抽屉
        └── user-account-actions.tsx # 改造为更多操作菜单
```

这里有一个设计原则：

**详情查看不应该变成一个新的业务修改入口。**

详情抽屉只负责读取和展示数据，编辑继续使用已有的编辑页面，重置密码、启用停用和删除继续调用原有的 Server Action。

这样可以避免为了增加一个查看功能，重复实现已有业务逻辑。

## 二、添加 Sheet 和 DropdownMenu

项目已经通过 shadcn 初始化，`components/ui/` 下的基础组件都由 shadcn 生成，不手写。

添加两个新组件：

```bash
pnpm dlx shadcn@latest add sheet dropdown-menu
```

生成后会得到：

- `components/ui/sheet.tsx`：右侧抽屉，默认 `side="right"` 从右滑出。
- `components/ui/dropdown-menu.tsx`：下拉菜单。

两个组件都基于 Base UI，和已有的 `dialog.tsx`、`alert-dialog.tsx` 风格一致，都用 `render` 属性组合触发器。

## 三、统一 cn 导入

项目里的 shadcn 组件原来用 `import { cn } from "cn"`，这里统一改成：

```ts
import { cn } from "@/lib/utils"
```

`lib/utils.ts` 就是 re-export cn，改成显式路径后更容易追踪，替换实现也只改一处。所有 `components/ui/*.tsx` 里的 cn 导入都要同步改掉。

## 四、扩展 constants 与列表查询

### 1. 补充 constants.ts

原来只有状态标签，现在追加两个共用常量：

```ts
export const USER_STATUS_BADGE_VARIANT: Record<
  UserStatus,
  "default" | "secondary"
> = {
  ACTIVE: "default",
  DISABLED: "secondary",
};

const USER_DATE_FORMATTER = new Intl.DateTimeFormat("zh-CN", {
  dateStyle: "medium",
  timeStyle: "short",
  timeZone: "Asia/Shanghai",
});

export function formatUserDate(value: Date) {
  return USER_DATE_FORMATTER.format(value);
}
```

这样列表页和详情抽屉都从 constants 取状态徽章样式和日期格式化，改一处不会漏另一处。`user-list.tsx` 里原来本地的 `STATUS_META` 和 `dateFormatter` 都可以删掉。

### 2. 扩展列表查询字段

`getUserList` 当前 select 里已经有 `createdAt`，补上 `updatedAt`：

```ts
select: {
  id: true,
  username: true,
  phone: true,
  status: true,
  createdAt: true,
  updatedAt: true,
},
```

不需要额外查一次数据库，列表本身就返回了详情抽屉所需的所有字段。

密码哈希同样不要加进 select，不是管理员该看到的内容。

## 五、实现用户详情抽屉

新建：

`features/users/components/user-detail-drawer.tsx`

```tsx
"use client";

import type { ReactNode } from "react";

import { Eye } from "lucide-react";

import type { UserStatus } from "@/app/generated/prisma/client";
import { Badge } from "@/components/ui/badge";
import { Button } from "@/components/ui/button";
import {
  Sheet,
  SheetContent,
  SheetDescription,
  SheetHeader,
  SheetTitle,
  SheetTrigger,
} from "@/components/ui/sheet";
import {
  USER_STATUS_BADGE_VARIANT,
  USER_STATUS_LABEL,

  return (

          <SheetTitle>用户详情</SheetTitle>

          </SheetDescription>

          <div className="flex items-center gap-3">

            <div>

            </div>
          </div>

          <div className="grid grid-cols-2 gap-5">
            <DetailItem label="用户名">{user.username}</DetailItem>

            <DetailItem label="手机号">{user.phone || "未填写"}</DetailItem>

            <DetailItem label="账号状态">
              <Badge variant={USER_STATUS_BADGE_VARIANT[user.status]}>
                {USER_STATUS_LABEL[user.status]}
              </Badge>
            </DetailItem>

            <DetailItem label="用户 ID">
              <span className="break-all">{user.id}</span>
            </DetailItem>

            <DetailItem label="创建时间">
              {formatUserDate(user.createdAt)}
            </DetailItem>

            <DetailItem label="最后更新时间">
              {formatUserDate(user.updatedAt)}
            </DetailItem>
          </div>
        </div>
      </SheetContent>

```

这里没有重新调用 Service，也没有创建 Server Action。

原因很简单：详情所需的数据已经包含在服务端查询结果中。用户点击查看时，只是控制抽屉显示和隐藏，不需要再向服务器请求一遍相同的数据。

这也体现了 Server Component 与 Client Component 的分工：

- Server Component 负责查询数据库。
- Client Component 负责抽屉打开、关闭等交互。
- 数据通过 Props 从服务端传给客户端。

### 统一触发器写法

触发器统一成：

```tsx
<SheetTrigger render={<Button variant="ghost" size="sm" />}>
  <Eye className="mr-1 size-4" />
  查看
</SheetTrigger>
```

`render` 里放一个空 Button 作为"画布"，Button 的实际内容（图标+文字）放在 Trigger 的 children 里。这是项目里 `DialogTrigger`、`AlertDialogTrigger` 已经在用的写法，Base UI 会把 children 合并到 render 元素上。之前有混用 `render` 里直接塞完整内容的情况，统一后更清楚。

## 六、实现更多操作菜单

现在改造 `user-account-actions.tsx`。

完整代码：

```tsx
"use client";

import { useState, useTransition } from "react";

import { MoreHorizontal } from "lucide-react";
import { toast } from "sonner";

import type { UserStatus } from "@/app/generated/prisma/client";

import {
  AlertDialog,
  AlertDialogAction,
  AlertDialogCancel,
  AlertDialogContent,
  AlertDialogDescription,
  AlertDialogFooter,
  AlertDialogHeader,
  AlertDialogTitle,
} from "@/components/ui/alert-dialog";
import { Button } from "@/components/ui/button";
import {
  DropdownMenu,
  DropdownMenuContent,
  DropdownMenuItem,
  DropdownMenuSeparator,
  DropdownMenuTrigger,
} from "@/components/ui/dropdown-menu";

import { deleteUserAction, setUserStatusAction } from "../actions";
import { UserResetPasswordDialog } from "./user-reset-password-dialog";

type UserAccountActionsProps = {
  userId: string;
  username: string;
  status: UserStatus;
};

export function UserAccountActions({
  userId,
  username,
  status,
}: UserAccountActionsProps) {
  const isActive = status === "ACTIVE";
  const nextStatus: UserStatus = isActive ? "DISABLED" : "ACTIVE";

  const [resetOpen, setResetOpen] = useState(false);
  const [deleteOpen, setDeleteOpen] = useState(false);

  const [deletePending, startDeleteTransition] = useTransition();

  async function handleStatusChange() {
    try {
      const result = await setUserStatusAction(userId, nextStatus);

      if (result.success) {
        toast.success(isActive ? "账号已停用" : "账号已启用");
      } else {
        toast.error(result.message ?? "操作失败");
      }
    } catch {
      toast.error("操作失败，请稍后重试");
    }
  }

  function handleDelete() {
    startDeleteTransition(async () => {
      try {
        const result = await deleteUserAction(userId);

        if (result.success) {
          setDeleteOpen(false);
          toast.success("用户已删除");
        } else {
          toast.error(result.message ?? "删除失败");
        }
      } catch {
        toast.error("删除失败，请稍后重试");
      }
    });
  }

  return (
    <>
      <DropdownMenu>
        <DropdownMenuTrigger render={<Button variant="outline" size="sm" />}>
          <MoreHorizontal className="mr-1 size-4" />
          更多
        </DropdownMenuTrigger>

        <DropdownMenuContent align="end">
          <DropdownMenuItem onClick={() => setResetOpen(true)}>
            重置密码
          </DropdownMenuItem>

          <DropdownMenuSeparator />

          <DropdownMenuItem onClick={handleStatusChange}>
            {isActive ? "停用账号" : "启用账号"}
          </DropdownMenuItem>

          <DropdownMenuSeparator />

          <DropdownMenuItem
            variant="destructive"
            onClick={() => setDeleteOpen(true)}
          >
            删除用户
          </DropdownMenuItem>
        </DropdownMenuContent>
      </DropdownMenu>

      <UserResetPasswordDialog
        userId={userId}
        username={username}
        open={resetOpen}
        onOpenChange={setResetOpen}
        hideTrigger
      />

      <AlertDialog
        open={deleteOpen}
        onOpenChange={(next) => {
          if (!deletePending) {
            setDeleteOpen(next);
          }
        }}
      >
        <AlertDialogContent>
          <AlertDialogHeader>
            <AlertDialogTitle>确认删除用户？</AlertDialogTitle>

            <AlertDialogDescription>
              即将永久删除用户「{username}」，该用户名会同时被释放。
              删除后无法恢复，请确认该用户没有需要保留的业务数据。
            </AlertDialogDescription>
          </AlertDialogHeader>

          <AlertDialogFooter>
            <AlertDialogCancel disabled={deletePending}>
              取消
            </AlertDialogCancel>

            <AlertDialogAction
              variant="destructive"
              onClick={handleDelete}
              disabled={deletePending}
            >
              {deletePending ? "正在删除..." : "确认删除"}
            </AlertDialogAction>
          </AlertDialogFooter>
        </AlertDialogContent>
      </AlertDialog>
    </>
  );
}
```

### 菜单项里为什么没写「正在处理...」？

下拉菜单的选项点击后默认会立刻关闭菜单。所以即便 `useTransition` 的 `pending` 变了，菜单项也已经不在屏幕上了，用户看不到「正在处理...」这个文案。

实际的操作反馈走 toast 就够了，不需要在菜单项里再显示一遍。删除操作不一样——它有弹窗，用户在弹窗里能看到「正在删除...」的状态，那里保留 pending 文案。

### 为什么要 try/catch？

`startTransition` 里如果 `await action()` 抛了异常（比如 `requireUserAdmin()` 拒绝，或者数据库连不上），异常会冒泡到最近的错误边界，用户看到的不是 toast，而是整页报错。

包一层 `try/catch`，在 `catch` 里给一个兜底的 `toast.error`，就能把所有异常都收进来，不会让整页崩溃。

### 弹窗为什么放在菜单外面？

重置密码弹窗和删除确认弹窗都与 `DropdownMenu` 同级，而不是嵌在 `DropdownMenuContent` 里面。

原因是菜单和弹窗都使用 Portal 挂载到 `document.body`，Base UI 菜单打开时会在内部维护焦点管理。如果弹窗根节点也嵌在菜单内容里，可能出现焦点冲突，导致弹窗里的输入框虽然看起来有焦点，但键盘输入进不去。

菜单项只负责把 `open` 设为 `true`，弹窗的挂载位置在菜单之外，两者互不干扰。

现在把详情抽屉接入列表。

每个入口的职责都很明确：

| 操作 | 实现方式 | 功能 |
|---|---|---|
| 查看 | 右侧抽屉 | 展示用户资料 |
| 编辑 | 页面跳转 | 修改用户名、手机号 |
| 更多 | 下拉菜单 | 重置密码、启用/停用、删除 |

### 每行四个弹层，会不会太重？

每行挂一个 Sheet、一个 DropdownMenu、两个 AlertDialog（删除确认 + 重置密码），十行就是四十个组件实例。目前数据量小没问题，但如果后面列表支持分页展示几百条，可以改成列表层面只挂载一套弹层，通过「当前选中的用户」状态来切换内容。

现在先不做——等后续批量操作那篇里自然会遇到这个优化点。

## 九、本篇小结

本篇主要完成了用户管理页面的交互优化。

从最初的多个按钮平铺，到现在的三个清晰入口：

- 查看：通过右侧抽屉快速查看用户资料。
- 编辑：进入独立编辑页面修改用户信息。
- 更多：将低频操作收纳到下拉菜单。

这看起来只是一次 UI 调整，但背后涉及了几个值得掌握的开发知识：

1. **不要手写 shadcn 已经提供的基础组件。** `sheet` 和 `dropdown-menu` 直接 `pnpm dlx shadcn add`，避免重复造轮子，也避免未来有人执行 `add drawer` 覆盖掉自己手写的文件。
2. **触发器统一写法。** `render={<Button />}` + children 放内容，这是 Base UI 组件的标准模式。
3. **业务常量集中管理。** 状态徽章样式、日期格式化函数提到 `constants.ts`，列表和详情共用。
4. **try/catch 兜底 Action 异常。** `startTransition` 里的异常不会自动变成 toast，要自己 catch 住。
5. **区分只读详情与业务修改操作。** 详情抽屉只查不改，避免重复实现业务逻辑。
6. **弹层提升到菜单外层。** 避免焦点冲突导致输入失效。

还有一个值得注意的设计原则：

**列表是工作入口，详情是信息窗口，编辑是业务操作，更多是辅助操作。**

当一个系统的功能逐渐增加时，不应该简单地在页面上不断堆叠按钮，而应该根据用户的操作频率和业务重要性，重新组织交互结构。

下一篇，我们可以继续完善用户管理模块，让用户列表具备更完整的筛选、状态过滤和批量操作能力。
